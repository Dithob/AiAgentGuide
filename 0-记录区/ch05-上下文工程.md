### 上下文工程 vs 提示词工程

| 维度         | 提示词工程              | 上下文工程                 |
| :----------- | :---------------------- | :------------------------- |
| **关注点**   | 单条指令怎么写          | 每次调用带什么内容         |
| **时间跨度** | 一轮对话                | 整个会话生命周期           |
| **核心问题** | 怎么让 LLM 理解指令     | 怎么让有限窗口装下关键信息 |
| **典型手段** | Few-shot、CoT、角色设定 | 裁剪、压缩、优先级分级     |
| **衡量指标** | 指令遵循度、输出质量    | Token 利用率、信息保留率   |
| **失败模式** | LLM 不按指令行事        | 关键信息被丢掉、Token 超限 |

两者不是替代关系，而是**互补关系**：好的提示词工程让单轮指令更有效，好的上下文工程让多轮对话可持续。在实际 Agent 项目中，上下文工程的重要性甚至超过提示词工程——因为 Agent 跑 30 轮后，提示词写得好不好已经不重要了，重要的是关键约束有没有被裁掉。

### 五种消息裁剪策略对比

| 策略           | 压缩率 | 信息保留 | 实现复杂度 | 额外 Token 开销 | 适用场景     |
| :------------- | :----- | :------- | :--------- | :-------------- | :----------- |
| **截断**       | 高     | 差       | O(1)       | 0               | 简单 demo    |
| **摘要压缩**   | 中高   | 中       | 中         | 高（调用 LLM）  | 长对话       |
| **滑动窗口**   | 中     | 中       | 低         | 0               | 实时交互     |
| **选择性保留** | 高     | 高       | 高         | 低              | 生产系统     |
| **语义保护型** | 最高   | 最高     | 最高       | 中              | 工业级 Agent |

消息裁剪优先级

| 优先级            | 消息类型                          | 裁剪策略                         | 理由                                             |
| :---------------- | :-------------------------------- | :------------------------------- | :----------------------------------------------- |
| **P0 🔴 永不裁剪** | System Prompt、当前用户输入       | 全量保留                         | System Prompt 是行为准则；当前输入是本轮任务目标 |
| **P1 🟠 尽量保留** | 工具调用 Schema、用户初始约束     | 全量保留，超限时压缩 Schema 描述 | 没有 Schema LLM 无法调用工具；初始约束影响全程   |
| **P2 🟡 可压缩**   | 工具返回值、Action-Observation 对 | 提取关键字段，丢弃原始大块输出   | 8000 行日志只需保留关键错误 3 行                 |
| **P3 🔵 可摘要**   | 中间推理过程（Thought）           | 摘要压缩，保留结论               | "让我想想..." 的推理链可压缩为结论               |
| **P4 ⚪ 可丢弃**   | 寒暄、确认、重复消息              | 直接丢弃                         | "好的"、"明白了" 无信息价值                      |

### 混合裁剪架构

💡 混合裁剪的核心思想

不是"选一个策略"，而是"给每类消息分配最合适的策略"。就像垃圾回收——不是所有垃圾一锅端，而是**分类处理**：可回收的提取精华、有害的单独处理、厨余的堆肥压缩、其他的直接丢弃。

```
                超出 Token 预算的完整上下文
                           │
                           ▼
                    ┌────────────┐
                    │  消息分类器  │
                    │type/priority│
                    └─────┬──────┘
                          │
       ┌──────────┬───────┼───────┬──────────┐
       │          │       │       │          │
       ▼          ▼       ▼       ▼          ▼
    [P0]       [P1]     [P2]    [P3]       [P4]
 System+     工具Schema  工具    中间推理    闲聊/确认
 当前输入    +用户约束    返回值
    │          │         │       │          │
    ▼          ▼         ▼       ▼          ▼
 全量保留    尽量保留   提取字段  摘要压缩    直接丢弃
            超限精简
       │          │       │       │
       └──────────┴───────┴───────┘
                          │
                          ▼
                    按优先级重组
                          │
                          ▼
 System → Schema → 摘要 → 保留消息 → 当前输入
```



###  上下文工程与记忆系统的关系

初学者常把"上下文工程"和"记忆系统"混为一谈。两者关系密切但关注点不同：

| 维度         | 上下文工程（本章）        | 记忆系统（第7章）                      |
| :----------- | :------------------------ | :------------------------------------- |
| **工作层**   | 短期 — 当前上下文窗口内   | 长期 — 跨会话持久化                    |
| **核心问题** | 窗口装不下时怎么裁        | 会话结束后怎么存                       |
| **时间尺度** | 单次会话内（分钟~小时）   | 跨会话（天~月）                        |
| **典型手段** | 裁剪、压缩、优先级分级    | 向量数据库、摘要持久化、KV 缓存        |
| **数据流向** | LLM ← 上下文窗口 ← 裁剪器 | LLM → 记忆写入 → 数据库 → 下次会话注入 |

两者协作的方式：记忆系统负责**存什么**（哪些经验值得跨会话保留），上下文工程负责**带什么**（这次调用 LLM 时，窗口里放什么）。记忆系统检索到的内容，会作为"记忆注入"消息进入上下文窗口，然后由上下文工程的裁剪策略决定是否保留。

### Claude Code 三级压缩链

#### 第1级：microCompact — 微压缩

**触发时机**：每轮对话后自动执行，当前上下文接近 70% 容量时。

**做法**：扫描对话历史中的工具返回值，将大块输出替换为摘要。例如 8000 行的 `read_file` 输出，压缩为"文件 app.py，共 800 行，主要函数：main()、process()、validate()"。

- **压缩率**：约 30-40%
- **信息损失**：低，只压缩工具返回值的冗余部分
- **额外开销**：小，用规则提取而非 LLM 摘要

#### 第2级：autoCompact — 自动摘要压缩

**触发时机**：当 microCompact 后仍接近 85% 容量时自动触发。

**做法**：用 LLM 对整个对话历史生成结构化摘要，然后用摘要替代旧消息，保留最近 N 轮完整对话。

- **压缩率**：约 60-70%
- **信息损失**：中，保留关键决策和约束，丢失推理细节
- **额外开销**：高，需要一次 LLM 调用生成摘要

#### 第3级：sessionMemoryCompact — 会话记忆持久化

**触发时机**：用户手动执行 `/compact` 命令，或会话结束前。

**做法**：将整个会话的精华写入持久化记忆文件（CLAUDE.md），下次会话启动时自动加载。这已经不是"压缩"，而是"转存"——把短期记忆转为长期记忆。

Q2: 五种消息裁剪策略分别是什么？各自的压缩率和信息保留如何？

① **截断**：超限时直接丢弃最早消息，压缩率高但信息保留差。② **摘要压缩**：用 LLM 生成旧对话摘要，压缩率中高、信息保留中等，但消耗额外 token。③ **滑动窗口**：保留最近 N 轮，上下文长度恒定，但不考虑重要性。④ **选择性保留**：按消息类型分别处理（System 全留、工具结果提取、闲聊丢弃），信息密度最高。⑤ **语义保护型**：锁定核心指令、保留行动-结果对、只压缩中间推理，压缩率和信息保留最优，但实现最复杂。

==Q4: Claude Code 的三级压缩链是什么？各级的触发时机和压缩方式有何不同？==

① **microCompact**（~70% 触发）：压缩工具返回值的大块输出为摘要，规则提取而非 LLM，压缩率 30-40%，信息损失低。② **autoCompact**（~85% 触发）：用 LLM 对旧历史生成结构化摘要，保留最近 N 轮完整对话，压缩率 60-70%，信息损失中等。有防死锁递归守卫和 3 次连续失败熔断。③ **sessionMemoryCompact**（手动/会话结束触发）：将整个会话精华写入 CLAUDE.md 持久化，下次会话自动加载，压缩率 >90%，只保留四类记忆（user/feedback/project/reference）。设计哲学是"渐进式压缩"——先低成本压低价值内容，不够再中成本压中价值，最后高成本转存高价值。

5. autoCompact 的防死锁设计是什么？

A限制最多压缩 3 次

B压缩失败后直接截断

C查询来源为 compact 时返回 false，防止递归压缩

D压缩时断开网络连接

**解析：**shouldAutoCompact 递归守卫：当查询来源是 session_memory 或 compact 时返回 false，防止"压缩→查询→再压缩"的死循环。另有 MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3 熔断。



10. 关于 Claude Code 的三级压缩链，以下说法正确的是？（多选）

AmicroCompact 用规则提取压缩工具返回值，不调用 LLM

BautoCompact 保留 20,000 token 给摘要，用 LLM 生成

CsessionMemoryCompact 将会话记忆持久化转存

D三级压缩按固定顺序依次执行，不可跳过

**解析：**三级压缩是按需触发的——microCompact 在 ~70% 时触发，只有不够才升级到 autoCompact (~85%)，再不够才升级到 sessionMemoryCompact。不是固定依次执行，而是渐进式升级。
