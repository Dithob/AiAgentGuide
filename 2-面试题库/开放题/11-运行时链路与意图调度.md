### O-24｜意图识别要不要单独拆一个 LLM 子任务？

- **级别**：L4　**来源**：你的疑问　**条目**：11

**参考回答**

> 先纠正一个前提：**意图识别是个"动作"不是"模块"**。三种方法里，"语义理解"那一层的实现本来就是 LLM。所以真正的问题是：**要不要把它拆成一次独立的 LLM 调用**？
>
> 五个权衡：
> - **延迟**：拆开多一次往返（+300ms~1s）；融合进主调用没额外延迟
> - **成本**：拆开多一次调用（但 prompt 小、可缓存）；融合让主 prompt 变大
> - **可控性**：拆开容易强约束（枚举 / JSON Schema）；融合混在生成里难约束
> - **可观测**：拆开能单独记录意图、看分布、做回归；融合埋在输出里难追踪
> - **可评测**：拆开能算准确率、混淆矩阵（意图分类是有标签的！）；融合几乎没法单独评测
>
> 我的建议是**分阶段**：
> 1. **验证期**——拆成独立子任务（甚至先上小模型）。你真需要的是"可观测"，不是省那 300ms。
> 2. **稳定期**——逐步融进主调用（用结构化输出约束），省一次往返换延迟。
> 3. **成熟期**——高频意图下沉成规则（关键词/缓存），热点路径不该每次过 LLM。
>
> **三个必须注意的点**：①**错误放大**——意图识别错了后面全错，所以要有兜底（低置信度就反问用户，或走通用路径）；②**要建评测集**——这是少数能用传统 ML 指标衡量的 LLM 环节；③**主流替代方案**——Function Calling 其实已经吞掉了一部分意图识别（让模型直接决定调哪个工具 = 意图识别 + 工具选择合并成一步），代价是中间意图不可观测。

**追问链**

1. → 意图识别错了怎么兜底？（低置信度反问用户，而不是硬猜）
2. → 你怎么知道意图识别准不准？（建带标签的评测集，看混淆矩阵，别靠感觉）
3. → 那为什么又说 Function Calling 已经吞掉了它？（模型直接选工具确实等价，但损失了可观测性——这正是拆与不拆的取舍核心）

**雷区**

- ❌ 说"意图识别只能靠关键词匹配"
- ❌ 一味追求"融合省延迟"，忽略了验证期最需要的是可观测和可评测
