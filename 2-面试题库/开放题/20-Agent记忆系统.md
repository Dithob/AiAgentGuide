### O-38｜Agent 的记忆怎么分类？召回太多会有什么问题？

- **级别**：L4　**来源**：ch07 八股 Q12 + §7.8 治理法则（手法 B+C+D）　**条目**：20

**参考回答**

> **先说分类**。按生命周期分三层：**短期记忆**（当前对话历史，过长走 LLM 摘要压缩）、**工作记忆**（当前任务的状态与中间变量，**几乎不能压**——丢掉任务状态等于从头再来）、**长期记忆**（历史摘要与交互，向量库 + 语义检索）。
> 长期记忆内部还要再分两档：**静态的**（用户偏好、系统规则、领域事实）几乎不变，**直接注入 System Prompt**，**不该进向量库**；**动态的**（对话摘要、执行经验、行为模式）持续更新，走向量库按相关性检索。
>
> **再说召回**。不能只看相似度，用**三维综合评分**：`recall_score = 意图匹配 × w1 + 时间衰减 × w2 + 频率加权 × w3`。意图匹配是 query 与记忆的余弦相似度；时间衰减是 `e^(-λΔt)`；频率加权是 `log(1 + 成功召回次数)`——**注意是"成功"召回，被召回但没帮上忙的不该涨权重**。
>
> **召回太多比太少更危险**，三个危害：**注意力稀释**（模型关注无关内容）、**指令冲突**（"偏好简洁"和"要求详细"同时召回）、**token 浪费**（挤掉 P0/P1）。
> **四道防线**：数量上限（每次 ≤5 条，简单问题 ≤3 条）、相关性阈值（< 0.7 不召回）、冲突检测（多条矛盾取最新的）、优先级排序（核心指令 > 最近经验 > 补充信息）。
> 再加一个 **JIT 原则**：不在一开始塞满上下文，而是每一步只注入当前需要的信息。

**追问链**

1. → 工作记忆和短期记忆怎么区分？（短期是"聊了什么"，工作记忆是"任务进行到哪一步"；后者几乎不可压）
2. → 静态记忆为什么不进向量库？（它几乎不变，检索是白花钱；直接写进 System Prompt 的静态区还能命中前缀缓存）
3. → 无服务端的 CLI Agent 怎么做记忆？（纯文件系统 + LLM 驱动压缩：轮次分割、三层压缩触发 80%/60%/413、AI→规则降级、增量压缩（上次压缩水平的 80% 才再压）、Provider/Reducer、双作用域 + LRU）
4. → 它写记忆的原则是什么？（**只存无法从当前项目状态推导的上下文**——能从 `package.json` 读到的就不写。四类型：user / feedback / project / reference）

**雷区**

- ❌ 说"记忆就是把历史都存进向量库"
- ❌ 说"召回得越多越保险"
- ❌ 把"召回次数"当成 `frequency_weight` 的输入
