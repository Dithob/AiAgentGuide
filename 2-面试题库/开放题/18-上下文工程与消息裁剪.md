### O-34｜上下文工程和提示词工程有什么区别？为什么说前者更重要？

- **级别**：L3　**来源**：ch05 §5.1（手法 A+D）　**条目**：18

**参考回答**

> **提示词工程管"单轮怎么说"**——关注点是单条指令怎么写，时间跨度是一轮对话，核心问题是"怎么让 LLM 理解指令"，手段是 Few-shot / CoT / 角色设定，衡量指标是指令遵循度和输出质量，失败模式是"LLM 不按指令行事"。
> **上下文工程管"这次调用带什么"**——关注点是一次调用带什么内容，时间跨度是整个会话生命周期，核心问题是"怎么让有限窗口装下关键信息"，手段是裁剪 / 压缩 / 优先级分级，衡量指标是 token 利用率和信息保留率，失败模式是"关键信息被丢掉、token 超限"。
>
> **它们不是替代关系，是互补关系**，但工程权重不一样：**Agent 跑 30 轮之后，提示词写得好不好已经不重要了，重要的是关键约束有没有被裁掉。** 所以长会话场景里上下文工程的权重更高。

**追问链**

1. → 那上下文工程和记忆系统的边界在哪？（记忆管"**存什么**"——跨会话持久化；上下文工程管"**带什么**"——窗口内装什么。检索回来的记忆还要过一遍裁剪器）
2. → 裁剪时最不能丢什么？（P0：System Prompt 和当前用户输入。丢了 System，行为会漂；丢了当前输入，本轮任务目标没了）
3. → 为什么不能简单地"从旧到新删"？（那是截断，按**位置**裁。但位置和新旧跟重要性没有相关性——工业级按**语义/优先级**裁）

**雷区**

- ❌ 把两者说成"同一个东西的新旧叫法"
- ❌ 说"上下文工程就是记忆系统"

### O-35｜Claude Code 的三级压缩链是怎么设计的？为什么要渐进式？

- **级别**：L4　**来源**：ch05 八股 `==Q4==`（手法 B+C+F）　**条目**：18

**参考回答**

> 三级，**按需升级而不是依次固定执行**。
> **① microCompact（~70% 触发）**：扫描历史里的工具返回值，把大块输出替换为**规则提取**的摘要——8000 行 `read_file` 输出压成「文件 app.py，共 800 行，主要函数 main/process/validate」。压缩率 30-40%，信息损失低，**不调 LLM**。
> **② autoCompact（~85% 触发）**：第 1 级后还不够才触发。用 **LLM** 对历史生成结构化摘要，摘要替代旧消息、**保留最近 N 轮完整对话**。压缩率 60-70%，信息损失中等，开销高（一次 LLM 调用）。
> **③ sessionMemoryCompact（手动 `/compact` 或会话结束）**：把会话精华写入持久化记忆文件，下次会话自动加载。压缩率 >90%——**严格说这不是压缩而是"转存"**，短期记忆转长期记忆。
>
> **为什么渐进**：这是一个**成本-收益阶梯**——能用规则提取的绝不调 LLM。工具返回值是半结构化的（行数、文件名、函数名、错误行），规则提取性价比远高于 LLM 摘要；而 microCompact 跑在每轮对话后，调 LLM 会直接抬高每轮的延迟。
> 设计哲学一句话：**先低成本压低价值内容，不够再中成本压中价值，最后高成本转存高价值。**

**追问链**

1. → 七、八十五这两个阈值在防什么？（给"下一轮输入 + 工具返回值"和"压缩动作自身消耗"留余量；和"有效上下文窗口"公式里减掉的 `max(maxOutputTokens, 20000)`、`AUTOCOMPACT_BUFFER 13,000` 是同一个预算方程的两端）
2. → autoCompact 有什么保护机制？（**递归守卫**：`shouldAutoCompact` 在查询来源是 `session_memory` 或 `compact` 时返回 false，防"压缩→查询→再压缩"死循环；外加 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3` 熔断）
3. → 迁移到自己的项目先做哪一级？（**先做 P2 工具返回值裁剪**——收益最大、零 LLM 成本、风险最小。LLM 摘要放最后，因为它是唯一引入新故障模式的环节，需要配降级链 AI → 规则 → 硬截断）

**雷区**

- ❌ 说"三级按固定顺序依次执行，不可跳过"（这是原题的干扰项 D）
- ❌ 说"压缩率越高越好"——压缩率与信息保留反向
