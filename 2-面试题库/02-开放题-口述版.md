### O-01｜从架构角度说明 Agent 比 ChatBot 多了什么

- **级别**：L3　**来源**：Q(ch01-1) 衍生（手法 A+C）　**卡片**：K-01, K-02

**参考回答**

> 差异不在模型，在架构。ChatBot 就是 `prompt → LLM → 文本`，一问一答。Agent 在 LLM 外面加了三层：
> ①**工具层**——通过 Function Calling 把 LLM 的决策落到真实动作（查 API、跑代码、读文件）；
> ②**记忆层**——短期记忆维持当前任务的上下文，长期记忆用向量库跨会话积累；
> ③**循环控制层**——把一次调用变成"感知→思考→行动→观察→再思考"的闭环，直到任务完成或触发终止条件。
> 再往外还有权限层和沙箱，因为工具是"动作"，会碰真实世界。
> 所以 ChatBot 是"会说"，Agent 是"会想、会做、会改"。

**追问链**

1. → 那这四层里，哪一层去掉影响最大？（循环控制层——去掉就退化成第二代的单步工具调用）
2. → 权限层为什么是必需的？（模型理解意图 ≠ 获得授权；高风险操作要人在环）
3. → 这三层在工程上分别落到哪些具体技术？（工具层→Function Calling/MCP；记忆层→向量库+摘要压缩；循环层→Agent Loop 引擎）

**雷区**

- ❌ 说"Agent 用了更大的模型"——底层是同一个 LLM
- ❌ 只说"Agent 会调工具"——漏掉循环和记忆，那是第二代

### O-02｜为什么同样一段中文比英文贵？工程上怎么应对？

- **级别**：L3　**来源**：Q(ch00-1) 衍生（手法 A+C）　**卡片**：K-05, K-06

**参考回答**

> 根因是**词表偏置**。计费按 Token 不按字符，而主流模型的 Tokenizer 词表以英文为核心：英文一个单词大概 1~1.3 个 Token，中文一个字要 1.5~2 个。所以同样一段内容，中文的 Token 数大约是英文的 1.5 到 2 倍，成本更高，而且更占上下文窗口。
> 工程上有四个手段：①换中文优化的模型，比如 Qwen、GLM；②把固定前缀（System Prompt + 工具 Schema）放到最前面吃 Prompt Cache，那是 50% 的折扣；③约束输出格式，因为输出 Token 本来就比输入贵 3~4 倍；④长材料先用摘要或检索压缩，别整段塞。
> 估算上我会记两个数：英文大概字符数除以 4，中文大概除以 2。

**追问链**

1. → 那中文 Token 多，是不是模型的中文能力就更差？（不是，词表效率 ≠ 理解能力，两件事）
2. → 如果预算很紧，你会先砍哪一块？（先砍输出——输出单价是输入的 3~4 倍）
3. → 你怎么实测一个模型的 Token 消耗？（用官方 Tokenizer 逐段计数，别用字符数猜）

**雷区**

- ❌ "中文一个字固定 3 个 Token"——那是 UTF-8 字节数，不是 Token 数

### O-03｜上下文窗口怎么分配？怎么最大化缓存命中？（★高频 L4）

- **级别**：L4　**来源**：Q-03 / Q-04 衍生（手法 B+C+D）　**卡片**：K-07, K-08, K-09

**参考回答**

> 我会把窗口分三段讲。
> **第一段是固定部分**：System Prompt、工具 Schema、Skill 触发词列表，典型只占 2% 到 8%，但它们**每次请求都要重发**，所以是最该被缓存的部分。
> **第二段是动态部分**：记忆注入、对话历史、工具返回结果，占 20% 到 55%，逐轮增长，缓存不了，只能靠压缩和按需召回控制。
> **第三段是输出预留**：留 30% 到 50%，因为模型要生成，不留就会被截断。
>
> 缓存命中的条件是**前缀完全相同，一字之差就全部失效**，所以结构原则是三条：
> ①固定内容放最前面——System Prompt、工具定义、Skill 描述；
> ②动态内容放最后——对话历史、记忆召回、用户当前输入；
> ③**把 System Prompt 和工具定义合并成同一条 system 消息**，增加前缀连续性，也因为 OpenAI 要求至少 5 条消息才触发缓存，合并后更容易达标。
>
> 效果上，固定 2K + 半固定 2K + 10 轮对话的规模，第 5 轮命中率大概 50%，第 10 轮能到 70%。
> 补充一个坑：教程里"缓存折扣"有两个口径——**单价口径约 50%**，**成本降幅口径约 90%**，回答时要说清是哪个口径。

**追问链**

1. → 对话历史涨到占 40% 了怎么办？（先摘要压缩旧轮次，再考虑向量召回按需注入）
2. → 记忆召回为什么缓存不了？（按需动态，每轮召回的片段可能不同，前缀就断了）
3. → 缓存对推理延迟有影响吗？（有，命中部分省掉 KV 计算，首 Token 延迟明显下降）
4. → 如果我要放一个动态的 few-shot 示例，放哪？（放动态区末尾，别插在固定区后面）

**雷区**

- ❌ 把用户输入放最前面——后续所有固定内容的前缀都被污染，缓存全失效
- ❌ 说"缓存命中率 100%"——只有固定前缀能保证，动态部分永远不行

### O-04｜上下文窗口满了怎么处理？五种策略怎么选？

- **级别**：L4　**来源**：Q-04 衍生（手法 A+D）　**卡片**：K-07

**参考回答**

> 四种基础策略，加一个组合：
> ①**窗口满了才有损失**——所以第一道防线是"不该进的别让它进"，工具返回结果先裁剪/摘要再注入；
> ②**截断**：保留最新消息，丢掉最早的。最简单，但会丢历史；
> ③**摘要压缩**：用 LLM 把旧对话压成摘要。有信息损失，还要额外一次调用；
> ④**向量召回**：历史入向量库，按需检索相关片段注入。不丢信息，但要维护向量库且有检索延迟；
> ⑤**滑动窗口**：固定长度，旧消息自动移出。实现简单，同样是丢历史。
>
> 生产里通常是**摘要 + 向量召回组合**：近几轮原样保留（保证连贯），更早的压成摘要，再往前的进向量库按需召回。
> 另外还要注意 **Lost in the Middle**——就算能塞进去，模型对中段信息的注意力也会下降，所以关键信息要放头尾。

**追问链**

1. → 摘要什么时候做？（到达阈值时做，别每轮都做，否则成本和延迟都受不了）
2. → 摘要本身会不会引入错误？（会，所以要保留原文索引，摘要只当导航）
3. → 你怎么衡量压缩有没有伤到效果？（用评估集对比压缩前后的任务成功率，见第 23 章）

**雷区**

- ❌ 只说"截断"——那是最粗暴的一种，面试官会继续追问更优解

### O-05｜为什么要用 Attention 而不是 RNN？

- **级别**：L2　**来源**：Q(ch00-6) 衍生（手法 A+B）　**卡片**：K-10

**参考回答**

> RNN 有两个死穴。一是**长距离依赖丢失**：它必须按顺序处理，第 1 个词的信息传到第 100 个词时基本衰减没了，LSTM 的门控只是缓解，没有根治。二是**无法并行**：顺序依赖决定了 GPU 的并行能力被浪费，训练以周计。
> Attention 一次解决两个问题：每个词可以直接和序列里所有词算相关度，不用逐步传递；而且所有位置可以同时计算，训练时间能从天级压到小时级。这就是论文标题"Attention Is All You Need"的底气。
> 代价是复杂度变成 O(n²)，序列很长时是瓶颈，所以工程上会有滑窗注意力、稀疏注意力、GQA 这类优化。

**追问链**

1. → 写出 Self-Attention 的公式。（`Softmax(QKᵀ/√d_k)V`）
2. → 为什么要除以 √d_k？（防点积过大导致 Softmax 梯度消失，是数值稳定性，不是归一化）
3. → O(n²) 具体怎么优化？（滑窗/稀疏注意力、KV Cache、FlashAttention 的 IO 优化）

**雷区**

- ❌ 说"除以 √d_k 是为了归一化"

### O-06｜RoPE 怎么工作？为什么长上下文都靠它？

- **级别**：L2　**来源**：教程 §1.2（手法 B+C）　**卡片**：K-12

**参考回答**

> 先讲为什么需要位置编码：Self-Attention 是位置无关的，"猫追狗"和"狗追猫"不加位置信息，模型看到的结果一样。
> RoPE 的做法是**在 Q 和 K 上施加旋转**：把 Q、K 向量看成二维平面上的点，按词的位置旋转不同角度。两个词距离越远，旋转角度差越大，它们的点积（也就是注意力分数）就越小——于是注意力分数**天然包含了相对位置**，不需要额外加位置向量。
> 它成为主流有三个原因：①**外推性强**，训练只见过 4K 位置，推理能扩到 128K+，配合 YaRN 这类缩放技术；②编码的是**相对位置**，不用像绝对位置编码那样学固定向量；③**不增加可训练参数**，旋转矩阵是计算时施加的。
> GPT-4、Llama、Qwen、DeepSeek 基本都用 RoPE。

**追问链**

1. → 外推（extrapolation）为什么重要？（训练成本决定不可能什么长度都训，推理要能延长）
2. → 直接外推会有问题吗？（会，超长位置的角度超出训练分布，会有性能衰减，所以需要位置插值/缩放）

**雷区**

- ❌ 说 RoPE 编码"绝对位置"
- ❌ 说 RoPE 引入了额外的可训练参数

### O-07｜预训练 / SFT / RLHF 的区别？能互相替代吗？

- **级别**：L3　**来源**：Q(ch00-6) 衍生（手法 A+D）　**卡片**：K-14

**参考回答**

> 三阶段，各管一件事。
> **预训练**：用 10~15 万亿 Token 的无标注文本做 Next Token Prediction，学语言规律和世界知识。这一步占 99% 以上的算力，产出**基座模型**——它很博学但不会对话，你问"你好"，它可能续写"欢迎光临"。
> **SFT**：用 1 万到 10 万条高质量的"指令-回答对"做监督微调，教模型**怎么回答**——格式、风格、指令遵循。本质是行为模仿，LIMA 论文证明 1000 条高质量数据就能显著提升对话能力。
> **RLHF**：用人类偏好数据（回答 A 比 B 好）训奖励模型，再用 PPO 优化，教模型**什么回答更好**——质量、安全、减少幻觉。
>
> **不能互相替代**。SFT 的学习信号是逐 Token 的交叉熵，只能模仿，教不了模型"什么是好回答"；RLHF 的学习信号是整体奖励打分，但它**教不了新知识**，只能优化已有能力的表达方式。所以是互补的：SFT 教格式，RLHF 教质量。

**追问链**

1. → 那知识到底从哪来？（全部来自预训练，SFT/RLHF 都不注入新知识）
2. → 如果我想让模型学会公司内部知识，该动哪一步？（都不动——用 RAG 或微调，但那是另一条路线，注意区分"知识注入"和"行为对齐"）
3. → SFT 数据量和质量哪个更重要？（质量，LIMA 是最直接的证据）

**雷区**

- ❌ 说"RLHF 能让模型学到新知识"

### O-08｜DPO 和 PPO 的区别？为什么趋势是 DPO？

- **级别**：L3　**来源**：教程 §1.3 补充八股 Q6（手法 A+C）　**卡片**：K-15

**参考回答**

> 两者都是做偏好对齐，差别在流程。
> **PPO** 是传统 RLHF：先训一个奖励模型（RM），再用 RM 打分通过 PPO 做强化学习优化。链路长、要额外加载一个模型、超参敏感、训练不稳定。
> **DPO** 跳过奖励模型，直接用偏好数据（A 比 B 好）通过一个简化目标函数优化模型。数学上已经证明 DPO 和 PPO 在最优解上等价，但工程上省掉一个 RM、更稳定、更快更便宜。
> 所以 2024 年之后 Llama 3、DeepSeek-V3、Qwen 2.5 基本都转向 DPO 或其变体。
> 边界要说一句：需要**在线采样**的场景 PPO 仍有优势，离线训练场景 DPO 是首选。另外还有 RLAIF，用 AI 代替人类做偏好标注来降本。

**追问链**

1. → 为什么 DPO 不需要奖励模型？（它把"奖励"隐式地编码进了策略与参考策略的比值里，等价推导掉了 RM）
2. → 偏好数据从哪来？（人工标注排序，或 RLAIF 用强模型标注）

### O-09｜System 和 User Prompt 的区别？怎么防绕过？

- **级别**：L3　**来源**：Q(ch00-3) 衍生（手法 A+C）　**卡片**：K-16

**参考回答**

> **System Prompt** 设定"你是谁、该怎么做"——角色、行为规则、输出格式、安全约束，在整个对话里持续生效，API 里是 `role: "system"`。**User Prompt** 是用户每次的具体诉求，`role: "user"`。一句话：System 决定"怎么做"，User 决定"做什么"。
> 为什么 System 更重要：它定义了行为边界和安全约束，而且是**多轮持续生效**的——用户后面怎么绕都绕不开它。在 Agent 里 Prompt 还不只是交互入口，它是决策的方向盘，规划、工具选择、输出格式都受它控制。
> 防绕过上我会做三层：①System 里写死权限边界和拒答规则；②涉及工具调用的动作走**运行时权限判定**，不能靠模型自律；③高层风险操作强制人工确认。要注意 Prompt 层面的防护是可以被 Prompt Injection 攻击的，所以真正的边界必须在代码层，不在 Prompt 层。

**追问链**

1. → 那 Prompt 里写"不要泄露系统提示词"有用吗？（有限，属软约束，必须配合输出过滤）
2. → 用户把恶意指令包装成"文档内容"塞进来怎么办？（工具返回和外部内容一律当不可信输入，和用户指令分级处理）

**雷区**

- ❌ 说"System Prompt 只是位置不同，本质一样"

### O-10｜CoT 为什么有效？什么时候反而有害？

- **级别**：L3　**来源**：Q(ch00-4) 衍生（手法 B+D）　**卡片**：K-17

**参考回答**

> CoT 有效有两个机制。①**扩展推理空间**：每生成一步推理，就为下一步提供了更多上下文，把一个大跳步拆成一串小跳步，单步难度下降。②**减少错误传播**：中间步骤可以自我检查，避免"一步错步步错"。论文里数学推理任务上能提升 15~30% 的准确率。
> 代价是**增加输出 Token**，而输出 Token 比输入贵 3~4 倍，还会拉长延迟。
> 所以它有害的场景很明确：①**简单问答/事实查询**——本来一步能答，强行推理反而可能把模型绕进去，还可能"过度推理"出错误结论；②**延迟敏感场景**——比如在线交互式补全；③**成本敏感且收益低的任务**。
> 我的判断标准是：任务**需不需要中间步骤**。需要（数学、逻辑、多跳推理）就上 CoT；不需要就不上。
> 再往上还有 Self-Consistency——多次采样后多数投票，正确路径更容易收敛，但成本是单次的 N 倍，只适合有确定答案的题。

**追问链**

1. → 那 ToT 什么时候用？（解空间大、需要探索和回溯的规划/创意类问题，代价是 Token 和延迟更大）
2. → 怎么判断 CoT 有没有真的起作用？（用评估集对比开/关的准确率，别靠感觉）

**雷区**

- ❌ 说"CoT 对所有任务都有提升"
- ❌ 把"梯度下降""反向传播"说成 Prompt 技巧

### O-11｜Embedding 是什么？RAG 为什么不直接塞全文？

- **级别**：L3　**来源**：Q(ch00-5) 衍生（手法 A+B）　**卡片**：K-18

**参考回答**

> Embedding 把文本映射成高维稠密向量，通常 768 到 3072 维，让语义相近的文本在向量空间里距离也近。它是语义检索、推荐、聚类这些能力的地基，也是 Agent 长期记忆的实现方式。
> **RAG 不直接塞全文**有三个原因：①全文可能直接超出上下文窗口；②就算塞得进，大量无关信息会**稀释注意力**，模型反而答得更差，中段的信息还特别容易被忽略（Lost in the Middle）；③Token 成本高、延迟大。
> 所以正确姿势是：文档切 Chunk → Embedding 入库 → 用户问题也 Embedding → 检索最相似的几个片段 → （可选 Rerank）→ 只把这几段注入上下文。这是在**准确性、速度、成本**三者之间取平衡。

**追问链**

1. → 那为什么不干脆把整个知识库微调进模型？（微调成本高、更新不灵活、容易灾难性遗忘；RAG 的检索结果可溯源、可热更新）
2. → 检索不到怎么办？（补 BM25 做混合检索、加 Rerank、优化 Chunk 切分策略）
3. → Chunk 切多大合适？（看文档结构，一般几百 Token 起步，重叠一部分保上下文；代码类按函数/类切）

**雷区**

- ❌ 说 Embedding 是为了压缩存储

### O-12｜余弦 / 欧氏 / 点积怎么选？为什么要先归一化？

- **级别**：L2　**来源**：Q-06 衍生（手法 A+D）　**卡片**：K-18

**参考回答**

> 三个指标的区别在"看不看长度"。
> **余弦相似度**只看方向不看长度，值域 [-1, 1]，1 表示方向完全一致、-1 表示相反，所以对文本长短不敏感——语义检索最常用。
> **欧氏距离**看绝对距离，值域 [0, +∞)，对向量长度敏感。
> **点积**同时看方向和大小，值域 (-∞, +∞)，计算最快。
> **归一化**的意义在于：把向量单位化后，点积和余弦就等价了——这样既快又保留语义性质，所以很多向量库在入库时就做了归一化，然后直接用点积检索。
> 补充一个坑：高维空间里余弦相似度的区分度会下降（维度灾难），所以实践中常用 Rerank 模型做二次精排来补救。

**追问链**

1. → 那什么时候该用欧氏距离？（更适合连续数值型特征，比如聚类场景）
2. → 归一化后还能算欧氏距离吗？（能，但此时欧氏距离和余弦是单调对应的，二选一即可）

### O-13｜一个需求该不该上 Agent？怎么判断？（L4）

- **级别**：L4　**来源**：Q-05 衍生（手法 C+D）　**卡片**：K-04

**参考回答**

> 我会问五个问题，任何一个是否定就先别上 Agent。
> ①**流程能不能被枚举完？** 能被枚举完的，用工作流引擎/状态机更快更稳更便宜。Agent 的价值恰恰在"路径不确定"。
> ②**是否需要外部实时数据或工具？** 需要工具才有上 Agent 的理由；纯文本问答用普通 LLM 调用就够。
> ③**失败代价有多大？** 代价高就必须配人工审核或权限分级，那架构复杂度会完全不同。
> ④**延迟和成本容忍度如何？** Agent 每个决策点都是一次 LLM 调用，多轮下来延迟和费用都不低。
> ⑤**有没有可量化的成功标准？** 没有的话，你连它到底变好还是变坏都判断不了。
>
> 结论模板：如果"流程不可枚举 + 需要工具 + 有可量化的验收标准"，那就上 Agent；否则优先做确定性流程，把 LLM 当其中一个环节用。

**追问链**

1. → 那"智能客服"算不算 Agent？（固定问答库不算；如果它要调工具查订单状态、发起退款，那就是 Agent）
2. → 上了之后怎么验证值不值？（建评估集，对比 Agent 方案和固定流程的任务成功率、平均成本、P95 延迟）

**雷区**

- ❌ 把"用了 LLM"等同于"用了 Agent"

### O-14｜"只决定不执行"意味着什么？工程后果是什么？

- **级别**：L3　**来源**：Q(ch00-6/ch01-21) 衍生（手法 B+C）　**卡片**：K-20

**参考回答**

> Function Calling 里 LLM 只输出"函数名 + 参数"的 JSON，**不执行任何代码**。执行是开发者代码的事，执行结果再作为工具消息注入回上下文，模型基于结果继续推理——这个循环就是 Agent 的工具层。
> 这个事实带来四个工程后果：
> ①**需要自己的执行循环**，处理"调 API → 解析 tool_call → 执行 → 回填结果 → 再调 API"，还要处理异常与重试；
> ②**安全边界在代码层**，不在模型层——所以要有权限判定（allow / deny / ask 三态）、沙箱、危险命令拦截；
> ③**工具描述是关键输入**，它写在上下文里，描述写得含糊会直接导致选错工具或参数填错，而且工具描述本身还占 Token；
> ④**工具数量要控制**，多了会导致选择困难，所以要有工具路由（按意图先筛候选工具）。
> 另外 `strict` 模式可以强制模型 100% 遵守 JSON Schema，减少解析失败。

**追问链**

1. → 为什么权限要做三态而不是布尔？（因为"系统也不该替用户做决定"——ask 是承认第三态；且 deny 必须对该次调用粘性生效，不能重试变成 allow）
2. → 多步工具调用会有什么新问题？（上下文膨胀、并发下的状态一致性、中断语义）

**雷区**

- ❌ 说"LLM 会执行函数"

### O-15｜开源还是闭源？你的选型决策框架是什么？（L4）

- **级别**：L4　**来源**：教程 §1.7（手法 C+D）　**卡片**：K-21

**参考回答**

> 三个维度按顺序过：
> ①**合规能不能过**——数据能不能出境、要不要私有化。金融医疗这类敏感数据，这一步就直接决定只能选开源私有部署。这是硬门槛，排第一。
> ②**能力够不够用**——在目标任务上的准确率是否达标。闭源在复杂推理和工具调用上通常还领先，但差距在缩小，很多场景开源已够用。
> ③**成本可不可控**——按"单价 × 预估调用量"算。高频调用开源长期更便宜（没有按量付费）；低频场景闭源按量付费反而更省。
> 另外还要看：是否需要微调定制行为（只有开源能做）、团队有没有运维推理服务的能力、生态是否稳定。
>
> 落地策略我一般用**混合**：原型和开发阶段用闭源快速验证 Agent 逻辑，上线后把非关键链路切开源降本。好框架像 LangGraph 支持改一行配置切模型，所以这个切换成本很低。

**追问链**

1. → 切换模型会有什么隐性成本？（Prompt 需要重调、工具调用格式可能有差异、行为不一致需要重新评估）
2. → 怎么证明"能力够用"？（在自建评估集上跑，看任务成功率，不看排行榜）
3. → 私有化部署的代价是什么？（要自己扛推理框架、显存、并发、监控，见第 26 章）

**雷区**

- ❌ 说"开源 = 免费可商用"——要逐个看许可

### O-16｜四种思维框架怎么递进？实际怎么选？

- **级别**：L3　**来源**：Q(ch00-4) 衍生（手法 A+C）　**卡片**：K-23

**参考回答**

> 它们是递进关系，每一层在前面基础上加一种能力：
> **CoT**——只会推理，适合数学逻辑这类纯思考任务，不接触外部世界；
> **ReAct**——在 CoT 上加了"行动"，推理和工具调用交替，所以需要实时数据或精确计算的任务它能做；
> **Plan & Execute**——再往上加"全局规划"，对多步任务先出计划再执行，避免走一步看一步反复绕路；
> **Reflection**——加"自我审查"，先生成再检查修正，用成本换质量。
> 另外 **ToT** 是多路径探索加回溯，适合解空间大、需要试错的规划类问题，可以看作 CoT 的进阶变体。教程里"四种"和"CoT→ReAct→ToT"两种列举都有，我按四种记。
>
> 选择原则是**越匹配越好，不是越复杂越好**：先看需不需要外部信息——不需要就 CoT，最省；需要就上 ReAct；步骤长且互相依赖就先规划；质量比成本重要再加 Reflection。复杂框架在简单任务上只会更贵更慢，还可能引入新的失败模式。

**追问链**

1. → ReAct 的失败模式有哪些？（工具选错、陷入循环、观察结果被误读、Token 爆掉）
2. → 怎么防止 Agent 陷入死循环？（最大步数限制、重复动作检测、反思触发、超时熔断）

### O-17｜反思模块什么时候触发？不触发会怎样？

- **级别**：L3　**来源**：Q-16 衍生（手法 A+B）　**卡片**：K-02, K-23

**参考回答**

> 反思的触发条件有三类：①**工具调用失败**；②**结果不符合预期**（比如返回为空、格式不对、和已有信息矛盾）；③**Agent 陷入循环**（重复同样的动作）。
> 另外高级一点的实现会在**关键决策点主动反思**，而不是等出错才反思。
> 反思做的事是：评估当前策略有效性 → 分析失败原因 → 调整后续规划。
> 如果完全没有反思，Agent 就退化成"一次性执行 + 报错即止"——它看不到自己行动的后果，也就没有纠错能力。这也正是"观察"这个能力域为什么是闭环的灵魂：**没有观察就没有纠错，没有纠错就只是自动化脚本**。
> 但要提醒一点：反思不是万能的。如果模型自身判断力不足，反思可能**固化错误**（自己给自己打高分）。所以反思要和外部信号（真实工具结果、评估集）配合，不能只靠模型自省。

**追问链**

1. → 反思的成本怎么控制？（只在触发条件命中时做，不要每轮都反思）
2. → 反思和"重试"有什么区别？（重试是重复动作，反思是改变策略）

### O-18｜Attention 用 O(n²) 换来了什么？什么时候它反而不如 RNN？

- **级别**：L4　**来源**：`==Q1==` 衍生（手法 D 边界权衡 + F 反向假设）　**卡片**：K-10

**参考回答**

> Attention 花 O(n²) 买了两样东西：
> ①**信息路径从 O(n) 降到 O(1)**——任意两个词一步直达，不用逐跳传递，这是它能解决长距离依赖的根本原因；
> ②**全位置并行**——Q/K/V 都是整块矩阵乘，没有跨位置依赖，GPU 能吃饱。
>
> 代价是**时间和显存都是 O(n²)**（要物化一个 n×n 的注意力矩阵）。所以序列一长，它反而可能不如 RNN 系：
> - **超长序列**：n=100K 时 n² 就是 10¹⁰ 量级，显存先炸；
> - **流式/增量推理**：RNN 每步只维护一个固定大小状态，Attention 要拖着不断增长的 KV Cache；
> - **边缘/端侧**：内存受限时，线性复杂度更现实。
>
> 工程上的四条出路：**FlashAttention**（分块+重算，只优化 HBM/SRAM 之间的 IO，不改变数学，结果完全等价）、**滑窗/稀疏注意力**（只算邻近或选定的位置对）、**线性注意力**（重排计算顺序把复杂度压到 O(n)）、**换范式**（Mamba/SSM 回到线性递归但保留并行训练）。

**追问链**

1. → 为什么 RNN 不能并行？（h_t 依赖 h_{t-1}，时间步之间有强制依赖）
2. → FlashAttention 凭什么"不改数学"就能加速？（它是 IO-bound 优化——注意力计算的瓶颈不在算力而在显存读写，分块把它留在片上 SRAM 里算）
3. → 那实际项目你怎么选？（短序列无脑 Attention；长文/流式才考虑线性方案；先量清楚序列长度分布再决定）

**雷区**

- ❌ 说"Attention 全面优于 RNN"——它是有前提的胜利，前提是序列不太长
- ❌ 把 FlashAttention 说成"近似算法"——它是精确等价，改的只是计算顺序和内存访问

### O-19｜为什么长上下文模型都选 RoPE？外推到底怎么做？

- **级别**：L3　**来源**：`==Q3==` 衍生（手法 B 追问原理 + C 落到工程）　**卡片**：K-12

**参考回答**

> 先回答"为什么是 RoPE"，三个原因各有一句"为什么"：
> ①**外推性强**——因为它让注意力分数只依赖**相对角度差**。位置差相同 → 角度差相同 → 分数不变。而位置差是训练时见过无数次的量，所以能迁移到更长的序列。对比之下，可学习位置编码是查表参数，训练没见过的位置根本没有参数；正弦编码虽然能算，但模型没见过的位置组合会导致分布不匹配。
> ②**编码相对位置**——分数变成只依赖 (i−j) 的函数，语义表示与绝对位置解耦，"整段往后挪"不改变内部关系。
> ③**不增加参数**——旋转矩阵是固定的三角函数矩阵，计算时施加，零新增可训练参数，不增显存、不增过拟合风险。
>
> 再说**外推怎么做**，是一条逐步递进的技术谱系：
> ```
> 位置插值 PI（把超长位置线性压回训练区间）
>   └─▶ NTK-aware 缩放（按频率分通道差异化缩放）
>         └─▶ YaRN（NTK + 注意力温度缩放，目前长文微调主流）
>               └─▶ 长上下文继续预训练（最贵，效果最好）
> ```

**追问链**

1. → 直接外推会怎样？（超出训练分布，性能会衰减，通常表现为长距离检索还行但推理崩坏）
2. → RoPE 为什么"不增加参数"很重要？（省显存、省训练成本、不引入新的过拟合面）
3. → "标称 10M 上下文"能信吗？（不能只看标称，要看有效窗口和长文综合能力——召回强不代表跨段推理强）

**雷区**

- ❌ "RoPE 编码绝对位置"
- ❌ "RoPE 引入了可训练参数"
- ❌ "有了 RoPE 就能无限外推"（必须配合缩放技术，且仍有衰减）

### O-20｜给你一个业务场景，你怎么在 CoT / ReAct / ToT / Plan&Execute 之间选？

- **级别**：L4　**来源**：`==Q12==` 衍生（手法 C 工程 + D 权衡）　**卡片**：K-23

**参考回答**

> 我按两个问题分岔：
> **第一问：需不需要外部信息或精确计算？**
> 不需要 → 再问"有没有确定答案"：有确定答案用 **CoT**（要更稳就叠 Self-Consistency 多次投票）；开放创作就直接答，最多加点 Few-Shot。
> 需要 → 进第二问。
> **第二问：步骤多不多、依赖强不强？**
> 不多、走一步看一步就行 → **ReAct**（推理和工具调用交替）。
> 多且前后依赖强 → **Plan & Execute**（先出完整计划再执行，避免反复绕路）。
> 另外两个可插拔模块：解空间大、需要试错回溯（规划/博弈/创意搜索）→ 换 **ToT**，或者更现实地做成"浅 ToT"只展开 2~3 条分支；输出质量比成本重要 → 在 ReAct 之后叠一层 **Reflection**。
>
> 举个具体例子：**"帮我把这个仓库的日志采集改成结构化输出"** —— 需要读代码（外部信息）+ 多步改动且互相依赖 → 我会用 **Plan & Execute** 打底（先扫出要改哪些文件、定顺序），每步工具调用走 ReAct 循环，最后加一层 Reflection 做自检（编译过没过、测试有没有挂）。不需要 ToT，因为解法空间不大。
>
> 边界一句：**流程可枚举的任务压根不该上 Agent**，直接用工作流引擎，比任何思维框架都便宜可靠。

**追问链**

1. → ReAct 的失败模式有哪些？（工具选错、陷入循环、误读观察、Token 爆炸）
2. → ToT 的成本怎么控？（限制分支数和深度，做浅 ToT；或者用启发式打分提前剪枝）
3. → 怎么知道选对了？（建评估集，比任务成功率 / 平均成本 / P95 延迟，别靠感觉）

**雷区**

- ❌ "越复杂效果越好"——复杂框架在简单任务上只增加成本和新的失败模式

### O-21｜位置编码到底解决了什么问题？去掉会怎样？

- **级别**：L3　**来源**：你在记录区写下的疑问　**卡片**：K-12

**参考回答**

> 解决的是"**Self-Attention 天生不知道顺序**"这个问题。
>
> 精确一点说：Self-Attention 是**置换等变（permutation equivariant）**的。看输出公式 `out_i = Σ_j softmax(q_i·k_j/√d_k)·v_j`——注意是**对 j 求和**。同一个词在不同位置，它的 embedding 完全相同，所以 q、k、v 都相同。于是去掉位置编码后，"猫追狗"和"狗追猫"里"猫"的输出都是同一组加权和——**加法可交换，求和与顺序无关**，两个向量一模一样。
>
> 所以：**去掉位置编码，模型分不出谁是主语谁是宾语。** 反过来，这也解释了为什么早期工作能用"打乱词序性能不降"来判定模型有没有用上位置信息。
>
> 一个需要澄清的常见误解：多头注意力确实学到了主谓宾关系，但那个能力来自**位置编码 + 注意力的联合作用**，不是纯注意力的能力。头学到的"关注主语"，本质是"关注某个相对位置上的词"。
>
> 哪部分真的不需要位置？**语义/指代关联**不需要（"it" 指代 "cat" 靠语义相似度就能匹配）；**语法角色、顺序敏感任务**（算术、代码）必须靠位置。

**追问链**

1. → 那你怎么向面试官证明这一点？（现场推上面那个"求和与顺序无关"的式子，或者提"打乱词序"实验）
2. → 位置编码有哪几类？为什么最后收敛到 RoPE？（见 O-19）

**雷区**

- ❌ 说"注意力天然能理解语法"——语法角色是位置信息带来的

### O-22｜128K 窗口该怎么分配？哪些内容能命中缓存？

- **级别**：L4　**来源**：你的错题 + `==` 相关知识点　**卡片**：K-07, K-09

**参考回答**

> 分三段说。
> **固定层（2~8%）**：System Prompt、工具 Schema、Skill 触发词列表——整个会话内**逐字节不变**，放 Prompt 最前面，缓存 100% 命中。
> **动态层（20~55%）**：记忆召回片段、对话历史、工具返回结果——**每轮都变**，缓存不了，只能靠压缩和按需召回来控制体量。
> **输出预留（30~50%）**：必须留，不留会被截断。
>
> 缓存的关键机制是：**命中条件是前缀完全相同，一字之差全部失效**。所以设计三原则：
> ①固定内容放最前；②动态内容放最后；③把 System Prompt 和工具定义**合并成同一条 system 消息**，增加前缀连续性（也因为 OpenAI 要求至少 5 条消息才触发缓存，合并后更容易达标）。
>
> 效果：固定 2K + 半固定 2K + 10 轮对话的规模，第 5 轮命中率约 50%，第 10 轮约 70%。
>
> ⚠️ 一个必须说清的口径：教程里"缓存折扣"有两个说法——**单价口径约 50%**，**输入成本降幅口径约 90%**（例：$5/M → $0.5/M）。答题时先确认问的是哪个，别混着说。

**追问链**

1. → 对话历史涨到占 40% 了怎么办？（先摘要压缩旧轮次，再考虑向量召回按需注入）
2. → 记忆召回为什么缓存不了？（按需检索，每轮召回的片段不同，插在中间会把后面所有内容的前缀打断）
3. → 缓存对延迟有影响吗？（有，命中部分省掉 KV 计算，首 Token 延迟明显下降）

**雷区**

- ❌ 把用户输入放最前面（后面所有固定内容的前缀都被污染）
- ❌ 说"缓存命中率能做到 100%"（只有固定前缀能保证）

### O-24｜意图识别要不要单独拆一个 LLM 子任务？

- **级别**：L4　**来源**：你的疑问　**条目**：11

**参考回答**

> 先纠正一个前提：**意图识别是个"动作"不是"模块"**。三种方法里，"语义理解"那一层的实现本来就是 LLM。所以真正的问题是：**要不要把它拆成一次独立的 LLM 调用**？
>
> 五个权衡：
> - **延迟**：拆开多一次往返（+300ms~1s）；融合进主调用没额外延迟
> - **成本**：拆开多一次调用（但 prompt 小、可缓存）；融合让主 prompt 变大
> - **可控性**：拆开容易强约束（枚举 / JSON Schema）；融合混在生成里难约束
> - **可观测**：拆开能单独记录意图、看分布、做回归；融合埋在输出里难追踪
> - **可评测**：拆开能算准确率、混淆矩阵（意图分类是有标签的！）；融合几乎没法单独评测
>
> 我的建议是**分阶段**：
> 1. **验证期**——拆成独立子任务（甚至先上小模型）。你真需要的是"可观测"，不是省那 300ms。
> 2. **稳定期**——逐步融进主调用（用结构化输出约束），省一次往返换延迟。
> 3. **成熟期**——高频意图下沉成规则（关键词/缓存），热点路径不该每次过 LLM。
>
> **三个必须注意的点**：①**错误放大**——意图识别错了后面全错，所以要有兜底（低置信度就反问用户，或走通用路径）；②**要建评测集**——这是少数能用传统 ML 指标衡量的 LLM 环节；③**主流替代方案**——Function Calling 其实已经吞掉了一部分意图识别（让模型直接决定调哪个工具 = 意图识别 + 工具选择合并成一步），代价是中间意图不可观测。

**追问链**

1. → 意图识别错了怎么兜底？（低置信度反问用户，而不是硬猜）
2. → 你怎么知道意图识别准不准？（建带标签的评测集，看混淆矩阵，别靠感觉）
3. → 那为什么又说 Function Calling 已经吞掉了它？（模型直接选工具确实等价，但损失了可观测性——这正是拆与不拆的取舍核心）

**雷区**

- ❌ 说"意图识别只能靠关键词匹配"
- ❌ 一味追求"融合省延迟"，忽略了验证期最需要的是可观测和可评测

### O-25｜Agent 怎么安全地执行操作？

- **级别**：L4　**来源**：ch02 §2.5b / 八股 Q9　**条目**：12

**参考回答**

> 按**可逆性**分级，而不是按危险等级：**可逆操作**（读文件、搜代码、跑测试、建临时文件）自由执行；**不可逆操作**（删文件、`git push`、发邮件、改配置）需用户确认；**危险操作**（`rm -rf /`、`git push --force`）始终确认且不可跳过。
>
> 为什么可逆性更实用：**"能不能撤销"比"危不危险"更能决定该不该拦**。发邮件按传统分级是"安全的"，但发出去收不回来，照样要拦；改文件是"中危"的，但有 Git 可回滚，反而可以放行。
>
> 还有一条更重要的原则：**单次授权 ≠ 全局授权**。用户批准"删除 dist/"，不等于批准"删除任意目录"，每次不可逆操作都要独立确认——这是为了防止**授权蔓延**。实现上要注意：每次重新请求确认、确认信息写**具体对象**（"删除 `dist/build.js`"而不是"删除文件"）、危险操作不提供"不再提示"、`deny` 对该次请求**粘性生效**（不能重试一下就变 allow）。

**追问链**

1. → 确认框应该怎么写？（必须含具体操作对象和类型，否则用户没法做有效判断）
2. → 权限判定为什么用三态 `allow/deny/ask` 而不是布尔？（因为"系统也不该替用户做决定"；而且 deny 要粘性）
3. → 那"会做"和"可以做"的区别是什么？（模型理解意图 ≠ 获得授权，也不等于持续授权）

**雷区**

- ❌ 只答"按低危/中危/高危分级"
- ❌ 认为"安全操作可以直接放行"

### O-26｜一个需求该用 Agent 还是传统程序？怎么判断？

- **级别**：L4　**来源**：ch03 §3.11 / 八股 Q6　**条目**：16

**参考回答**

> 一条判据贯穿：**确定性任务不需要决策，而决策才是 Agent 的核心价值**。
>
> **传统程序完胜**：CRUD、数学计算、格式转换（CSV→JSON）、定时批处理、高并发低延迟 API。给这些加 Agent 就像给计算器装个大脑——费钱还更慢。
> **Agent 完胜**：自然语言交互、多步骤编排、灵活错误处理、跨领域问答、长尾场景。共同点是**需要临场决策**。
>
> 落地就用**混合架构**：对每个函数问一句"**它的输出是否唯一确定**"——是就写确定性代码，不是才交给 LLM。也就是 **LLM 负责判断和编排，代码负责执行和保证**。
>
> 就算该用 Agent，也要盯 **`QPS × 单次成本` vs 预算**。具体锚点（查天气）：直接调 API 成本 0、延迟 0.1s、准确率 100%；Agent 是 $0.0001/次、1.5s、95%。每天 10 次可以接受，一万次要考虑，**一百万次必须退回传统程序**。

**追问链**

1. → 混合架构怎么切分？（按"输出是否唯一确定"）
2. → Agent 的单次成本怎么估才准？（要按 token 递增算，多轮任务远高于"一轮问答"）
3. → 准确率 95% 比 100% 差，为什么还值得？（低频场景换灵活性和长尾覆盖；高频场景就不值）

**雷区**

- ❌ 认为"Agent 更先进，能用就用"

### O-27｜Agent 循环什么时候停？怎么防止死循环？

- **级别**：L3　**来源**：ch03 八股 Q3　**条目**：13

**参考回答**

> **主出口是 AI 自己不再请求 `tool_calls`**——它认为信息够了，就返回最终回答，循环结束。但光靠这个不安全，模型可能反复调工具不回头，所以要三层保护：**AI 自主停**（主出口）+ **`max_loops` 上限**（保险丝）+ **超时 / token 预算**（成本熔断）。
>
> 另外要说清**两层循环**：外层 `while True` 是多轮对话（等用户输入，用户说 quit 退出），内层 `while True` 才是单个任务的 Agent 循环。问"循环什么时候停"问的是内层。

**追问链**

1. → 怎么判断 Agent 陷入了循环？（重复动作检测——同样工具、同样参数反复调用）
2. → 超出 `max_loops` 了该怎么收场？（优雅降级，把已拿到的信息和失败原因告诉用户，而不是静默丢弃）

**雷区**

- ❌ 说"循环执行固定次数后停止"
- ❌ 把"用户说 quit"当成 Agent 循环的终止条件

### O-28｜什么是 token 递增？Agent 成本该怎么估？

- **级别**：L4　**来源**：ch03 八股 Q7　**条目**：15

**参考回答**

> 因为**每一轮循环都要把整个历史重新发一遍**，所以 `prompt_tokens` 是逐轮累积的：第 1 轮 200，第 2 轮 600，第 3 轮 1000……**总成本接近轮数的平方级**，不是"单轮 × 轮数"。
>
> 对策五条：`max_loops` + token 预算上限；上下文裁剪（**裁剪时始终保留 system 消息**）；过长的工具结果先截断或摘要再回填；固定前缀（system + 工具 Schema）放最前吃 Prompt Cache；最后是**可观测**——记录每轮 prompt/completion token，把曲线画出来才能发现异常。

**追问链**

1. → 怎么发现成本异常？（调用链分析，看 `prompt_tokens` 曲线斜率；看缓存命中率）
2. → 裁剪历史时最不能丢什么？（system 消息——丢了角色和规则，行为会漂）
3. → 除了裁剪还有什么降本手段？（前缀缓存、小模型做简单环节、把高频路径下沉成规则）

**雷区**

- ❌ 说"token 递增是因为模型输出越来越长"——是**输入**的累积，与输出无关
- ❌ 按"单轮 token × 轮数"估总成本

### O-29｜工具调用失败了怎么处理？两个工具一个成功一个超时怎么重试？

- **级别**：L4　**来源**：ch03 §3.8 + 思考题 2　**条目**：14

**参考回答**

> 先分类，再选策略。
> **临时性故障**（`TimeoutError`、429、503）→ **指数退避重试**（1s→2s→4s，生产环境加 jitter 防惊群），重试耗尽后优雅降级。
> **逻辑性错误**（`TypeError` 参数错、`JSONDecodeError`、`KeyError`、`PermissionError`）→ 重试没用，**把错误信息作为观察结果告诉 AI**，让它自己决定换工具 / 改参数 / 跟用户道歉。
>
> **重试的粒度是关键**：要放在**工具层**，不要放在 Agent 循环层。
> 一个任务里天气超时、路线成功——如果把整个 `for tool_call in msg.tool_calls` 包在重试里，路线那次就白跑了。
> 正确做法是**每个 `tool_call` 独立重试**：失败的那个返回 error 结果**照常回填**，成功的那个结果已经在 `messages` 里，模型下一轮直接复用，不会重复执行。
>
> **加分点**：对有副作用的工具（下单、发邮件），给 `tool_call` 加**幂等键 / 结果缓存**——否则"重试"很容易变成"重复下单"。

**追问链**

1. → 错误信息要暴露多少给模型？（足够它决策即可，但对外降级提示不要暴露内部细节）
2. → 为什么"告诉 AI"比"直接返回固定错误文案"好？（AI 能自我修正——这是 Agent 容错的来源）
3. → 重试次数用完了怎么办？（降级返回有意义的提示，而不是崩溃）

**雷区**

- ❌ 把整个 Agent 循环包进重试
- ❌ 所有错误都重试（逻辑错误再试也一样）

### O-31｜Prompt 工程分哪三层？各自解决什么问题？

- **级别**：L3　**来源**：ch04 §4.1~4.3　**条目**：17

**参考回答**

> 三层，从"长什么样"到"怎么用"。
> **① 结构层**——Prompt 的骨架，6 个结构单元：Role（角色，决定知识边界与风格）、Directive（核心指令，必填）、Context（背景）、Exemplars（Few-shot 示例）、Format（输出格式）、Style（风格）。**Role 和 Directive 是必填，Format 强烈推荐**，其余可选。
> **② 工程方法层**——怎么引导模型思考：System Prompt / 角色扮演 / Few-shot / CoT / ToT / ReAct / APE 七种，各有适用场景。
> **③ 输出工程（Answer Engineering）**——让输出**可被程序消费**：结构化（JSON Schema 约束而非自由文本）、解析（`JSON.parse` 而非正则抠）、验证（字段完整性、类型、业务逻辑）。
>
> 关键认知：**在 Agent 系统里 LLM 的输出不是给人看的，是给下游代码消费的**——所以第三层从"可选"变成"必选"。这也是 Agent 场景和"聊天场景里写 Prompt"最大的区别。

**追问链**

1. → 为什么 Agent 里输出工程是必选？（下游代码要解析、验证、执行；自由文本没法可靠解析）
2. → `response_format` 的 `strict: True` 解决什么问题？（禁止额外字段，schema 强约束）
3. → 结构层里哪个单元最容易被忽略但收益最大？（Exemplars——用例子代替描述，最直观；Format——约束输出格式等效于给下游一个契约）

**雷区**

- ❌ 把三层说成"System / User / Context"（那是**role 的划分**，是结构层的内部概念，不是三层结构）
- ❌ 说"输出工程就是让回答更好看"

### O-32｜为什么 Agent 系统要用模板引擎写 Prompt，而不是字符串拼接？

- **级别**：L3　**来源**：ch04 八股 `==Q5==`（手法 A+B+D）　**条目**：17

**参考回答**

> 字符串拼接（f-string、`+`）有三个死穴：**① 可读性差**——变量超过 3 个就变成一行巨型字符串，没法 review；**② 无法条件渲染**——「有工具时渲染工具列表，没工具时给兜底话术」这种逻辑写不出来；**③ 无法复用**——多个 Agent 共享基础模板时无法继承。
> Jinja2 正好覆盖这三点：变量注入 `{{ var }}`、条件逻辑 `{% if %}`、循环渲染 `{% for %}`、模板继承 `{% extends %}` + `{% block %}`。
> 本质是**Prompt 与业务逻辑解耦**：模板文件管理提示词，代码只负责准备数据。
>
> **但最有价值的一层是第四点：模板边界 = 缓存边界。** 前缀缓存要求前缀逐字节相同，模板化让静态区 / 半静态区 / 动态区的分界**显式且可审计**，我才能可靠地把"每轮都在变"的分节推到 Prompt 末尾。不做模板化，这个分界藏在字符串拼接的执行路径里，缓存命中率是飘的。

**追问链**

1. → 动态渲染不也会破坏缓存吗？（会。所以模板化的价值不在"能渲染"，而在"让可缓存的部分保持逐字节稳定"；会话内不变的渲染进半静态区并 memoize）
2. → 把 Prompt 模板放进文件系统有安全风险吗？（有——模板能改 Agent 的行为定义，所以工业级 Agent 禁止 Agent 自己写模板和配置，Claude Code 就禁止写 `settings.json` 和 `.claude/skills/`）
3. → 除了 Jinja2 还有什么？（Mustache / Handlebars（JS 生态）；核心能力一致）

**雷区**

- ❌ 说模板引擎只是为了"写起来好看"
- ❌ 说"模板化之后缓存命中率就有保证"——它只让边界可见，排序才决定命中率

### O-33｜工业级 Agent 的 System Prompt 怎么做分区缓存？静态区和动态区怎么划分？

- **级别**：L4　**来源**：ch04 八股 Q8 + §4.7（手法 B+C+D）　**条目**：17

**参考回答**

> **为什么必须分区**：工业级 System Prompt 能到 4000-6000 token（工具规则 + 安全策略 + 环境信息 + 记忆文件）。每轮全量发送不仅贵，还抬高首 token 延迟。
> **怎么分三区**：**静态区**（工具使用规则、安全策略、输出格式规范）跨用户可缓存；**半静态区**（用户偏好、项目配置、记忆文件）同会话内可缓存；**动态区**（MCP 指令、临时指令、Agent 列表）每轮变化。
> **怎么实现**：用 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 标记分隔。静态区用 global scope 缓存；半静态区用 **memoize**（以配置对象为 key，`/clear` 或 `/compact` 时重置）；动态区用 `DANGEROUS_uncachedSystemPromptSection` **每轮重算**。
>
> **设计原则是一句排序律**：**按"变化频率"降序排列——最不变的塞最前面，每轮变的甩到最后面。**
>
> 函数名里带 `DANGEROUS` 不是吓人，是**把代价写在 API 名字上**：每轮重算意味着 prompt prefix 改变，提供商的 prompt cache 全部 miss，1000+ token 的 miss 就是额外的延迟和成本。

**追问链**

1. → 具体说说 MCP 指令为什么危险？（它长在 Prompt **中段**，一变后面全 miss——命中长度从"全量"掉到"前半段"，未命中部分按全价计费且要重新 prefill，TTFT 上升）
2. → 那怎么解决？（两条路：挪到 Prompt 末尾，或把"每轮重算"改成"事件驱动重算"——后者本质是把 Uncached 降级成 Memoized）
3. → 挪到末尾有副作用吗？（有。指令遵循度会下降——越靠后的约束越容易被后续动态内容冲淡，要在"缓存省钱"和"指令可靠"之间权衡）
4. → 半静态区为什么不能跨用户缓存？（它含用户偏好、项目配置这些**因人而异**的内容；跨用户缓存等于串号）

**雷区**

- ❌ 说"动态区越小越好"——应该说"**动态区的分节越靠后越好**"，规模取决于业务，位置才是设计变量
- ❌ 把 memoize 当成"永久缓存"（配置对象变了就失效，`/clear`/`/compact` 也重置）

### O-34｜上下文工程和提示词工程有什么区别？为什么说前者更重要？

- **级别**：L3　**来源**：ch05 §5.1（手法 A+D）　**条目**：18

**参考回答**

> **提示词工程管"单轮怎么说"**——关注点是单条指令怎么写，时间跨度是一轮对话，核心问题是"怎么让 LLM 理解指令"，手段是 Few-shot / CoT / 角色设定，衡量指标是指令遵循度和输出质量，失败模式是"LLM 不按指令行事"。
> **上下文工程管"这次调用带什么"**——关注点是一次调用带什么内容，时间跨度是整个会话生命周期，核心问题是"怎么让有限窗口装下关键信息"，手段是裁剪 / 压缩 / 优先级分级，衡量指标是 token 利用率和信息保留率，失败模式是"关键信息被丢掉、token 超限"。
>
> **它们不是替代关系，是互补关系**，但工程权重不一样：**Agent 跑 30 轮之后，提示词写得好不好已经不重要了，重要的是关键约束有没有被裁掉。** 所以长会话场景里上下文工程的权重更高。

**追问链**

1. → 那上下文工程和记忆系统的边界在哪？（记忆管"**存什么**"——跨会话持久化；上下文工程管"**带什么**"——窗口内装什么。检索回来的记忆还要过一遍裁剪器）
2. → 裁剪时最不能丢什么？（P0：System Prompt 和当前用户输入。丢了 System，行为会漂；丢了当前输入，本轮任务目标没了）
3. → 为什么不能简单地"从旧到新删"？（那是截断，按**位置**裁。但位置和新旧跟重要性没有相关性——工业级按**语义/优先级**裁）

**雷区**

- ❌ 把两者说成"同一个东西的新旧叫法"
- ❌ 说"上下文工程就是记忆系统"

### O-35｜Claude Code 的三级压缩链是怎么设计的？为什么要渐进式？

- **级别**：L4　**来源**：ch05 八股 `==Q4==`（手法 B+C+F）　**条目**：18

**参考回答**

> 三级，**按需升级而不是依次固定执行**。
> **① microCompact（~70% 触发）**：扫描历史里的工具返回值，把大块输出替换为**规则提取**的摘要——8000 行 `read_file` 输出压成「文件 app.py，共 800 行，主要函数 main/process/validate」。压缩率 30-40%，信息损失低，**不调 LLM**。
> **② autoCompact（~85% 触发）**：第 1 级后还不够才触发。用 **LLM** 对历史生成结构化摘要，摘要替代旧消息、**保留最近 N 轮完整对话**。压缩率 60-70%，信息损失中等，开销高（一次 LLM 调用）。
> **③ sessionMemoryCompact（手动 `/compact` 或会话结束）**：把会话精华写入持久化记忆文件，下次会话自动加载。压缩率 >90%——**严格说这不是压缩而是"转存"**，短期记忆转长期记忆。
>
> **为什么渐进**：这是一个**成本-收益阶梯**——能用规则提取的绝不调 LLM。工具返回值是半结构化的（行数、文件名、函数名、错误行），规则提取性价比远高于 LLM 摘要；而 microCompact 跑在每轮对话后，调 LLM 会直接抬高每轮的延迟。
> 设计哲学一句话：**先低成本压低价值内容，不够再中成本压中价值，最后高成本转存高价值。**

**追问链**

1. → 七、八十五这两个阈值在防什么？（给"下一轮输入 + 工具返回值"和"压缩动作自身消耗"留余量；和"有效上下文窗口"公式里减掉的 `max(maxOutputTokens, 20000)`、`AUTOCOMPACT_BUFFER 13,000` 是同一个预算方程的两端）
2. → autoCompact 有什么保护机制？（**递归守卫**：`shouldAutoCompact` 在查询来源是 `session_memory` 或 `compact` 时返回 false，防"压缩→查询→再压缩"死循环；外加 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3` 熔断）
3. → 迁移到自己的项目先做哪一级？（**先做 P2 工具返回值裁剪**——收益最大、零 LLM 成本、风险最小。LLM 摘要放最后，因为它是唯一引入新故障模式的环节，需要配降级链 AI → 规则 → 硬截断）

**雷区**

- ❌ 说"三级按固定顺序依次执行，不可跳过"（这是原题的干扰项 D）
- ❌ 说"压缩率越高越好"——压缩率与信息保留反向

### O-36｜ReAct 有哪些局限？后续的范式各自补了什么？

- **级别**：L3　**来源**：ch06 八股 Q4 + §6.11 家族演进（手法 A+D）　**条目**：19

**参考回答**

> 四个结构性局限，而后续演进基本是**一对一补漏**：
> **① token 线性膨胀**——每步 Observation 都进上下文，步数越多单次调用越贵。**ReWOO** 治它：先规划再执行（Planner → Worker → Solver），Observation **根本不回流给模型**，LLM 调用次数从"每步 1 次"降到固定 2~3 次；代价是**计划不能动态调整**。
> **② 严格串行**——独立工具也必须排队。**LLM Compiler** 治它：把计划编译成**依赖图 DAG**，识别可并行分支并发执行；依赖之间仍不可并行。
> **③ 格式解析不稳定**——正则抠 `Action:` 文本很脆。这是**协议问题不是模型能力问题**，解药是换 **Function Calling / Structured Output** 结构化协议。
> **④ 错了不知道**——一路走到黑没有质量评估。**Reflexion** 治它：执行 → 评估 → 反思 → 重试，把反馈源从"外部环境"扩展到"自己的推理过程"；代价是**反思轮次可能过多**。再往上 **LATS** 把选行动变成蒙特卡洛树搜索，能回溯。

**追问链**

1. → ReWOO 省 token 的机制到底是什么？（不是压缩上下文，而是让 Observation **不进模型的 context**——它只出现在 Worker 的局部变量和 Solver 那一次调用的输入里）
2. → ReWOO 的硬约束是什么？（计划必须**可静态解析**（Worker 用正则抠 `#E`），且步骤间**不能有数据依赖的环**）
3. → ReAct 能自然支持多 Agent 协作吗？（**不能**，它是单 Agent 模式。要 Fork 子代理或上 CrewAI / AutoGen 这类框架）
4. → 生产环境现在默认用哪个形态？（Function Calling ReAct——本质是"去掉文本解析层"）

**雷区**

- ❌ 说 ReWOO 的收益是"更聪明"（收益是省 token，代价是不可动态调整）
- ❌ 说"等模型变强了文本解析就稳定了"（是协议问题）
- ❌ 说 ReAct 天然支持多 Agent

### O-37｜生产级 Agent 主循环要加哪些稳定性保障？

- **级别**：L4　**来源**：ch06 §6.13 + ch09 §9.8（手法 C+D）　**条目**：19、22

**参考回答**

> 两套互补的清单，先说主循环六件套：
> **① 双模式**——Chat 单轮直答 / Agent 自动多轮，按场景选，避免"每句你好都跑完整循环"。
> **② Token Budget**——全局预算实时累加，超限即停。
> **③ 死循环保护**——连续 **2 轮**相同失败自动终止（阈值 2 是灵敏度与容错的平衡点）。
> **④ 截断恢复**——被 `max_tokens` 截断时注入 `continue` 续写，**限次**。
> **⑤ 指数退避**——临时错误 `2^n` 秒退避避免雪崩，**区分可重试 / 不可重试**。
> **⑥ 413 压缩**——请求过大时紧急压缩重试，作为正常压缩的兜底。
>
> 再加运行时层的五个熔断/恢复机制：**上下文溢出熔断**（`max_context_tokens = 120K`）、**死循环检测**（`max_turns = 20`、`max_tool_errors = 3`）、**压缩降级链**（AI → 规则 → 硬截断）、**Checkpoint 恢复**（状态序列化）、**心跳检测**（`idle_timeout = 10min`）。
>
> 三条设计心得：**恢复一定要限次**（否则是换个名字的死循环）；**错误一定要分类**（临时性故障重试，逻辑性错误告诉 AI）；**阈值不能太敏感**（一次失败就退出会误杀网络抖动）。

**追问链**

1. → 心跳超时应该终止任务还是暂停？（**暂停且可恢复**（`canResume: true`）——直接终止的话用户回来发现任务没了，体验比多花点钱更糟）
2. → 哪一项是"能演示"和"能交付"的分界线？（**Checkpoint 恢复**——没有状态序列化，中断一次前面全白跑）
3. → 死循环保护的阈值为什么取 2 而不是 3 或 5？（越大容错越好但发现问题越晚、烧钱越多；2 是平衡点，且要配"相同失败"的判据而不是"任意失败"）

**雷区**

- ❌ 说"截断恢复可以无限续写"
- ❌ 把"连续 2 轮相同失败"说成"连续 2 轮任意失败"

### O-38｜Agent 的记忆怎么分类？召回太多会有什么问题？

- **级别**：L4　**来源**：ch07 八股 Q12 + §7.8 治理法则（手法 B+C+D）　**条目**：20

**参考回答**

> **先说分类**。按生命周期分三层：**短期记忆**（当前对话历史，过长走 LLM 摘要压缩）、**工作记忆**（当前任务的状态与中间变量，**几乎不能压**——丢掉任务状态等于从头再来）、**长期记忆**（历史摘要与交互，向量库 + 语义检索）。
> 长期记忆内部还要再分两档：**静态的**（用户偏好、系统规则、领域事实）几乎不变，**直接注入 System Prompt**，**不该进向量库**；**动态的**（对话摘要、执行经验、行为模式）持续更新，走向量库按相关性检索。
>
> **再说召回**。不能只看相似度，用**三维综合评分**：`recall_score = 意图匹配 × w1 + 时间衰减 × w2 + 频率加权 × w3`。意图匹配是 query 与记忆的余弦相似度；时间衰减是 `e^(-λΔt)`；频率加权是 `log(1 + 成功召回次数)`——**注意是"成功"召回，被召回但没帮上忙的不该涨权重**。
>
> **召回太多比太少更危险**，三个危害：**注意力稀释**（模型关注无关内容）、**指令冲突**（"偏好简洁"和"要求详细"同时召回）、**token 浪费**（挤掉 P0/P1）。
> **四道防线**：数量上限（每次 ≤5 条，简单问题 ≤3 条）、相关性阈值（< 0.7 不召回）、冲突检测（多条矛盾取最新的）、优先级排序（核心指令 > 最近经验 > 补充信息）。
> 再加一个 **JIT 原则**：不在一开始塞满上下文，而是每一步只注入当前需要的信息。

**追问链**

1. → 工作记忆和短期记忆怎么区分？（短期是"聊了什么"，工作记忆是"任务进行到哪一步"；后者几乎不可压）
2. → 静态记忆为什么不进向量库？（它几乎不变，检索是白花钱；直接写进 System Prompt 的静态区还能命中前缀缓存）
3. → 无服务端的 CLI Agent 怎么做记忆？（纯文件系统 + LLM 驱动压缩：轮次分割、三层压缩触发 80%/60%/413、AI→规则降级、增量压缩（上次压缩水平的 80% 才再压）、Provider/Reducer、双作用域 + LRU）
4. → 它写记忆的原则是什么？（**只存无法从当前项目状态推导的上下文**——能从 `package.json` 读到的就不写。四类型：user / feedback / project / reference）

**雷区**

- ❌ 说"记忆就是把历史都存进向量库"
- ❌ 说"召回得越多越保险"
- ❌ 把"召回次数"当成 `frequency_weight` 的输入

### O-39｜Tool RAG 是什么？它到底解决什么问题？

- **级别**：L3　**来源**：ch08 §8.3 + ❓你的疑问（手法 A+E+F）　**条目**：21

**参考回答**

> 工具注册到几十上百个时，把全部工具描述塞进 Prompt 会 **token 爆炸**，而且**描述之间互相干扰、选错工具的概率反而上升**。Tool RAG 把工具描述向量化建索引，按用户意图只检索 **Top-K 个最相关工具**注入——本质是 RAG 思想在"工具"上的复用，底层用的是同一套 Embedding + 向量检索机制。
>
> **关于"核心目的"要说两层**：**直接目的是控制注入开销（省 token）**——这是定义性收益，不管检索准不准都成立；**提升选择准确率是有条件的衍生收益**——它依赖检索召回率，如果检索把该用的工具漏掉了，Tool RAG 会比全量注入**更差**。
> 所以工程上必须配兜底：关键词命中兜底、或对高置信度任务回退全量注入。

**追问链**

1. → 那这道题选"提高准确率"错了吗？（不错，但它不是"核心目的"——题目问的是设计动机。而且 A 的成立依赖"检索可靠"这个前提，B 是无条件成立）
2. → Tool RAG 引入了什么新故障点？（**检索漏召回**——原本"工具都在"变成了"工具可能没被找到"，需要有兜底路径）
3. → 工具描述怎么写才能提升召回质量？（描述要写清"什么时候该用"而不只是"这是什么"——与 `description` 决定工具被选中是同一个道理）

**雷区**

- ❌ 说 Tool RAG 是为了"增加工具数量"
- ❌ 说 Tool RAG 一定比全量注入准（漏召回时会更差）

### O-40｜什么时候该用多 Agent 而不是单 Agent？

- **级别**：L4　**来源**：ch08 八股 Q5 + §8.6 决策矩阵（手法 A+C+D）　**条目**：21

**参考回答**

> **先看单 Agent 的三个瓶颈**：**① 上下文爆炸**（任务越复杂，工具/记忆/中间结果越多，Prompt 超限）、**② 能力冲突**（一个 Agent 同时当"搜索者"和"写作者"，System Prompt 是矛盾的，角色会乱）、**③ 串行瓶颈**（所有步骤排队，独立子任务无法并行）。
>
> **决策矩阵**（满足任一即考虑多 Agent）：**步数 > 5 且存在并行子任务** / **需要多角色**（搜索者 + 写作者 + 审核者）/ **工具 > 10 个且能分组** / 上下文超出单 Prompt 容量 / 需要并行加速。反之单 Agent 更简单也更便宜。
>
> **多 Agent 买到什么**：**上下文隔离**（每个 Agent 只看自己需要的信息）、**并行执行**、**角色专精**（各自独立 System Prompt）。
> **代价**：通信开销、状态同步、结果整合——尤其要小心"**谁来综合判断**"：**综合判断必须留在有全局视角的主 Agent 手里**，子 Agent 只看到局部上下文。

**追问链**

1. → 和 Fork 子代理什么关系？（Fork 是多 Agent 的一种轻量形态：主代理 Thought 阶段判断可委派 → 子代理继承上下文、共享 prompt cache、后台执行 → 完成后通知主代理整合。它同时解决串行、**自我确认偏误**、优先级漂移）
2. → Fork 的 Prompt 有什么规则？（不偷看、不编造、**不推诿理解**、指令式而非背景介绍式）
3. → 多 Agent 的记忆怎么隔离？（按作用域分——User Scope 跨项目、Project Scope 仅当前项目，见条目 20）

**雷区**

- ❌ 说"多 Agent 更先进，能拆就拆"（它是为隔离和并行**付代价**）
- ❌ 说"委派出去就让子 Agent 自己综合判断"

### O-41｜Loop / Runtime / Sandbox 三者的关系和职责边界是什么？

- **级别**：L3　**来源**：ch09 八股 Q5（手法 A+B）　**条目**：22

**参考回答**

> **严格嵌套，不是并列**：**Sandbox 在最外层**（所有 Agent 行为最终都在某个隔离环境中执行）→ **Runtime 在中间层**（为 Loop 提供基础设施）→ **Agent Loop 在最内层**（是 Runtime 里的一个逻辑循环）。
> 分工：**Agent Loop 决定"做什么"**（LLM 推理决定下一步行动）；**Runtime 决定"怎么做"**（把逻辑语义转成可执行计算）；**Sandbox 决定"在哪里做、在什么约束下做"**。
>
> **边界问题一句话对应一层**：
> ① "该做什么决策？" → **Agent Loop**
> ② "工具参数合法吗？" → **Runtime 工具注册层**（类型、值域、必填校验）
> ③ "有权限调用吗？" → **Runtime 权限控制层**（角色权限矩阵 + 审批）
> ④ "代码在哪执行？" → **Sandbox**（隔离环境 + 资源限制）
> ⑤ "历史太长怎么办？" → **Runtime 记忆管理层**（窗口压缩 + 摘要替代）
>
> Runtime 自己是五层：LLM 管理 / 工具注册 / 记忆管理 / 执行调度 / 可观测。

**追问链**

1. → Runtime 包括 LLM 推理计算吗？（**不包括**。推理由模型服务端完成，Runtime 只调 API 并处理响应——这是最常见的"不包括"考点）
2. → Agent Loop 是五步还是六步？（教程给的是六步：感知 → 推理 → 规划 → 执行 → 观察 → **评估**。多出的"评估"把"是否结束"从隐式的 `tool_calls` 判断变成显式步骤，**有了评估步才挂得上质量检查**）
3. → 为什么要分这么细？（因为可替换——换 Runtime 不动 Loop，换 Sandbox 不动 Runtime，符合工程上的关注点分离）

**雷区**

- ❌ 说三层是并列的
- ❌ 说 Runtime 负责执行 LLM 推理

### O-42｜Docker 和 Firecracker 做沙箱有什么区别？你怎么选？

- **级别**：L3　**来源**：ch09 八股 Q3 + §9.6（手法 A+D+F）　**条目**：22

**参考回答**

> **核心区别是隔离原理**：**Docker 容器共享宿主机内核**——隔离在进程/文件系统层面，所以**内核漏洞可以逃逸**；**Firecracker 微虚拟机每个沙箱运行独立内核**——内核级隔离，逃逸难度极高。
> **代价对比**：Docker 启动秒级、资源开销小；Firecracker 启动约 **125ms**、资源开销更大（每实例要跑一个内核）。
>
> **选型原则**：**金融 / 医疗这类高安全场景选 Firecracker**；**一般 Web 场景 Docker 够用**；**不想自建就选 E2B / Modal 这类云沙箱**。
> 另外还有两个方向：**进程级**（`subprocess` + `ulimit`/`cgroups`，毫秒级但隔离最弱，只适合简单验证）和 **WASM**（Wasmtime/Wasmer，毫秒级、无系统调用，适合轻量计算）。
>
> **但选完技术还不够——单层沙箱一定不够**，工业级是三层纵深：应用级命令静态分析（23+ 验证器 + AST）→ 权限决策引擎（三步决策 → auto-allow / regular / disabled）→ OS 级隔离（macOS Seatbelt、Linux Bubblewrap + seccomp、Windows PowerShell 包装）。

**追问链**

1. → 单层为什么不够？（静态分析绕不过混淆；权限引擎挡不住 OS 漏洞；OS 隔离挡不住"合法命令的恶意效果"）
2. → 举个"合法命令的恶意效果"的例子？（**裸 Git 仓库的 `core.fsmonitor` 劫持**：攻击者建一个裸仓库并把 `core.fsmonitor` 指向恶意脚本，Agent 执行 `git status` 时 Git 自动跑那个脚本——检查的是无害命令，恶意行为发生在工具内部。防御是进沙箱前 `scrubBareGitRepoFiles()` 清扫）
3. → 沙箱的网络隔离是断网吗？（不是。**HTTP/SOCKS 代理 + 域名白名单**——Agent 能 `npm install`（registry 在白名单），不能 `curl evil.com`。断网最安全但会废掉大部分能力）
4. → 文件系统怎么控？（Bubblewrap 挂载命名空间三级：`--bind` 可写（项目目录、/tmp）、`--ro-bind` 只读（系统库、/usr/bin）、`--dev-null` 完全屏蔽（敏感路径））

**雷区**

- ❌ 说 Docker 和 Firecracker "都是容器，差不多"
- ❌ 说沙箱就是禁用网络
- ❌ 把 `excludedCommands` 当安全边界（原文自己写着"用户便利功能，非安全边界"）

### O-43｜什么是 Harness Engineering？和 Prompt / Context Engineering 什么关系？

- **级别**：L3　**来源**：ch10 八股 Q1（手法 A+B+D）　**条目**：23

**雷区**

- ❌ 说"Harness 取代了 Prompt 工程"（是嵌套包含）
- ❌ 只举"换个更强的模型"当优化手段（答偏到模型侧）

### O-45｜Hooks 有哪几类？为什么说它是 Harness 的安全网？

- **级别**：L3　**来源**：ch10 §10.5（手法 A+B+C）　**条目**：23

**参考回答**

> 四类：**pre-hook**（执行前：参数校验、权限检查、**成本预估**）、**post-hook**（执行后：结果校验、格式检查、日志记录）、**error-hook**（异常时：重试、降级、告警）、**approval-hook**（高危操作：暂停执行，等人工确认）。
> 说它是安全网，是因为**它把"安全"从模型自律变成了系统强制**——模型可能一时糊涂要删库，但 approval-hook 不依赖它清醒，照样在执行前拦下来。
> 这是 Harness 思路的精髓：**不信任单次决策，用结构性拦截兜底**。

**追问链**

1. → approval-hook 什么时候该挂？（按**可逆性**判据：不可逆操作必须审批——和条目 12 是同一套判据；另外"单次授权 ≠ 全局授权"）
2. → error-hook 里重试和降级怎么选？（**临时性故障**重试，**逻辑性错误**把错误信息回喂给 LLM 让它改参数——见条目 14）
3. → 有了 Hooks 还需要沙箱吗？（需要。Hooks 是**应用级拦截**，只能拦住已知规则；沙箱是**执行级兜底**，能限制未知后果。**两层都要**）

**雷区**

- ❌ 把 Hooks 说成"日志钩子"（四类里三类都在改变执行流程，不只是记录）
- ❌ 说"有了 Hooks 就不用沙箱了"

### O-46｜让你从零设计一个 Agent 系统，安全与稳定性上你怎么落？

- **级别**：L4　**来源**：ch10 最佳实践清单（手法 C+D）　**条目**：23

**参考回答**

> 按八条落地：**最小权限**（工具走白名单，只列必需工具）→ **最大轮次限制**（`max-turns` 10~20，防死循环烧 Token）→ **沙箱隔离**（代码执行进沙箱，资源与网络都受限）→ **知识注入**（项目规则写进 AGENTS.md）→ **上下文管理**（滑动窗口 + 摘要压缩 + 关键信息保留）→ **可观测性**（每步的输入、输出、耗时、Token 全记）→ **自验证**（工具结果在沙箱里验证合理性）→ **渐进授权**（简单任务严约束、复杂任务宽约束）。
> 最后一条看起来和"最小权限"矛盾，其实不冲突：**最小权限是默认姿态，渐进授权是随可信度动态放宽的规则**。

**追问链**

1. → `max-turns` 设多大？为什么不能设得很大？（一般 **10~20**；太大会让死循环变成"烧钱黑洞"，配合连续工具错误上限一起用）
2. → 可观测到底记什么？（每步的**输入 / 输出 / 耗时 / Token**——没有这四样，多步调用出错时定位不到是哪一步坏的）
3. → 渐进授权怎么判断"可以给更多权限"？（按**任务阶段 + 操作可逆性 + 历史行为**综合判定，而不是一次性放开）
4. → 这些和沙箱三层纵深防御是什么关系？（八条是**设计原则**，三层纵深是**具体落地**：应用级静态分析 → 权限决策引擎 → OS 级隔离，见条目 22）

**雷区**

- ❌ 只说"最小权限"，漏了"渐进授权"（会被追问过度约束导致任务完不成）
- ❌ 把八条讲成清单背诵，说不出每条在防什么

### O-47｜向量检索为什么必须配 BM25？混合检索怎么做？

- **级别**：L3　**来源**：ch11 §11.2（手法 A+B+E）　**条目**：24

**参考回答**

> 因为**纯向量检索的关键词匹配能力差**：搜 "GPT-4o" 可能召回 "GPT-4"——语义很相似，但根本不是同一个模型。反过来 BM25 做**精确关键词匹配**，正好补这个洞。
> 工程上用 `EnsembleRetriever` 之类的加权融合，两边各召回 Top-10 再融合，经验权重 **BM25 0.4 / 向量 0.6**。
> 顺带说下三种度量的选型：**余弦**（只看方向，文本最常用，值域 **[-1,1]**）、**欧氏**（看绝对距离，图像）、**内积**（考虑模长，**归一化后等价于余弦**）。

**追问链**

1. → 为什么向量检索会漏掉关键词？（它压的是**语义**，把 "4o" 和 "4" 视为近义；版本号的差异恰恰在字符层）
2. → 权重 0.4/0.6 是硬规则吗？（不是，是**经验起点**；专有名词/型号多的语料可以上调 BM25，纯自然语言问答可以上调向量）
3. → 只做混合检索够吗？（不够，还有 **Query 改写 / HyDE / 先召回 Top-20 再 Rerank**，见 O-49）

**雷区**

- ❌ 说"余弦相似度值域 [0,1]"（你错过这道题：方向类指标可以为负）
- ❌ 说"向量检索能覆盖关键词场景"

### O-48｜HyDE 是什么？什么时候有效、什么时候会翻车？

- **级别**：L3　**来源**：ch11 §11.3（手法 A+B+D）　**条目**：24

**参考回答**

> HyDE 解决的是"**用户问题太短，向量化后语义信息不足**"。做法是：先让 LLM 针对问题生成一个**假回答**，用假回答的向量去检索（它比短问题语义丰富得多），再拿检索结果生成真回答。
> 流程：问题"RAG 怎么做？" → LLM 生成假回答"RAG 是检索增强生成技术……" → 用假回答检索 → 用检索结果生成真回答。
> **有效场景**：短查询、口语化提问、术语不规范的提问。**翻车场景**：假回答本身 hallucinate 了，方向一偏，检索到的就是错的邻域——所以它适合召回阶段，最终答案仍要基于真实检索结果。

**追问链**

1. → HyDE 和 Query 改写有什么区别？（Query 改写生成的是**多个查询角度**；HyDE 生成的是**一段"像是答案"的文本**，用它去贴近文档的向量分布）
2. → 代价是什么？（**多一次 LLM 调用 + 一次额外的向量化**，延迟和成本都上升；所以它常和"简单问题不检索"的 Agentic RAG 路由配合使用）
3. → 怎么降低翻车概率？（假回答只用于**召回**，生成阶段严格基于真实文档；必要时多生成几个假回答做多路召回）

**雷区**

- ❌ 说"HyDE 用假回答当答案"（假回答只用于检索，**不进最终答案**，否则就是拿幻觉当事实）
- ❌ 只讲原理不讲失效边界（L2，不到 L3）

### O-49｜线上 RAG 检索不到相关文档，你怎么排查？

- **级别**：L4　**来源**：ch11 八股 Q5（手法 C+D）　**条目**：24

**参考回答**

> 五步排查，按"先便宜后贵、先检索后生成"的顺序：
> ① **Query 改写**——用 LLM 改写用户问题，生成多个角度并行检索（用户问法和文档写法不一致是最常见原因）；
> ② **HyDE**——短问题语义不足时用假回答检索；
> ③ **调 chunk_size**——太大不精确、太小语义不完整，经验区间 **512~1024**；代码库要改成**按 AST 符号切**；
> ④ **加混合检索**——补 BM25 关键词通道；
> ⑤ **加大召回量 + Reranker**——先召回 Top-20，再精选 Top-5。
> 关键顺序：**先确认是检索侧没召回（Recall 低），再看生成**。检索没召回，换模型、改 Prompt 都救不回来。

**追问链**

1. → 怎么判断是检索的问题还是生成的问题？（先看**检索指标**：召回率、精确率、MRR；召回里有正确答案但答案没用上 → 生成侧问题；召回里根本没有 → 检索侧问题）
2. → 为什么"先多召回再精选"是标准打法？（召回要**便宜且全**，精选要**贵但准**——把 Cross-Encoder 这类重模型只用在 20 个候选上）
3. → 代码库的检索为什么要单独处理？（代码的语义单位是**符号与调用关系**，按字符切会把函数切两半；用 tree-sitter 按 AST 符号切，还能带上 `symbol_name` / `line_start` / `signature` 等元数据，让 Agent 能精确定位跳转）
4. → 什么时候应该放弃优化检索，改用别的方案？（**全局性/跨文档问题**——"整个系统有哪些模块"这类，向量检索天然答不了，要上 GraphRAG，见 O-53）

**雷区**

- ❌ 上来就说"换个更强的模型"（顺序错了，先查检索侧）
- ❌ 只给一二招，给不出可排查的**顺序**

### O-50｜RAG 系统怎么评估？指标怎么选？

- **级别**：L3　**来源**：ch11 八股 Q4（手法 A+C）　**条目**：24

**参考回答**

> 分两段评估。**检索质量**：**召回率**（相关文档有没有被检索到）、**精确率**（检索结果里有多少相关）、**MRR**（第一个相关结果排第几）。**生成质量**：**忠实度**（回答是否基于检索内容，有没有幻觉）、**相关性**（是否切题）、**完整性**（是否覆盖了问题的所有方面）。
> 自动化可以用 **Ragas** 框架（用 LLM 给 LLM 的答案打分）。
> 我的排障顺序是**先检索后生成**：召回率低说明"漏了"，这时候换模型改 Prompt 都救不回来。

**追问链**

1. → 忠实度低说明什么？（要么检索给了噪音，要么 Prompt 没有约束"只基于检索内容作答"，要么模型在补自己的知识）
2. → 精确率低但召回率高，要改什么？（召回太宽 → 收紧 Top-K 或上 **Reranker**；这是"先多召回再精选"里第二阶段没做的原因）
3. → 指标好但用户还是不满意怎么办？（加**用户反馈闭环**——生产级 RAG 是五段闭环，最后一环就是"持续评估优化"，不是搭完就完）

**雷区**

- ❌ 只说"看准确率"（RAG 至少要分检索和生成两段，各有各的指标）
- ❌ 把忠实度当成检索指标（它是**生成**指标，检测幻觉）

### O-51｜检索出的内容互相冲突，Agent 该怎么取舍？

- **级别**：L4　**来源**：ch11 八股 `==Q6==`（手法 A+C+D）　**条目**：24 🔆

**参考回答**

> 企业知识库版本多、来源杂，**冲突是常态**，我不会只答"取最新的"，而是三重保障：
> **① 元数据加权排序**——按发布时间 + 权威等级双重加权，优先采信**高权威 + 最新**；
> **② 多智能体辩论**——让不同 Agent 分别代表冲突的文档互相论证，梳理矛盾点，筛出逻辑最通顺的答案，用"辩论"替代"单点裁决"；
> **③ 强制溯源**——要求答案必须附检索来源，把最终裁决权交回人类。
> 三者是**组合**不是三选一：加权解决大多数，辩论处理难分歧，溯源保证可审计。

**追问链**

1. → 两篇文档权威等级相同、时间也相同，怎么选？（**不该由系统硬选**——走强制溯源，把矛盾显式呈现给用户。这正是"不硬撑取最新"的价值）
2. → 多 Agent 辩论成本很高，值得吗？（只在**高价值、低频率**的决策上用；日常问答靠元数据加权就够了）
3. → 加权里的"权威等级"怎么定？（按来源类型分档：官方文档 > 内部规范 > 个人笔记；再叠加发布时间衰减）
4. → 和"引用来源"是什么关系？（溯源是元数据的外化——**没有元数据加权就没有可靠溯源**）

**雷区**

- ❌ 只说"取最新的"（这是最常见也最减分的答法）
- ❌ 把三种策略说成三选一

### O-52｜新闻、股价这类实时更新的知识，RAG 怎么适配？

- **级别**：L4　**来源**：ch11 八股 `==Q8==`（手法 A+C+D）　**条目**：24 🔆

**参考回答**

> 三个机制覆盖全链路——**判断要不要实时 → 怎么更新 → 怎么保证不过期**：
> **① 动态路由 Agent**：先判断问题是否需要实时数据。需要 → 优先调搜索/实时 API，**不查静态向量库**；不需要 → 正常走向量库。类似"先思考再行动"的智能分发。
> **② 流式增量更新**：用消息队列监听知识库变动，**增量新增/更新向量**，不全量重构。
> **③ 缓存失效机制**：高频问题设缓存时效，元数据一更新立刻清空旧缓存。
> 三个分别对应"路由 / 增量 / 失效"，只讲增量更新是最常见的漏项。

**追问链**

1. → 只做增量更新够不够？（不够。**索引更新了但答案还是缓存里的旧内容**，是最典型的 bug——所以必须有缓存失效）
2. → 动态路由判断错了怎么办？（保守策略：**不确定就两个源都查**，再做结果融合；或者让 Agent 在答案里标注数据时间戳，让用户能判断）
3. → 和 Agentic RAG 是什么关系？（动态路由就是它的延伸——从"要不要检索"升级到"**检索哪个源**"）
4. → 缓存时效设多长？（按数据变化频率定：股价秒级、新闻分钟级、文档天级；**用元数据里的更新时间驱动失效**，而不是固定 TTL 一刀切）

**雷区**

- ❌ 只答"加个实时接口"或"做增量更新"（缺了路由与失效，不成链路）
- ❌ 说"把实时数据都写进向量库"（实时数据往往不需要长期索引，直接查 API 更准更省事）

### O-53｜GraphRAG 和向量 RAG 有什么区别？什么时候该上 GraphRAG？

- **级别**：L3　**来源**：ch11 八股 Q10（手法 A+D+E）　**条目**：24

**参考回答**

> **核心区别在检索方式**：向量 RAG 做语义相似度搜索，找的是"**像**"的文本块；GraphRAG 先从文档抽**实体和关系**建图，检索时做**图遍历**，找的是"**有关联**"的信息。
> 它补的是向量 RAG 的死穴：**只能检索局部相似片段，答不了全局性问题**（比如"整个系统架构包含哪些模块？"）。
> **适合四类场景**：多跳推理（A 公司 CEO 毕业于哪所大学）、关系分析（这个故障影响了哪些下游服务）、全局摘要、因果追溯。
> **代价也不小**：构建成本高（LLM 抽实体关系烧大量 Token）、维护复杂（文档更新要同步改图谱）、**实体歧义**（"苹果"是公司还是水果）、简单问答杀鸡用牛刀。
> 所以最佳实践是**混合**：向量 RAG 做 90% 日常问答，GraphRAG 做 10% 复杂关联分析——**不是替代，是互补**。

**追问链**

1. → 实体歧义怎么处理？（**实体消歧 / Entity Disambiguation**：结合上下文与类型约束判断"苹果"指公司还是水果，必要时在图谱里保留多类型节点）
2. → 文档频繁更新的场景能上吗？（慎上。文档一改就要同步图谱，维护成本远高于加向量；**先做向量 RAG，只对稳定的核心实体建图**）
3. → 一句话怎么向非技术同事解释？（向量 RAG 找"长得像"的，GraphRAG 找"有关系的"）

**雷区**

- ❌ 说"GraphRAG 是下一代 RAG，会替代向量 RAG"（互补关系，且它成本高得多）
- ❌ 只讲优点不提实体歧义与维护成本

### O-54｜HNSW 的原理是什么？为什么不直接线性扫描？

- **级别**：L3　**来源**：ch11 八股 `==Q13==`（手法 A+B+D）　**条目**：24 🔆

**参考回答**

> HNSW（分层可导航小世界图）构建**多层图**：**上层稀疏（高速公路）、下层稠密（城市道路）**，搜索时从上层快速定位区域，再逐层下降到 Layer 0 精细搜索。
> 五步：顶层入口 → **贪心搜索**（邻居更近就移过去）→ 本层没有更近的就下降一层 → 底层用**优先级队列**维护 Top-K → 返回 Top-K。
> 为什么不线性扫描：10 万向量线性要 **10 万次**距离计算（≈200ms），HNSW 约 **17 次**（≈2ms），**快约 100 倍**。
> 代价是**空间换时间**——每个节点要额外存邻居指针。

**追问链**

1. → 为什么上层要稀疏？（稀疏才能**一次跨越大距离**，先粗定位再精修，这是多层图相对单层图的核心收益）
2. → 是精确搜索吗？（**近似**最近邻 ANN——牺牲一点点召回率换两个数量级的速度，工程上完全值得）
3. → 为什么不用外部向量数据库也能做？（原文实现是**纯手写 HNSW + bincode 序列化到本地文件**；小规模场景不需要上一整套向量库）
4. → 余弦距离怎么算？（**余弦距离 = 1 - 余弦相似度**，把"越大越相似"转成"越小越近"才能用最近邻检索）

**雷区**

- ❌ 说 HNSW 没有代价（**额外内存存邻居指针**）
- ❌ 说它是精确搜索（是 ANN，近似）

### O-55｜Agentic RAG 和 Deep Research 有什么区别？

- **级别**：L3　**来源**：ch11 八股 Q17（手法 A+D）　**条目**：24

**参考回答**

> **Agentic RAG**：检索 → 反思 → 再检索，关注"信息**够不够**"，输出简短回答，通常 ≤ 3 轮，是**答题思维**。
> **Deep Research**：检索 → 分析 → **追问** → 再检索 → 综合，关注"信息**全不全**"，输出综合报告，通常 3~10 轮，是**调研思维**。
> 典型场景对比：问"限流策略和降级策略分别是什么？"用 Agentic RAG；问"分析所有模块的技术选型和设计权衡"用 Deep Research。
> 一句话：**前者优化宽度（够不够答），后者优化深度（有没有漏）**，互补不替代。

**追问链**

1. → 为什么 Deep Research 要"追问"这一步？（单轮只能覆盖已知维度；**追问是把知识边界往外推**——分析完发现还有没覆盖的方面，再定向检索）
2. → 轮次越多越好吗？（不是。轮次和成本线性相关，要有**收敛判据**：新检索带来的增量信息低于阈值就停）
3. → 和普通 RAG（每次都检索）相比，Agentic RAG 的核心增益是什么？（**智能路由**——"你好"这类问题不检索，省 Token 降延迟；复杂问题可多轮、可换关键词、可验证相关性、可标注来源）

**雷区**

- ❌ 把两者说成替代关系
- ❌ 说"轮次越多越全面"（要讲收敛与成本）

### O-56｜LLM-Wiki 是什么？和 RAG 怎么配合？

- **级别**：L3　**来源**：ch12 §12.1（手法 A+B+D）　**条目**：25

**参考回答**

> LLM-Wiki 是 Karpathy 提出的一种知识组织方式：**用文件系统代替向量检索，用自然语言代替微调**，让知识**编译一次、持续维护**，而不是每次查询重新推导。
> 三层架构：**Raw Sources**（`raw/`，原始资料，**不可变**）→ **Wiki**（LLM 提取整理、互相链接的知识页）→ **Schema**（结构规则，元知识）；靠 **Ingest / Query / Lint** 三个操作运转。
> 和 RAG 的分工我记一句话：**LLM-Wiki 适合"规则少但重要"的知识，RAG 适合"量大但需要筛选"的知识**。
> 为什么这么分：项目约定、安全红线这类内容交给 RAG，每次检索都可能漏、召回顺序一变答案就变，它们需要的是**稳定注入**而不是相似度排序。工程上一般组合用：**AGENTS.md 放核心规则 + RAG 放海量文档 + LLM-Wiki 放整理过的知识体系**。

**追问链**

1. → "编译一次"具体省了什么？（Query 时**读已编译好的页面，不再重读原始文件**——查询成本与资料总量**解耦**）
2. → 为什么 `raw/` 要不可变？（保留**可追溯的证据链**：Wiki 错了能回到源头重编；而且 Wiki 是**增量更新**而非重建，重建会丢人工修订、成本随资料量爆炸）
3. → Schema 和 purpose.md 有什么区别？（Schema 是**结构规则**，purpose 是**方向意图**——Karpathy 的原始设计只有前者，工业级实现补了 purpose，让 Agent 在 ingest/query 时知道"这个 Wiki 为什么存在"）

**雷区**

- ❌ 说 LLM-Wiki 是 RAG 的替代品（互补）
- ❌ 说"新知识进来重建 Wiki 就行"（增量更新）

### O-57｜LLM-Wiki 有哪两种实现形态？AGENTS.md 和 SOUL.md 分别管什么？

- **级别**：L3　**来源**：ch12 §12.2 + §12.3（手法 A+C+D）　**条目**：25

**参考回答**

> 两种形态：**Agent 内嵌式**（知识作为 Markdown / Skill 放进 Agent 工作环境，轻量、Agent 原生、易迁移、人机共读）和**独立知识系统**（自建解析索引检索，支持 PDF/DOCX/网页等多源，有知识树与关系图谱，多 Agent 通过 API / MCP 共享）。
> 选型的本质**不是"用 Skill 还是桌面应用"**，而是——**知识是 Agent 的一部分，还是独立基础设施**。前者强调让 Agent 自己拥有知识，后者强调把知识能力做成可调用的服务。个人/单项目用内嵌式，规模更大或要团队共享就上独立系统。
> 两个文件：**AGENTS.md 是项目的宪法**——项目身份、行为规则、**安全红线**、工具偏好、环境信息、工作流程；**SOUL.md 是人格**——语气与风格，比如"涉及破坏性操作必须确认""不确定的事情就说不确定"。

**追问链**

1. → SOUL.md 为什么要放在 System Prompt 最前面？（它内容固定，对应**静态全局段**，而 **prompt cache 只对前缀生效**——最稳定的内容放最前，后面变化才不会让整段缓存失效，见条目 17）
2. → AGENTS.md 里的"安全红线"和 Hooks 的 approval-hook 重复吗？（不重复，是**互补两道**：AGENTS.md 让 Agent **不想**做，Hooks 让它 **做不了**）
3. → 独立知识系统对外怎么暴露能力？（**本地 HTTP API + MCP Server**：健康检查、项目列表、文件树与内容、Hybrid 混合检索、知识图谱、触发资料源重扫描——Agent 不用手写 HTTP 调用）

**雷区**

- ❌ 把两种形态的区别说成"Skill vs 桌面应用"
- ❌ 把 SOUL.md 和 AGENTS.md 混为一谈（一个管硬规则，一个管软风格）

### O-58｜两步 CoT Ingest 为什么要拆成两步？知识库怎么保证不腐烂？

- **级别**：L4　**来源**：ch12 八股 Q4 + §12.7/12.8（手法 B+C+D）　**条目**：25

**参考回答**

> **两步 CoT Ingest**：Step 1（分析）让 LLM 读素材输出结构化 JSON——关键实体、核心论点、与现有 Wiki 的关联、矛盾、结构建议；Step 2（生成）基于这份 JSON 生成 Wiki 文件。Karpathy 原始设计是单步（边读边写）。
> 拆开的三条理由：① **分析和生成是不同的认知任务**，分开后各自质量更高；② 分析结果**可被缓存和审查**（人能先检查 JSON 再决定要不要生成）；③ 支持长内容的**链式思考**。工程上再配 **SHA256 增量缓存 + 持久化队列**，既不重复烧 Token，也不会中途丢任务。
> **抗腐烂靠 Lint**：孤立页面（无双向链接）、断链（指向不存在页面的 wikilink）、索引一致性（index.md 与实际文件对不对得上）、**AI 级矛盾检测**（页面间的事实冲突，只有 LLM 能做）、**置信度标注**（EXTRACTED / INFERRED / AMBIGUOUS / UNVERIFIED）。
> 我觉得置信度标注最容易被忽略但最有价值：**它区分了"从原文提取的"和"模型推断的"，不标的话 Wiki 用久了就分不清哪些是真知识、哪些是模型编的**。

**追问链**

1. → 检索时怎么排序？（**四信号关联度**：来源重叠 ×4.0 > 直接链接 ×3.0 > Adamic-Adar（共同邻居）×1.5 > 类型亲和 ×1.0——**客观证据（同源）权重高于主观判断（链接）**）
2. → 上下文怎么装？（五阶段管线：分词搜索（中文 **CJK 二元组**）→ 可选向量语义（LanceDB）→ **图谱扩展（2 跳带衰减）** → **预算控制（Wiki 60% / 历史 20% / 索引 5% / 系统提示 15%）** → 组装时附**完整内容**并按 [1][2] 编号引用）
3. → 为什么图谱扩展要带衰减？（不衰减会让**弱关联无限扩散**污染上下文）
4. → 隐私边界怎么说？（知识库文件和离线图谱**始终留在本地**；但**问答/摄入时**的 prompts、引用、检索片段仍可能发往模型提供商；API 密钥不存应用配置里，本地访问要过来源检查 + 启动凭据检查）

**雷区**

- ❌ 说"单步摄入就够了"（工业级都拆两步）
- ❌ 只讲 Lint 的四项检查，漏了**置信度标注**
- ❌ 说"用了本地知识库数据就完全不出网"（问答/摄入环节仍会发往模型提供商）
