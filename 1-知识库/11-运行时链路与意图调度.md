**§2.8 三种意图识别方法**

> Step 2（意图识别）和 Step 3（任务分类）是整条链路的**分叉点**——Agent 能否走上正确的执行路径，取决于这两步做得好不好。

| 方法 | 原理 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 关键词匹配 | 匹配预设关键词，如"天气"→查询意图 | 速度快，成本低 | 粗粒度，误判率高 | 简单指令型交互 |
| 语义理解 | 通过 LLM 深层理解用户表达的真实意图 | 精准，能理解隐含意图 | 成本高，延迟大 | 复杂多意图场景 |
| 模式识别 | 基于历史对话模式匹配相似意图 | 利用经验，越用越准 | 依赖数据量，新意图难识别 | 高频重复场景 |

> 实际工程中，**三者通常组合使用**：先用关键词匹配快速筛选常见意图，命中后直接走快速路径；没命中则交给 LLM 做语义理解；长期积累的模式数据用于优化匹配规则。这就是**分层意图识别**策略。

**§2.9 模型 vs 工具：何时调用谁？**

> **调用模型（LLM）**：理解用户意图和上下文 / 逻辑推理和因果分析 / 生成文本、代码、创意内容 / 结果整合与格式化 / 判断下一步做什么
> **调用工具（Tools）**：搜索实时信息（天气、新闻）/ 执行代码（运行、测试）/ 读写文件（磁盘操作）/ 调用外部 API（支付、数据库）/ 数学计算（高精度运算）
> 一个关键原则：**模型擅长"思考"，工具擅长"行动"**。调度器的核心职责就是判断当前子任务属于哪一类，把任务分给最合适的执行者。
> 调度器的核心价值在于**避免无谓的调用**：如果用户只是问"Python 怎么排序"，不需要调用搜索工具，模型直接回答即可；如果用户问"北京明天天气"，模型无法知道实时数据，必须调用工具。

**==Q6: 从用户输入到 Agent 输出，完整链路包含哪些步骤？每步的作用是什么？==**

> 完整 8 步链路：① 用户输入接收（接收原始消息，预处理清洗）② 意图识别（理解用户想做什么，决定执行路径）③ 任务分类（判断任务类型和复杂度，决定是否需要拆解）④ 任务拆解（仅复杂任务需要）⑤ 执行调度（决定何时调用模型、何时调用工具）⑥ 工具调用（通过 Function Calling/MCP 调用外部工具）⑦ 结果整合（收集各步骤输出，缝合为完整答案）⑧ 输出返回（格式化返回用户，同时存入记忆）。
> 关键：**Step 5→2 的回边表示迭代循环，Agent 不是单程直线，而是可以循环调整的。**

**==Q7: Agent 如何判断一个任务是简单问答还是需要多步执行？判断依据是什么？==**

> 通过**意图识别 + 任务分类**两步判断。
> **任务分类依据四个维度**：① 是否需要外部数据？（需要 → 至少涉及工具调用）② 是否需要多步操作？（需要 → 必须任务拆解）③ 输入的复杂度？（单句问答 → 简单，长文+多要求 → 复杂）④ 是否有依赖关系？（步骤间有先后依赖 → 复杂调度）
> 简单问答：跳过拆解和工具调用，直接回答。复杂任务：走完 8 步链路，可能多轮迭代。

## 一、完整 8 步链路

| 步骤 | 做什么 | 为什么需要 | 负责模块 |
| :--- | :--- | :--- | :--- |
| **① 输入接收** | 接收原始消息（文本/图片/语音），格式化、清洗噪声 | Agent 与外部世界的接口 | 输入处理 + 消息队列 |
| **② 意图识别** | 理解用户想做什么（问答 / 修改 / 开发） | 不同意图走不同路径 | LLM + 规则引擎 |
| **③ 任务分类** | 判断类型与复杂度等级 | 复杂度决定要不要拆解 | 分类器 |
| **④ 任务拆解** | 拆成有序子任务，定依赖与顺序 | 单次调用完不成复杂目标 | 规划 Planning |
| **⑤ 执行调度** | 决定先后、何时用模型、何时用工具 | 资源有限，顺序影响效率 | 调度器 Scheduler |
| **⑥ 工具调用** | 通过 Function Calling / MCP 调外部能力 | LLM 本身不会查天气、跑代码、读写文件 | 工具模块 |
| **⑦ 结果整合** | 收集碎片输出，缝成连贯答案 | 多步结果是碎片化的 | LLM + 记忆缓存 |
| **⑧ 输出返回** | 格式化 + 写入记忆 | 体验取决于输出；记忆供下轮用 | 格式化引擎 + 记忆写入 |

```
① 输入 ─▶ ② 意图识别 ─▶ ③ 任务分类 ─▶ ④ 任务拆解(仅复杂) ─▶ ⑤ 执行调度 ─▶ ⑥ 工具调用 ─▶ ⑦ 结果整合 ─▶ ⑧ 输出
             ▲                    │
             └──── 回边（工具返回新信息时，重新理解意图）──────┘
```

> **两处关键**：① **④ 是条件步骤**（简单任务跳过）；② **⑤→② 的回边**说明它不是流水线。

## 二、意图识别：三种方法与分层策略

**核心是把三种方法按成本从低到高串成漏斗**：

```
用户输入
  │
  ├─ ① 关键词匹配（成本 0，延迟 ~0）── 命中 ──▶ 直接走快速路径
  │                                    └ 未命中
  ├─ ② 语义理解（LLM，贵但准）──────────▶ 得到意图
  │
  └─ ③ 模式识别（历史高频）────────────▶ 反哺优化 ① 的规则
```

| 层 | 成本 | 准确率 | 什么时候用 |
| :--- | :--- | :--- | :--- |
| 关键词匹配 | 极低 | 低（粗粒度、误判率高） | 简单指令型交互 |
| 语义理解 | 高（多一次 LLM 调用） | 高（能理解隐含意图） | 复杂多意图场景 |
| 模式识别 | 低（查表） | 依赖数据量，新意图识别不了 | 高频重复场景 |

## 三、任务分类的四个维度

| 维度 | 判断 | 结论 |
| :--- | :--- | :--- |
| **是否需要外部数据？** | 需要 | 至少涉及工具调用 |
| **是否需要多步操作？** | 需要 | 必须任务拆解 |
| **输入复杂度？** | 单句问答 → 简单；长文+多要求 → 复杂 | 决定要不要拆 |
| **步骤间有依赖？** | 有先后依赖 | 复杂调度（可能要串行） |

→ **简单问答**：跳过 ④ 和 ⑥，直接答。
→ **复杂任务**：走完 8 步，且可能多轮迭代。

## 四、调度器：模型 vs 工具

**唯一原则：模型擅长"思考"，工具擅长"行动"。**

| 判断节点 | 结论 |
| :--- | :--- |
| 需要**外部数据**？（天气/新闻/数据库） | → **调工具** |
| 需要**逻辑推理**？（理解/分析/因果） | → **调模型** |
| 需要**格式化输出**？（润色/排版） | → **调模型** |
| 需要**验证结果**？ | → **工具 + 模型交叉验证**（工具取事实，模型判断一致性） |

**调度器的真正价值不是"该调谁"，而是"避免无谓的调用"**：

> 问"Python 怎么排序" → 不该调搜索，模型直接答。
> 问"北京明天天气" → 模型不可能知道，**必须**调工具。

> 工程上还要加一层成本/延迟考量：**简单意图走关键词快速路由（低成本），复杂意图才走完整 LLM 推理链路（贵但准）**。

## ❓ 你的疑问解答

> **你在记录区写的疑问**：这种意图识别真靠谱吗，是不是让一个意图识别 LLM 子任务来识别更好？

**先纠正一个隐含前提**：意图识别不是某个"神秘模块"，它只是一个**动作**。你记录表里的"**语义理解**"这一行，实现方式就是让 LLM 判断意图。所以"用意图识别 LLM"**已经在方案里了**——真正的问题是：**要不要把它拆成一个独立的 LLM 子任务**？

这取决于五个权衡：

| 维度 | 独立 LLM 子任务 | 融进主 LLM 调用 |
| :--- | :--- | :--- |
| **延迟** | ➕ 多一次往返（+300ms~1s） | ✅ 无额外延迟 |
| **成本** | ➖ 多一次调用（但 prompt 小，且可缓存） | ➖ 主调用 prompt 变大 |
| **可控性** | ✅ 输出可强约束（枚举 / JSON Schema），不达概率就给默认值 | ❌ 混在生成里，难约束 |
| **可观测** | ✅ 意图可单独记录、看分布、做回归 | ❌ 埋在输出里，难追踪 |
| **可评测** | ✅ 分类有标签，能用准确率/混淆矩阵衡量 | ❌ 几乎没法单独评测 |
| **效果** | ✅ 专用提示词 + Few-Shot，分类更准 | ➖ 可能被"顺便回答"带偏 |

**我的建议是分阶段**：

| 阶段 | 做法 | 理由 |
| :--- | :--- | :--- |
| **验证期** | 拆成**独立子任务**（甚至先上小模型） | 好调试、好评测、能看意图分布——这个阶段你最需要的是「可观测」而不是「省 300ms」 |
| **稳定期** | 逐步**融进主调用**（用结构化输出 / Function Calling 约束） | 链路稳定后，省一次往返换延迟和成本 |
| **成熟期** | 高频意图**下沉成规则**（关键词/缓存） | 热点路径不该每次都过 LLM |

**三个必须注意的风险**

1. **错误放大**：意图识别错了，后面全错。所以要有**兜底**——低置信度就反问用户，或走"通用路径"而不是硬猜。
2. **可评测**：意图识别是少数**能用传统 ML 指标衡量**的 LLM 环节（有标签、有混淆矩阵），所以**应该建评测集**，别靠感觉。
3. **主流替代方案**：其实**Function Calling 已经吞掉了一部分意图识别**——让模型直接决定"调哪个工具"，等价于把「意图识别 + 工具选择」合并成一步。这是目前最主流的做法，缺点是**无法单独观测中间意图**。

> **一句话结论**：你直觉是对的——**分层的、可评测的意图识别比"靠主模型顺便猜"更靠谱**，但代价是延迟和一次额外调用；所以正确姿势是**先拆开求可观测，稳定后再融合求延迟**。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 8 步链路是一条直线 | **⑤→② 有回边**，可以循环迭代 |
| 每个任务都要走完 8 步 | ④ 任务拆解**只在复杂任务时执行**，简单问答直接答 |
| 意图识别只能用关键词 | 三种方法分层组合；语义理解层就是 LLM |
| 调度器越"积极调工具"越好 | 它的价值恰恰是**避免无谓调用**（能直答就别调工具） |
| 模型能算精确数学 | 不能。高精度运算属于工具的职责 |
| 多步任务里步骤顺序无所谓 | 有依赖关系时必须串行，调度要考虑顺序 |

## 🎤 面试怎么答（口述模板）

> **问：Agent 从用户输入到输出，中间经历了哪些步骤？**
> "完整是 8 步：输入接收、意图识别、任务分类、任务拆解、执行调度、工具调用、结果整合、输出返回。这里面有两个点必须讲到——**第四步任务拆解是条件触发的**，简单问答会跳过，直接回答；**第五步到第二步有一条回边**，因为工具可能返回新信息，需要重新理解意图，所以 Agent 不是一条直线，是可以循环迭代的。"

> **追问：那怎么判断一个任务简单还是复杂？**
> "看四个维度：要不要外部数据（要就至少有工具调用）、要不要多步（要就必须拆解）、输入复杂度（单句还是长文多要求）、步骤间有没有依赖。四个维度综合起来决定走不走完整链路。"
