2. 五步：**感知**（收消息+历史）→ **决策**（要不要调工具）→ **行动**（执行工具）→ **观察**（结果回填历史）→ **循环**。

**§3.6 理解 Agent 循环**

> 回顾上面的代码，Agent 的核心是一个 `while True` 循环：
> 感知用户消息 + 历史 → 决策（AI 判断：调工具 or 回答?）→ 行动（执行工具）→ 观察（工具结果加入历史）→ 响应（返回自然语言）
> 这就是 **ReAct 循环**的简化版——第 6 章会详细讲解。现在你只需要理解：
> 1. **感知**：AI 接收用户消息和对话历史
> 2. **决策**：AI 判断是否需要调用工具
> 3. **行动**：如果需要，执行工具调用
> 4. **观察**：把工具结果给 AI，让它看到结果
> 5. **循环**：AI 看到结果后，可能继续调工具，也可能直接回答

**==Q3: Agent 循环什么时候停止？==**

> 当 AI 不再请求调用工具时（finish_reason 为 stop），循环结束，返回最终回答。需设置 max_loops 防止无限循环。

**Q4: 为什么需要多轮对话？**

> AI 可能需要多次工具调用才能完成任务；用户可能追问相关问题，需要从历史中获取上下文。多轮对话让 Agent 具备"记忆"能力。

## 一、循环的五步（对应你自己写的 `agent.py`）

| 步骤 | 代码位置 | 具体做了什么 |
| :--- | :--- | :--- |
| **① 感知** | `messages.append({"role":"user",...})` | 用户输入拼进历史；`messages` 里已经有 system + 前几轮的对话 |
| **② 决策** | `client.chat.completions.create(model, messages, tools=tools_schema)` | 把**历史 + 工具列表**一起发给模型，让模型自己判断要不要调工具 |
| **③ 行动** | `for tool_call in msg.tool_calls:` → `execute_tool_with_retry(...)` | 逐个执行模型要求调用的工具 |
| **④ 观察** | `messages.append({"role":"tool","tool_call_id":...,"content":...})` | 结果**回填进历史**，模型下一轮就能"看到" |
| **⑤ 循环** | 回到 `②` | 模型看到结果后：继续调工具 / 或直接回答 |

```
                  ┌──────────────────────────────┐
                  │                              │
   ① 感知 ──▶ ② 决策 ──▶ ③ 行动 ──▶ ④ 观察 ──▶ ⑤ 回到②
              │
              └─ 没有 tool_calls? ──▶ 输出回答，跳出循环
```

## 二、终止条件：三轮保护

| 保护 | 位置 | 作用 |
| :--- | :--- | :--- |
| **AI 自己停** | `if not msg.tool_calls:` | 主出口——AI 认为信息够了就不再要工具（你说的 finish_reason=stop） |
| **上限兜底** | `if loop_num >= MAX_AGENT_LOOPS` | 防止模型反复调工具不回头（本代码里是 10） |
| **用户退出** | `if user_input.lower() in ["quit","exit","退出"]` | 外层循环的退出（对应你记录里的"当用户说 quit"） |

> ⚠️ 注意区分**两层循环**：外层 `while True` 是"多轮对话"（等用户输入），内层 `while True` 是"Agent 循环"（一个任务内的多步执行）。**Q3 问的是内层**——它由 AI 决定何时停，`max_loops` 只是保险丝。

## 三、多轮对话 = Agent 的记忆

**关键机制**：`messages` 数组**跨用户输入累积**（在 `run_agent()` 里只初始化一次，不在每轮重建）。

于是出现了这个现象——**追问可以不调工具**：

```
用户：北京今天天气怎么样？
  → 调 get_weather("北京") → 晴 25°C
用户：那上海呢？
  → 调 get_weather("上海")
用户：哪个更热？
  → ❌ 不调工具 ✅ 直接从历史里比较 25°C vs 28°C 回答
```

> 这就是「短期记忆」的朴素实现：**历史即记忆**。理解这一点，就理解了第 7 章记忆系统要解决什么——历史会无限膨胀（见条目 15 的 token 递增）。

## 四、三个容易忽略的工程细节（你的代码里已经处理了）

| 细节 | 你的代码 | 不处理会怎样 |
| :--- | :--- | :--- |
| **SDK 对象要转普通 dict** | `messages.append(msg.model_dump(exclude_none=True))` | SDK 的 message 对象直接塞回 messages，下次请求可能序列化失败 |
| **工具参数 JSON 解析可能失败** | `try: json.loads(...) except JSONDecodeError` | 模型生成非法 JSON → 整轮崩掉 |
| **空输入要忽略** | `if not user_input: continue` | 白发一次请求，白花钱 |

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 循环执行固定次数后停止 | 主出口是 **AI 不再请求工具**；次数上限只是保底 |
| 用户说 quit 时 Agent 循环停止 | 那是**外层**多轮对话循环；Agent 内层循环由 AI 决定停 |
| 每次用户提问都要重建 messages | 那样就没有"记忆"了——追问必须靠累积的历史 |
| 追问一定要重新调工具 | 不一定。能从历史推理出来的（比较、追问细节）就直接答 |
| 工具结果随便塞回 messages 就行 | 必须以 `role:"tool"` + 对应 `tool_call_id` 返回，否则模型对不上号 |

## 🎤 面试怎么答（口述模板）

> **问：Agent 循环什么时候停止？**
> "主出口是 **AI 自己不再请求调用工具**——当返回的消息里没有 `tool_calls`，说明它认为信息已经够了，循环结束返回最终回答。但光靠这个不安全，模型可能反复调工具不回头，所以还要设一个 `max_loops` 上限兜底。另外要区分两层循环：外层是多轮对话等用户输入，内层才是单个任务里的 Agent 循环。"

> **追问：为什么要有对话历史？**
> "因为 Agent 的记忆就是对话历史。一是 AI 可能要多轮工具调用才完成一个任务，中间结果必须留在历史里；二是用户会追问，比如'那上海呢''哪个更热'，这些都能从历史里拿到上下文，甚至不用重新调工具——直接比较之前的结果就行。"
