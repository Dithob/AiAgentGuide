## 🎯 30 秒结论

1. **提示词工程管单轮怎么说，上下文工程管每次调用带什么**。两者互补，但 Agent 跑 30 轮以后，**上下文工程的重要性超过提示词工程**——因为这时候提示词写得好不好已经不重要了，重要的是**关键约束有没有被裁掉**。
2. 五种裁剪策略不是单选题：压缩率高往往信息保留差（截断），信息保留好往往实现复杂（语义保护型）。**真正落地的答案是"混合裁剪"——给每类消息分配最合适的策略。**
3. 混合裁剪的骨架是一张**优先级表**：P0 永不裁剪 → P1 尽量保留 → P2 可压缩 → P3 可摘要 → P4 可丢弃。
4. 记忆系统负责**存什么**，上下文工程负责**带什么**——检索回来的记忆，仍要过一遍裁剪器。
5. Claude Code 的落地形态是**三级压缩链 + 渐进升级**：microCompact（~70%，规则提取，30-40%）→ autoCompact（~85%，LLM 摘要，60-70%）→ sessionMemoryCompact（手动/会话结束，转存长期记忆，>90%）。
6. 设计哲学一句话：**先低成本压低价值内容，不够再中成本压中价值，最后高成本转存高价值。**

**⑤ 上下文工程与记忆系统的关系（原文表）**

| 维度         | 上下文工程（第 5 章）     | 记忆系统（第 7 章）                    |
| :----------- | :------------------------ | :------------------------------------- |
| **工作层**   | 短期 — 当前上下文窗口内   | 长期 — 跨会话持久化                    |

## 一、五种裁剪策略：一张表选完

把原文的表读成「**能不能接受信息损失**」这一个问题：

| 问你自己的问题 | 回答 | 选它 |
| :--- | :--- | :--- |
| 只是 demo，跑了就行？ | — | **截断**（O(1)，零额外开销） |
| 愿意多花一次 LLM 调用换更多历史？ | 愿意 | **摘要压缩** |
| 只需要"最近发生的事"，且要恒定的上下文长度？ | 是 | **滑动窗口** |
| 需要按消息类型区别对待，且要信息密度最高？ | 是 | **选择性保留**（生产系统首选） |
| 是工业级 Agent，要求压缩率和信息保留都最优？ | 是 | **语义保护型**（实现最复杂） |

**五个策略的代价曲线**

| 策略 | 硬伤 |
| :--- | :--- |
| 截断 | **丢掉的可能正是 P0**——它不看内容，只看新旧 |
| 摘要压缩 | 摘要本身要花 LLM 调用（额外 token + 延迟），且**摘要会丢细节，而细节常常就是线索** |
| 滑动窗口 | 上下文长度恒定是优点，但**"最近 ≠ 最重要"** |
| 选择性保留 | 怎么分类是新的难题——分类器本身是工程成本 |
| 语义保护型 | 复杂度最高，容易过度设计；调试困难 |

> **面试可以直接给的一句话**：*"前三种是'按位置/长度'裁，后两种是'按语义'裁。工业级一定是按语义裁，因为位置和长度跟重要性没有相关性。"*

## 二、P0~P4：把优先级表用起来

原则：**先按 P4→P0 的顺序砍，砍到刚好装下为止。**

| 步骤 | 动作 | 付出的代价 |
| :--- | :--- | :--- |
| 1 | 丢 P4（寒暄、确认、重复） | 几乎没有 |
| 2 | 压缩 P3（Thought → 结论） | 丢失推理链，但结论保留 |
| 3 | 提取 P2（工具返回值 → 关键字段） | 丢失原始输出，**这是省 token 最大的一块** |
| 4 | 精简 P1（压缩 Schema 描述） | 工具选择准确率会下降——**要慎重** |
| 5 | P0 不动 | 装不下就该报错/熔断，而不是裁 P0 |

**P2 是真正的"富矿"**：一条 `read_file` 返回 8000 行是常态，而下游真正需要的可能只是「文件 app.py，共 800 行，主要函数：main()、process()、validate()」。

## 三、Claude Code 的三级压缩链（落地形态）

| 级别 | 触发时机 | 做法 | 压缩率 | 信息损失 | 额外开销 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **① microCompact** | 每轮对话后自动执行，当前上下文接近 **~70%** 容量时 | 扫描历史里的工具返回值，把大块输出替换为**规则提取**的摘要 | 约 **30-40%** | 低（只压冗余部分） | 小（**不调 LLM**） |
| **② autoCompact** | microCompact 后仍接近 **~85%** 容量时 | 用 **LLM** 对整段历史生成结构化摘要，用摘要替代旧消息，**保留最近 N 轮完整对话** | 约 **60-70%** | 中（保留关键决策与约束，丢推理细节） | 高（一次 LLM 调用） |
| **③ sessionMemoryCompact** | 用户手动 `/compact`，或会话结束前 | 把整个会话精华写入持久化记忆文件（CLAUDE.md），下次会话启动自动加载 | **>90%** | 只保留四类记忆 | — |

> **第 3 级严格说不是"压缩"而是"转存"**——把短期记忆转成长期记忆。这也是它与 [20-记忆系统](20-Agent记忆系统.md) 的接口。

**两个工程细节（原题的考点）**

| 机制 | 设计 | 为什么必须有 |
| :--- | :--- | :--- |
| **递归守卫** | `shouldAutoCompact`：当查询来源是 `session_memory` 或 `compact` 时**返回 false** | 否则形成「压缩 → 触发一次查询 → 又判定需要压缩」的**死循环** |
| **连续失败熔断** | `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3` | 摘要一直失败时及时止损，避免无限重试烧钱 |

## 🔆 强化延伸（你标了 `==Q4==`）

你标的是 `==Q4: Claude Code 的三级压缩链是什么？各级的触发时机和压缩方式有何不同？==`。原答案给了"是什么"，这里补两层：**为什么是这个顺序**，以及**这个设计能被迁移到哪里**。

### 🔆1 为什么是"三级"而不是"一个更强的压缩器"

一个直觉方案是：既然 autoCompact 压缩率最高，为什么不在 70% 就直接上 LLM 摘要？

| 方案 | 一次压缩的成本 | 压缩时机 | 问题 |
| :--- | :--- | :--- | :--- |
| 只做 LLM 摘要（一档） | 高（每次都要调 LLM） | 70% 就触发 | **每次都花 LLM 的钱，而且摘要会丢细节**——很多情况下规则提取就够了 |
| 三级渐进（实际方案） | 低 → 中 → 高 | 按需升级 | 只在必要时才付出更高成本 |

**核心是一个"成本-收益阶梯"**：

```
信息价值密度
  高 │  ● P0 System / 当前输入        ← 用 sessionMemoryCompact 转存（高成本、高价值）
     │  ● P1 Schema / 初始约束
  中 │  ● P2 工具返回值（8000行→3行）  ← microCompact 规则提取即可（零 LLM 成本）
     │  ● P3 Thought 推理链            ← autoCompact 摘要（中成本）
  低 │  ● P4 寒暄/确认                ← 直接丢弃（零成本）
     └────────────────────────────────────▶ 处理成本
```

> **判据：能用规则提取的，绝不调 LLM。** microCompact 就是这条判据的产物——工具返回值是**半结构化**的（有明确的字段、行数、函数名），规则提取的性价比远高于 LLM 摘要。

**为什么阈值是 70% / 85%（而不是 90% / 99%）**

| 阈值 | 留出的余量在防什么 |
| :--- | :--- |
| 70% 触发 microCompact | 给**下一轮的输入 + 工具返回值**留空间——触发时不能等到满，否则这一轮就已经溢出了 |
| 85% 触发 autoCompact | 给 autoCompact **自己的 LLM 调用**（含它的输出）留空间 |
| 会话结束 / 手动 转存 | 给**下一次会话的冷启动**留空间（呼应 ch07 的"有效上下文窗口"公式） |

> 这解释了 ch07 里那个公式为什么长这样：
> `有效上下文窗口 = 模型上下文窗口 - max(maxOutputTokens, 20000) - AUTOCOMPACT_BUFFER`（13,000）
> **压缩阈值和输出预留是同一个预算方程的两端。**

### 🔆2 追问链（4 问，练到能连续答）

1. **问**：三级压缩是"按固定顺序依次执行"吗？
   → **不是**。是**按需升级**——70% 时只跑 microCompact，跑完还不够才升级到 autoCompact（85%），再不够才转存。原题 D 选项（"按固定顺序依次执行，不可跳过"）就是踩这个坑。
2. **问**：为什么 microCompact 不调 LLM？
   → 工具返回值是半结构化的，规则提取（行数、文件名、函数名、错误行）就够用；调 LLM 在这里是**用高成本换边际收益**。另外它跑在每轮对话后，调 LLM 会直接抬高每一轮的延迟。
3. **问**：autoCompact 的递归守卫在防什么？
   → 防「压缩 → 压缩过程本身触发一次 LLM 查询 → 该查询又被判定需要压缩」的死循环。实现上是 `shouldAutoCompact` 在来源为 `session_memory` / `compact` 时返回 false。再叠加 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3` 熔断兜底。
4. **问**：这套设计迁移到自己的项目，最该先做哪一级？
   → **microCompact（P2 工具返回值裁剪）**。理由：收益最大（大块输出占比最高）、成本最低（零 LLM 调用）、风险最小（工具返回值本来就有"摘要后仍可用"的性质）。第二优先是 P4 直接丢弃。**LLM 摘要要放到最后做，因为它是唯一引入新故障模式的环节。**

### 🔆3 你的表达可以再进一步

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 上下文工程就是提示词工程的新名字 | 关注点不同：前者管"带什么"（多轮、生命周期），后者管"怎么说"（单轮指令）；且 Agent 长会话里前者权重更高 |
| 三种压缩是**依次固定执行**的 | 是**按需升级**：~70% 触发第 1 级，不够才升第 2、第 3 级 |
| 上下文工程和记忆系统是一回事 | 记忆系统管**存什么**（跨会话），上下文工程管**带什么**（窗口内）；检索回来的记忆仍要过裁剪器 |
| 裁剪就是"按时间从旧到新删" | 那是**截断**——最粗糙的一种，会误删 P0。工业级按**优先级/语义**裁 |
| 压缩率越高越好 | 压缩率和信息保留是**反向关系**；"语义保护型"之所以最复杂，就是为了同时要两者 |
| 摘要压缩一定优于规则提取 | 工具返回值是半结构化的，**规则提取性价比更高且不引入 LLM 故障模式** |
| 窗口够大就不用管上下文工程 | 窗口越大，中间信息被稀释越严重（"lost in the middle"），**装得下 ≠ 用得到** |
| 记忆检索回来的内容可以直接塞 | 检索回来的内容要先过裁剪优先级——它多半是 P2/P3 级 |

> "我不会只选一种策略，实际落地一定是**混合裁剪**：先给每类消息打优先级，再按 P0 到 P4 依次砍。
> P0 是 System Prompt 和当前用户输入，永不裁剪——System 是行为准则，当前输入是本轮任务目标；P1 是工具 Schema 和用户初始约束，尽量保留，真的超限才压缩 Schema 描述；P2 是工具返回值和 Action-Observation 对，可压缩，这是省 token 的最大一块，比如 8000 行 read_file 输出通常只需要'文件 app.py、800 行、主要函数 main/process/validate'这几行；P3 是中间推理 Thought，可以摘要成结论；P4 是寒暄、确认这类，直接丢。
> 判据是：**位置和长度跟重要性没有相关性**——所以不能简单地按新旧截断，必须按语义裁。"

> **追问：具体实现层次上是怎么做的？**
> "拿 Claude Code 举例，它做的是**三级压缩链 + 渐进升级**。
> 第一级 microCompact，上下文到 ~70% 触发，压缩工具返回值，用**规则提取**而不是 LLM，压缩率 30-40%，信息损失低。第二级 autoCompact，第一级压完还到 ~85% 才触发，这时才用 LLM 生成结构化摘要，保留最近 N 轮完整对话，压缩率 60-70%。第三级 sessionMemoryCompact，用户手动 `/compact` 或会话结束触发，把会话精华写进 CLAUDE.md 持久化——严格说这已经不是压缩而是**转存**，把短期记忆变长期记忆。
> 设计哲学是**先低成本压低价值内容，不够再中成本压中价值，最后高成本转存高价值**。两个细节值得提：autoCompact 有递归守卫，查询来源是 compact 时直接返回 false，否则会死循环；还有连续 3 次失败的熔断。"

> **追问：如果要你对自己的项目做一版，会怎么排优先级？**
> "先做 P2 的规则提取——收益最大、零 LLM 调用、风险最小，因为工具返回值本身就有'摘掉冗余仍可用'的性质。再补 P4 直接丢弃，几乎白捡。**LLM 摘要放到最后**，因为它是唯一会引入新故障模式的环节：摘要可能失败，所以必须配降级链，AI 摘要 → 规则摘要 → 硬截断，一级级往下掉。"
