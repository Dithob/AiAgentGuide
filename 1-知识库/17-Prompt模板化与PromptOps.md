## 🎯 30 秒结论

1. 05 条讲的是「**怎么写一条好 Prompt**」，本篇讲的是「**当 Prompt 变成工程产物**」——结构可拆、模板可渲染、版本可管、缓存可算。
2. Prompt 的第一个进阶认知是**它不是一段文字，而是三层**：**结构层**（骨架，6 个结构单元）→ **工程方法层**（怎么思考，CoT/ToT/ReAct…）→ **输出工程**（给程序消费，结构化+解析+验证）。
3. 字符串拼接写 Prompt 的三个死穴：**可读性差**（变量 > 3 个就乱）、**无法条件渲染**、**无法复用**。解药是**模板引擎**（Jinja2 / Handlebars）。
4. **PromptOps = 把 Prompt 当接口管**：输入契约 / 输出约定 / 错误处理 / 版本控制——四要素和 API 一一对应。
5. 工业级的分水岭是**分区缓存**：越稳定的越靠前（静态区 → 半静态区 → 动态区），最大化前缀缓存命中。**能给 Prompt 分区，比能把 Prompt 写漂亮值钱得多。**
6. 一条判据贯穿：**每轮都变的 section 一定破坏前缀缓存**——所以给它命名的函数里会带 `DANGEROUS`。

**① Prompt 的结构层：6 个结构单元**

| 单元          | 作用                                 | 必填 |
| :------------ | :----------------------------------- | :--- |
| **Role**      | 角色设定，决定知识边界与回答风格     | ✅    |
| **Directive** | 核心指令，描述要做什么               | ✅    |
| **Context**   | 背景信息，提供决策依据               | 可选 |
| **Exemplars** | 示例（Few-shot），引导输出格式与风格 | 可选 |
| **Format**    | 输出格式约束（JSON/Markdown/表格）   | 推荐 |
| **Style**     | 风格约束（语气、长度、细节程度）     | 可选 |

**② 输出工程三要素**

> **① 结构化**：用 JSON Schema 约束输出格式，而非自由文本
> **② 解析**：下游代码用 JSON.parse() 而非正则表达式提取信息
> **③ 验证**：校验字段完整性、类型正确性、业务逻辑合法性

**③ C.L.E.A.R 原则（你摘录的完整对照表）**

| 原则           | 含义             | 反例 → 正例                                                  |
| :------------- | :--------------- | :----------------------------------------------------------- |
| C — Concise    | 简洁，剔除冗余   | "帮我生成一个你觉得合适的设计" → "生成一个 SaaS 产品落地页，包含 Hero、Features、Pricing 三段" |
| L — Logical    | 有逻辑，条理分明 | 大段文字描述 → 用编号步骤：①分析需求 ②设计方案 ③输出代码     |
| E — Explicit   | 明确，不留歧义   | "写得专业一点" → "语气正式，用第三人称，每段不超过 3 句话"   |
| A — Adaptive   | 可迭代优化       | 一次性写死 → 先草稿，测试效果后逐步改进                      |
| R — Reflective | 可复盘复用       | 用过就丢 → 保存高质量 Prompt 到模板库，标注适用场景          |

**④ Few-shot 选择四技巧**

> **① 示例数量**：1-3 个通常足够，超过 5 个边际收益递减
> **② 示例多样性**：不要给 3 个高度相似的例子，要覆盖不同情况
> **③ 示例顺序**：将最相关的示例放在最后（靠近实际输入），效果最佳
> **④ 标签一致**：所有示例的输出格式必须完全一致，否则模型会困惑

**⑤ 八股 Q6 / Q8**

> **Q6: C.L.E.A.R 原则是什么？举个反例和正例。**
> 反例："帮我写一个好的产品介绍"——不简洁、不明确、无格式约束。
> 正例："为 SaaS 产品写 150 字介绍，突出自动化和节约成本两个卖点，语气正式，用第三人称，输出 Markdown 格式"。

> **Q8: 工业级 Agent 的 System Prompt 为什么要做分区缓存设计？静态区和动态区如何划分？**
> **原因**：工业级 Agent 的 System Prompt 可达 4000-6000 token（工具规则+安全策略+环境信息+记忆文件）。如果每轮全量发送，不仅成本高，还增加首 token 延迟。
> **划分方式**：①**静态区**（工具规则、安全策略）跨用户可缓存；②**半静态区**（用户偏好、记忆文件）同会话内可缓存；③**动态区**（MCP 指令、临时指令）每轮可能变化。
> **实现**：用 SYSTEM_PROMPT_DYNAMIC_BOUNDARY 标记分隔静态区和动态区。

## 二、LLM 参数工程（采样参数，别和 Prompt 混为一谈）

| 参数 | 做法 | 一句话记忆 |
| :--- | :--- | :--- |
| **Temperature** | 控制概率分布的"尖锐程度" | 低 = 分布尖锐、选高概率 Token（确定性）；高 = 分布平坦（多样性） |
| **Top-K** | **硬截断**：只从概率最高的 K 个 Token 中选 | K=1 等于贪心解码；K=50 就是从 Top 50 里采样 |
| **Top-P**（核采样） | **动态截断**：从概率累积和达到 P 的最小 Token 集合中选 | P=0.1 只考虑少数几个；P=0.9 保留更多选项 |
| **Repetition Penalty**（1.0–1.3） | 降低**已出现** Token 的概率 | 越高惩罚越强，但太高会导致输出不通顺 |
| **Frequency Penalty**（0.0–0.3） | 按**出现频率**惩罚 | 出现次数越多，被惩罚越重 |

> 易混点：**Repetition Penalty 是"出现过就罚"，Frequency Penalty 是"出现越多罚越重"。** 前者是开关式，后者是累加式。

## 三、模板化提示词：为什么必须上模板引擎

当变量超过 3 个，字符串拼接就开始混乱；遇到"有工具时渲染工具列表、没工具时渲染兜底话术"，f-string 直接写不出来。

**字符串拼接 vs 模板引擎**

| 维度 | 字符串拼接（f-string / `+`） | 模板引擎（Jinja2） |
| :--- | :--- | :--- |
| 可读性 | 变量 > 3 个就乱 | 模板与数据分离，读起来像文档 |
| 条件渲染 | **写不出来**（要靠 Python 拼 if） | `{% if %}` |
| 循环渲染 | 要手写 for 拼字符串 | `{% for %}` |
| 复用 | 无法继承 | `{% extends %}` / `{% block %}` |
| 边界 | 简单场景够用 | 引入模板层，需管理模板文件 |

**Jinja2 四大能力**

| 能力 | 语法 | 作用 |
| :--- | :--- | :--- |
| 变量注入 | `{{ var }}` | 把运行时数据填进模板 |
| 条件逻辑 | `{% if %}` / `{% else %}` | 按运行时状态决定渲染哪段 |
| 循环渲染 | `{% for tool in tools %}` | 把工具列表 / few-shot 示例批量铺开 |
| 模板继承 | `{% extends %}` / `{% block %}` | 多 Agent 共享基础模板，只覆写差异块 |

> 工程价值一句话：**模板文件管理提示词，代码只负责准备数据**——Prompt 与业务逻辑解耦。这也是 PromptOps 的地基。

## 四、PromptOps：把 Prompt 当接口管

当你有 10+ 个 Prompt 模板、5+ 个 Agent 角色、频繁迭代时，「改一个词 → 手动测试 → 上线 → 发现回退」就撑不住了。

**提示词即接口（Prompt as Interface）**

| 设计要素     | 含义                              | 类比 API     |
| :----------- | :-------------------------------- | :----------- |
| **输入契约** | 模板变量 + 类型约束 + 必填校验    | API 请求参数 |
| **输出约定** | JSON Schema / 格式约束 + 字段说明 | API 响应格式 |
| **错误处理** | 解析失败重试、降级策略、超时处理  | API 错误码   |
| **版本控制** | 语义化版本 + 变更日志 + 回滚能力  | API 版本号   |

**教学级 vs 工业级 PromptOps**

| 维度            | 教学级（§4.6）          | 工业级（§4.7）                      |
| :-------------- | :---------------------- | :---------------------------------- |
| **关注点**      | 模板版本管理、灰度发布  | 缓存命中率、token 成本优化          |
| **Prompt 结构** | 单一模板字符串          | 分区组装（静态/半静态/动态）        |
| **缓存策略**    | 不关注                  | memoized vs uncached，boundary 分界 |
| **Token 优化**  | 模板复用减少重复编写    | dedup 去重、路径归一化、描述预算    |
| **可观测性**    | 版本日志、质量评分      | 缓存命中率监控、token 消耗追踪      |

> 一句话对照记忆：**教学级管「版本」，工业级管「缓存 + 成本」。**

## 五、Prompt 分区缓存设计（高频考点）

**三级分区**

| 分区         | 内容                                                 | 跨用户可缓存 | 跨会话可缓存 |
| :----------- | :--------------------------------------------------- | :----------- | :----------- |
| **静态区**   | 工具使用规则、安全策略、输出格式规范、Git 安全协议   | ✅ 是         | ✅ 是         |
| **半静态区** | 用户偏好、项目配置、记忆文件                         | ❌ 否         | ✅ 同会话内   |
| **动态区**   | MCP 指令（服务器连接状态变化）、临时指令、Agent 列表 | ❌ 否         | ❌ 每轮变化   |

**Memoized vs Uncached：两种动态分节策略**

| 分节类型 | 包装函数 | 重算时机 | 典型内容 | 代价 |
| :--- | :--- | :--- | :--- | :--- |
| **Memoized** | `systemPromptSection()` | `/clear` 或 `/compact` 前保持不变，跨轮复用 | 用户偏好、项目配置、记忆文件摘要 | 无（配置不变则命中） |
| **Uncached** | `DANGEROUS_uncachedSystemPromptSection()` | **每轮重新计算** | MCP instructions（服务器连接状态每轮可能变） | prompt prefix 改变 → 提供商 cache **全部 miss**，1000+ token 的 miss 意味着额外延迟和成本 |

**System Prompt 的 16 个分节与 boundary**

```
┌─────────────────────────────────────────┐
│  静态区（跨用户可缓存）                     │
│  1. intro          自我介绍               │
│  2. system         系统级指令             │
│  3. doingTasks     任务执行规则            │
│  4. actions        操作安全策略            │
│  5. usingTools     工具使用规则            │
│  6. toneStyle      沟通风格               │
│  7. outputEfficiency 输出效率              │
├─────────────────────────────────────────┤  ← DYNAMIC_BOUNDARY
│  半静态区（同会话内可缓存）                  │
│  8. session_guidance 会话级引导            │
│  9. memory         记忆文件摘要            │
│  10. env_info      环境信息               │
│  11. language      语言偏好               │
│  12. output_style  输出样式               │
├─────────────────────────────────────────┤
│  动态区（每轮可能变化）                      │
│  13. mcp_instructions MCP 服务器指令       │
│  14. scratchpad     临时草稿              │
│  15. frc            功能路由上下文          │
│  16. summarize_tool_results 工具结果摘要   │
└─────────────────────────────────────────┘
```

> 命名哲学：函数名里带 `DANGEROUS` 不是吓人，是**提醒调用方"这里每轮都在破坏缓存"**——把代价写在 API 名字上，比写在文档里有效。

## 🔆 强化延伸（你标了 `==` 的三处）

你标的是 `==模板化提示词==`、`==Jinja2 四大能力==`、`==Q5==`——三处指向同一个知识点：**Prompt 的模板化**。这里把它讲透。

### 🔆1 为什么"模板化"是 PromptOps 的前置条件，而不是可选项

面试官如果追问"模板化到底解决了什么"，按这个顺序答能答到 L4：

| 层次 | 模板化解决的事 | 不做会怎样 |
| :--- | :--- | :--- |
| **L1 可读性** | 模板与数据分离 | 变量 > 3 个，Prompt 变成一行巨型 f-string，review 不了 |
| **L2 可维护性** | 改文案不动代码 | 改一个语气词要动 Python 文件，得回归测试代码 |
| **L3 可组合性** | `extends` / `block` 继承 | 10 个 Agent 角色各抄一份 4000 token 的 System Prompt，改一处要改十处 |
| **L4 可缓存性** | **模板边界 = 缓存边界** | 这是最容易被漏掉的一层 ↓ |

**第 4 层是关键，也是本条目和 02/05 的接缝**：

> 前缀缓存要求"前缀逐字节相同"。模板化让 **静态区/半静态区/动态区的分界是显式的、可审计的**——
> 你能一眼看出"哪些 section 每轮都在变"，从而把它们推到 Prompt 末尾。
> **反过来说：不做模板化，你根本没法可靠地做分区缓存，因为分界藏在字符串拼接的执行路径里。**

**Jinja2 在 Agent 里的三个真实落点**

| 落点 | 模板需要渲染什么 | 为什么必须动态 |
| :--- | :--- | :--- |
| **工具清单** | `{% for tool in tools %}` 把注册表渲染成 tool 描述块 | 工具是注册的，不同会话可用工具不同（呼应 O-26 的 Tool RAG） |
| **Few-shot 示例** | `{% for ex in exemplars %}` | 示例经常按场景切换，甚至从向量库检索 |
| **Skill 指令** | `{% extends 'base.j2' %}` + `{% block directive %}` | 多 Skill 共享同一套骨架，只覆写核心指令段 |

**⚠️ 一个反直觉的坑**

> 动态渲染本身**会破坏缓存**。所以工程上的正确姿势是：
> **模板化的价值不在于"能渲染"，而在于"让可缓存的部分保持逐字节稳定"。**
> 工具清单这类"会话内不变、跨会话可能变"的内容，应该渲染进**半静态区**（同会话 memoize），而不是每次调用都重新渲染进系统提示的开头。

### 🔆2 逐条追问链（练到能连续答）

1. **问**：为什么不用 f-string？
   → 变量 > 3 个可读性崩；**条件渲染和循环渲染写不出**；无法继承复用。
2. **问**：模板引擎和 Prompt 缓存有什么关系？
   → **模板边界让缓存边界显式化**。前缀缓存只认逐字节相同的前缀，模板化才能可靠地把"每轮都变"的分节推到末尾（对应 §五的 `DYNAMIC_BOUNDARY`）。
3. **问**：那动态渲染是不是越少越好？
   → 是，但要看**变化频率**：会话内不变 → memoize（半静态区）；每轮都变 → uncached（动态区），且**必须放最后**，否则整段缓存全 miss。
4. **问**：把 Prompt 模板放进文件系统，会不会引入安全问题？
   → 会。模板 = 可执行的渲染逻辑 + 外挂的文本资产。所以工业级 Agent 会**禁止 Agent 自己写模板/配置文件**（Claude Code 就禁止写入 `settings.json` 和 `.claude/skills/`，见 [22 §沙箱](22-Agent运行时与安全沙箱.md)），否则等于给它留了改自己 System Prompt 的后门。

## ❓ 你的疑问解答

> 你在 ch04 记录区写下的疑问：
> **「所以为什么 MCP 指令会破坏缓存，服务器连接状态每轮可能变化？」**

**先回答"为什么它的内容会每轮变"**

MCP（Model Context Protocol）服务器的连接状态是**运行时外部状态**，不受 Agent 的 Prompt 结构控制：

| 变化来源 | 例子 |
| :--- | :--- |
| 服务器上线/掉线 | 你刚连的 MCP server 挂了重连，`tools/list` 结果变了 |
| 工具集变化 | 服务器动态注册了新工具（如按需加载的 Skill 工具） |
| 授权状态变化 | OAuth token 过期 → 该服务器的指令段被移除 |
| instructions 字段本身 | server 的 `instructions` 由 server 方维护，可能热更 |

所以 MCP instructions 段**不能假设"会话内不变"**，只能放进 Uncached 分节、每轮重算。

**再回答"为什么"每轮重算就等于"破坏缓存"**（这是你真正在问的）

前缀缓存（Prompt Caching）的命中条件只有一个：**从第 0 个 token 开始逐字节相同**。

```
第 N 轮 prompt:  [ 静态区 3000t ][ 半静态区 1500t ][ MCP 800t ][ 动态区 ... ]
                                  ↑
第 N+1 轮:        [ 静态区 3000t ][ 半静态区 1500t ][ MCP 803t ][ 动态区 ... ]
                                                      ↑ 只改了 3 个 token
```

结果：**cacheable prefix 在第 4500 个 token 处断裂**，后面 800 + N 个 token 全部按未命中计价。

| 后果 | 具体数字 |
| :--- | :--- |
| **命中长度** | 从"全量 5300"掉到"前 4500" |
| **成本** | 未命中部分按全价计费（通常约为缓存价的 10 倍量级） |
| **延迟** | 未命中前缀需要重新 prefill，TTFT 显著上升 |

**所以真正的设计原则是一条排序律：**

> **按"变化频率"降序排列 section —— 最不变的塞最前面，每轮变的甩到最后面。**
> MCP 指令之所以"危险"，不是因为它不重要，而是因为**它长在 Prompt 的中段**：它一抖，后半段全废。

**反向思考（面试可以主动抛出来加分）**

如果 MCP 指令必须每轮变、又不想破坏后面的缓存，有两条出路：
1. **把它挪到 Prompt 末尾**（或干脆作为一条 user 消息注入）——代价是模型对它的注意力权重下降；
2. **降低它的变化频率**：只在服务器集合真正变化时才重算（把"每轮重算"改成"事件驱动重算"），这本质上就是把它从 Uncached 降级成 Memoized。

**自测两问**

1. 一个 section 从"每轮变"改成"会话内不变"，它应该从哪个分节搬到哪个分节？成本变化如何？
   <br>→ Uncached（动态区）→ Memoized（半静态区）；命中长度增加该 section 的 token 数，TTFT 与单轮成本同步下降。
2. 把 MCP 指令从 Prompt 中段移到末尾，缓存命中了，但可能引入什么新问题？
   <br>→ 指令遵循度下降（长上下文"中间遗忘 / 尾部注意力"，且越靠后的约束越容易被后续动态内容冲淡），需要在"缓存省钱"与"指令可靠"之间权衡。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 模板引擎只是"写起来好看" | 它的第四层价值是**让缓存边界显式化**——不做模板化就做不可靠的分区缓存 |
| Temperature 调高 = 更聪明 | 只是分布更平坦、更多样；**推理任务应该调低**，创作才调高 |
| Top-K 和 Top-P 是一回事 | Top-K 是**固定数量**硬截断；Top-P 是**动态集合**累积概率截断 |
| Repetition Penalty 和 Frequency Penalty 一样 | 前者"出现过就罚"（开关式），后者"出现越多罚越重"（累加式） |
| Few-shot 示例越多越好 | 1~3 个足够，**超过 5 个边际收益递减**；且示例要多样、标签要一致 |
| 动态 section 越多越灵活 | 每个动态 section 都是一个**缓存断裂点**；能 memoize 就别 uncached |
| Prompt 里塞变量用字符串拼接也行 | 变量 > 3 个就失控，且**条件渲染/循环渲染根本写不出** |
| C.L.E.A.R 是"风格偏好" | 其中 **A（Adaptive）和 R（Reflective）是工程纪律**——迭代 + 入库复用，不是文案技巧 |

## 🎤 面试怎么答（口述模板）

> **问：你为什么在 Agent 项目里用模板引擎，而不是直接拼字符串？**
> "三个理由，按重要性递增。第一是**可读性**——变量超过 3 个，f-string 就变成一行巨型字符串，没法 review。第二是**能力**——「有工具时渲染工具列表、没工具时渲染兜底话术」这种条件渲染，还有把工具注册表铺开的循环渲染，字符串拼接根本写不出来；Jinja2 的 `{% if %}`、`{% for %}`、`{% extends %}` 直接覆盖。第三，也是最关键的一点——**模板边界就是缓存边界**。
> 前缀缓存只认逐字节相同的前缀，模板化让静态区、半静态区、动态区的分界变成显式的、可以审计的东西，我才能可靠地把「每轮都变」的分节推到 Prompt 末尾。不做模板化，这个分界藏在字符串拼接的执行路径里，缓存命中率是会飘的。"

> **追问：那模板化了，缓存命中率就能保证吗？**
> "不能，模板化只是让边界可见。真正决定命中率的是 **section 的排序**——原则是按变化频率降序：最不变的塞最前面。比如静态区放工具使用规则、安全策略，这部分跨用户都能命中；半静态区放用户偏好、记忆摘要，只在会话内命中，用 memoize 包起来，`/clear` 或 `/compact` 才重算；动态区放 MCP 指令这种每轮可能变的东西，函数名在 Claude Code 里直接叫 `DANGEROUS_uncachedSystemPromptSection`。
> 有个具体的坑：MCP 指令长在 Prompt 中段，它一变，**后面的全部 miss**——命中长度从 5300 掉到 4500，而且未命中部分是按全价计的。所以要么把它挪到末尾，要么把「每轮重算」改成「事件驱动重算」，本质上就是把它从 Uncached 降级成 Memoized。"

> **追问：PromptOps 和「把 Prompt 存 git」有什么区别？**
> "存 git 只是版本控制，是 PromptOps 四要素里的一条。完整的 PromptOps 是**把 Prompt 当接口管**：输入契约（模板变量 + 类型约束 + 必填校验，对应 API 请求参数）、输出约定（JSON Schema + 字段说明，对应响应格式）、错误处理（解析失败重试、降级、超时，对应错误码）、版本控制（语义化版本 + 变更日志 + 回滚，对应版本号）。
> 教学级 PromptOps 管的是版本和灰度；工业级管的是**缓存命中率和 token 成本**——观察指标从「质量评分」变成「缓存命中率监控 + token 消耗追踪」。"
