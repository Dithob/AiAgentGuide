## 一、开源 vs 闭源

| 维度 | 闭源 | 开源 |
| :--- | :--- | :--- |
| 代表 | GPT-4.1、Claude Sonnet 4.5、Gemini 2.5 Pro | Llama、DeepSeek、Qwen、GLM、Mistral |
| 优势 | 能力上限高、开箱即用、无需运维 | 数据不出境、可微调、无 API 依赖、成本低 |
| 劣势 | 数据出境风险、按量付费、不可微调 | 需自建推理服务、能力可能落后半代 |
| 适合 | 通用场景、快速迭代、多模态 | 敏感数据、私有化部署、深度定制 |

**选型五维度**

| 维度 | 判断 |
| :--- | :--- |
| 数据隐私 | 金融/医疗等敏感场景必须优先开源私有化 |
| 成本 | 高频调用开源长期更划算；低频闭源按量付费更省 |
| 能力上限 | 闭源在推理与工具调用上通常仍领先 |
| 可控性 | 需要微调/定制行为 → 开源 |
| 生态 | 闭源 API 更稳定；开源需自己维护推理服务 |

> 混合策略：**关键场景用闭源，辅助场景用开源**。

### 🔍 核实记录：Llama 4 那一行（2026-09-13 查证）

教程原文写的是「Llama 4 · Meta · 开源 · 10M · 2025.4 发布 · MoE 架构」。逐条核对 Meta 官方博客（`ai.meta.com/blog/llama-4-multimodal-intelligence`）：

| 教程说法 | 判定 | 说明 |
| :--- | :--- | :--- |
| Llama 4 / Meta | ✅ 真 | 确实存在，2025-04-05 发布 |
| 2025.4 发布 | ✅ 真 | 官方发布日期 2025-04-05 |
| MoE 架构 | ✅ 真 | Llama 系首次用 MoE |
| **10M 上下文** | ⚠️ **半真** | **10M 只是 Scout**；Maverick 是 **1M**。教程把整条产品线写成 10M，属错误泛化 |
| **开源** | ⚠️ **不严谨** | 准确说法是**开放权重（open weights）**，许可为 **Llama 4 Community License**，非 OSI 认证开源协议：MAU > 7 亿需单独授权；EU 的**多模态**能力受限制（纯文本路径可用） |

**两个补充事实（面试加分）**

1. **10M 是"标称值"**：独立测试显示 4-bit 量化超过约 5M Token 后困惑度上升 15~20%，有效窗口更接近 **5M**；Fiction.LiveBench 在 128K 长度上 Scout 只有 15.6%，而 Gemini 2.5 Pro 是 90.6%——**"大海捞针"式召回可以，跨段综合会崩**。
2. **Behemoth 没发**：发布时预告的 2T 级教师模型 Llama 4 Behemoth 始终未公开权重，后被搁置。所以"Llama 4"目前**只有 Scout 和 Maverick 两个可用变体**。

**另外一个坑**：Llama 4 发布时有过 LMArena 争议——Meta 提交榜单的是内部实验版（`Llama-4-Maverick-03-26-Experimental`），表现优于公开发布的版本。

## 三、Responses API：新一代 API 范式

2025 年 3 月 OpenAI 发布，**替代 Chat Completions API**，成为构建 Agent 的新标准接口。

| 变化 | Chat Completions | Responses API |
| :--- | :--- | :--- |
| 内置工具 | 自己实现 Function Calling 循环 | **原生内置** Web Search / Code Interpreter / File Search |
| 状态管理 | 客户端维护 `messages` 数组 | 服务端维护，用 `previous_response_id` 续接 |
| 流式 | 事件粒度粗 | 细分 `text.delta` / `tool_call` / `tool_output` 等事件类型 |
| 多模态 | Base64 编码传图 | `input` 参数直接传图片/文件 |

```python
# 旧：Chat Completions —— 需要手动循环：调 API → 检查 tool_calls → 执行工具 → 追加结果 → 再调 API
# 新：Responses API —— 一步到位
response = client.responses.create(
    model="gpt-4.1",
    input="北京天气怎么样？",
    tools=[{"type": "web_search_preview"}],   # 内置 Web Search
)
print(response.output_text)
```

**本质变化**：把"Agent 循环"从**客户端**搬到了**服务端**——这不是换个名字，是范式迁移。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 开源模型能力一定不如闭源 | 差距在缩小；很多场景已够用，且成本优势巨大 |
| 开源 = 免费可商用 | 要看具体许可（如 Llama 有月活限制） |
| "开放权重" = "开源" | **不是一回事**。开放权重只给权重，不给训练数据和训练代码，许可也非 OSI 认证（Llama 4 是 Community License）。面试里说"开放权重"比说"开源"准确 |
| 整个 Llama 4 都是 10M 上下文 | 10M 只有 **Scout**；Maverick 是 1M。别把产品线里某个变体的极值说成整条线 |
| 上下文窗口标称值 = 可用值 | 标称常有水分。Llama 4 Scout 标称 10M，实测有效约 5M，且长上下文**召回强、跨段综合弱** |
| 闭源一定更好 | 敏感数据/私有化场景开源是唯一解 |
| Responses API 只是改了个名 | 它把 Agent 循环服务端化，是范式变化 |
| 有了内置工具就不需要 Function Calling | 自定义工具仍需自己声明与执行 |

## 🎤 面试怎么答（口述模板）

> **问：开源和闭源模型怎么选？**
> "不是能力问题，是三个权衡：成本、隐私、可控性。如果业务涉及敏感数据必须私有化，那就只能选开源；如果是高频调用，开源长期更便宜，因为不用按 Token 付费；如果需要微调或深度定制行为，也只有开源能做。实际项目里我一般用混合策略——开发和原型阶段用闭源快速验证 Agent 逻辑，上线后切开源降本，好的框架像 LangGraph 支持改一行配置切模型。"

> **追问：那你怎么评估一个模型适不适合？**
> "三个维度：能力够不够用（在目标任务上准确率达标）、成本可不可控（单价乘预估调用量）、合规能不能过（数据能不能出境、要不要私有化）。"
