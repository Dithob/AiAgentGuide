## ⚡ TL;DR（先看这三行，下面正文是参考资料）

- **一句话**：调用顺序**由 LLM 自行推理、不需要硬编码**，代价是出错率 / 延迟 / 成本**三升**，外加 **token 递增**。
- **三要点**：①**token 递增**：每轮把上次消息追加进历史 → 越到后面每轮越贵，必须设 `max_loops` + token 预算上限；②**重试粒度**要对：重试单个工具调用，**不要重试整个 Agent 循环**；③灵活性是买来的，不是免费的。

## 🎯 30 秒结论

1. **多工具协作的调用顺序由 LLM 自行推理**（读工具 description + 用户意图），**不需要硬编码流程**。
2. 代价是**三升**：出错概率上升、延迟上升、成本上升——灵活性是买来的。
3. **token 递增现象**：每轮把上次消息追加进历史 → `prompt_tokens` 逐轮增长 → **越到后面每轮越贵**。
4. 所以必须设 **`max_loops` + token 预算上限**。
5. 重试的**粒度**要对：**重试单个工具调用，不要重试整个 Agent 循环**（否则成功的工具白跑）。

## ❓ 你的疑问解答

> **你在记录区写的疑问**：多工具协作无需硬编码流程 这个是不是不太严谨，按理说多工具肯定会写代码加以控制的。

**你的直觉是对的，而且抓得很准。** 这句话之所以别扭，是因为它把两件事混在了一句里。拆开就成立了：

| 问题 | 由谁决定 | 是不是"硬编码" |
| :--- | :--- | :--- |
| **调哪个工具、按什么顺序、要不要继续** | **LLM 推理**（读 description + 意图） | ❌ 动态编排——这正是 Agent 区别于工作流的地方 |
| **工具本身怎么实现、怎么注册** | 代码 | ✅ 全是硬编码 |
| **参数怎么校验、类型对不对** | 代码（+ Schema 约束） | ✅ 硬编码 |
| **权限判定、沙箱、危险操作拦截** | 代码 | ✅ 硬编码 |
| **循环上限、超时、token 预算** | 代码 | ✅ 硬编码 |
| **异常重试、降级** | 代码 | ✅ 硬编码 |

**所以更严谨的表述是**：

> **执行路径由 LLM 动态编排（软控制）；边界、预算、权限、安全由代码硬约束（硬控制）。**
> 选择题说的"无需硬编码流程"，指的只是**前者**。

**而且你的判断在工业界是成立的**——真实系统会在外层加越来越多硬控制：

| 硬控制手段 | 作用 |
| :--- | :--- |
| 工具白名单 / 工具路由 | 只把本次任务相关的工具交给模型，减少选错 |
| 强制流程骨架 | 关键路径用**状态机**固定（这正是第 18 章 LangGraph 的价值：把软编排收敛成硬流程） |
| 人工确认卡点 | 不可逆操作强制拦截（见条目 12） |
| 预算熔断 | `max_loops` / token 上限 / 超时 |

**结论**：选择题那句话作为"考点"没错（它想强调"顺序不是代码写死的"），但作为"工程描述"不完整。**能指出这一点，就是面试里比背题的人强的地方。**

## 一、多工具协作：收益与代价

| | 单工具 Agent | 多工具 Agent |
| :--- | :--- | :--- |
| 编排方式 | 基本只有一条路 | **AI 自行推理顺序** |
| 灵活性 | 低 | **高**（能根据上下文调整） |
| 出错概率 | 低 | **↑**（选错工具、顺序错、参数错） |
| 延迟 | 低 | **↑**（串行多轮） |
| 成本 | 低 | **↑**（轮数 × 递增的 prompt） |
| 适用 | 确定性任务 | **不确定性高的任务** |

> ⚠️ 别被"AI 自主编排"迷住：**在确定性任务上，硬编码流程又快又稳又便宜**。Agent 的优势是灵活性，不是速度。

---

## 二、token 递增现象（成本黑洞）

**原因**：每轮循环都 `messages.append(...)`，而**每一轮都要把整个 history 重新发一遍**。

```
第 1 轮  prompt ≈ 200   （system + 用户问题 + 工具 Schema）
第 2 轮  prompt ≈ 600   （+ 上一轮 assistant 的 tool_calls + tool 结果）
第 3 轮  prompt ≈ 1000  （+ 又一轮）
...
第 N 轮  prompt ≈ 前 N-1 轮总和的累积
```

**两个后果**

| 后果 | 说明 |
| :--- | :--- |
| **单轮成本越往后越高** | 不是线性，是**累积增长** |
| **总成本 ≈ 轮数的平方级** | 5 轮任务的总 prompt ≈ 1+2+3+4+5 倍于单轮 |

**对策**

| 对策 | 做法 |
| :--- | :--- |
| 硬上限 | `MAX_AGENT_LOOPS`、token 预算 |
| 上下文裁剪 | 只保留最近 N 轮；裁剪时**始终保留 system 消息** |
| 工具结果压缩 | 过长的工具返回先截断/摘要再回填 |
| 前缀缓存 | 固定前缀（system + 工具 Schema）放最前，吃 Prompt Cache（见条目 02） |
| 可观测 | 记录每轮 prompt/completion token，才能发现异常（见下） |

> 你的 `4-code/first_agent/TODO` 里第二优先级列的就是这套上下文控制方案，方向完全正确。

## 三、调用链分析（可观测性）

**调用链 = 一次用户请求内，所有模型调用 + 工具调用的完整记录。** 没有它，成本问题就是黑盒。

你的 `AgentTracer` 记录了什么，为什么这么设计：

| 字段 | 用途 |
| :--- | :--- |
| `loop` / `has_tool_call` | 区分"🔧 工具调用轮"和"💬 最终回答轮" |
| `prompt_tokens` / `completion_tokens` | **用来看递增现象**——这是最关键的字段 |
| `time_seconds` | 每轮延迟，定位慢在哪一步 |
| `tool_calls` | 调了哪些工具，判断是否选错 |
| `prompt_cache_hit_tokens` / `miss` | 缓存命中情况，直接决定成本 |

**"关键发现"的正确读法**：把每轮 `prompt_tokens` 列出来，你会看到它**单调递增**——这不是 bug，是 Agent 结构的必然。所以预算要按"总轮数"而不是"单轮"来估。

## 四、重试粒度：只重试失败的工具

> 教程思考题：一个 Agent 同时调天气 API 和路线 API，天气超时了但路线成功。如果直接重试整个循环，路线结果就浪费了。怎么只重试失败的工具？

**答案：把重试放在"工具层"，不要放在"Agent 循环层"。**

| 错误做法 | 正确做法 |
| :--- | :--- |
| 把整个 `for tool_call in msg.tool_calls:` 包进 `try/except` 重试 | **在 `execute_tool_with_retry(func_name, args)` 里重试**——粒度是单个 `tool_call` |
| 失败的循环整体重跑 | 失败工具返回 error 结果**照常回填**；成功的工具结果已经在 `messages` 里，模型下一轮直接复用 |

**三层好处**

1. 已成功的工具**不会重复执行**（尤其对有副作用/要花钱的工具至关重要）。
2. 失败信息也变成"观察"，模型下一轮可以**改参数重试 / 换工具 / 告诉用户**。
3. 重试次数按工具独立计，不会因为一个工具拖垮整轮。

**加分点**：对有副作用的工具，还可以给 `tool_call` 加**幂等键 / 结果缓存**，防止"重试"变成"重复下单"。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 多工具协作完全不需要代码控制 | **顺序**由 LLM 定，但**边界/预算/权限/重试**全是代码硬控制 |
| 多工具一直更好 | 确定性任务上硬编码更快更稳更便宜 |
| 多工具只增加延迟，不增加出错概率 | **出错概率也上升**（这是选择题里最容易漏的一点） |
| token 递增是因为模型变啰嗦 | 是**历史被反复重发**导致的累积，跟模型输出无关 |
| 出错就重试整个 Agent 循环 | 应**只重试失败的那个工具调用**，否则浪费已成功的结果 |
| 成本按"单轮 token × 轮数"估 | 实际是**累积增长**，要按总轮数带来的累积量估 |

## 🎤 面试怎么答（口述模板）

> **问：多工具协作是怎么编排的？有什么代价？**
> "调用顺序不需要硬编码——LLM 读每个工具的 description，结合用户意图自己推理出先调谁后调谁，中间还能根据观察结果调整。但这里要说清一点：**'不硬编码'指的是执行路径的动态编排，不是整个系统没有代码约束**。工具的注册、参数校验、权限判定、循环上限、异常重试，这些全是代码在硬控制。生产系统还会用状态机把关键路径固定下来，牺牲灵活性换确定性。
> 代价是**三升**：出错概率上升、延迟上升、成本上升。成本这块有个特有意思的现象叫 **token 递增**——每轮循环都要把整个历史重发一遍，所以 prompt_tokens 是逐轮累积的，总成本接近轮数的平方级。所以必须设 max_loops 和 token 预算。"

> **追问：一个任务里两个工具，一个成功一个超时，你会怎么重试？**
> "我会把重试放在**工具层**，而不是 Agent 循环层——也就是 `execute_tool_with_retry` 这种粒度是单个 tool_call。失败的返回 error 结果照常回填给模型，成功的那个结果已经在历史里了，模型下一轮直接复用，不会重复跑。这样既没浪费，也让模型有机会自己决定是改参数重试还是换方案。"
