## 🎯 30 秒结论

1. **Schema 里最重要的是 `description`**——AI 靠它判断"要不要调这个工具"，`name` 只是标识。
2. `required` 告诉 AI 哪些参数**必须**给；类型写错会直接导致调用失败。
3. 异常分两类：**临时性故障**（超时/限流/503）可重试；**逻辑性错误**（参数错/权限不足）**再试也一样**。
4. 三种处理策略：**重试** / **优雅降级** / **让 AI 知道**（把错误信息告诉模型，让它决定下一步）。
5. 重试用**指数退避**（1s → 2s → 4s），生产环境还要加 **jitter** 防雪崩。

**§3.8 三种异常处理策略**

> - **重试**：对于临时性故障（超时、限流），重试可能成功
> - **优雅降级**：对于不可恢复的故障，返回有意义的提示，而不是崩溃
> - **让 AI 知道**：把错误信息告诉 AI，让 AI 自己决定下一步（换工具？改参数？道歉？）

你摘录的「重试 vs 降级」决策表：

| 异常类型 | 能否重试 | 策略 | 示例 |
| :--- | :--- | :--- | :--- |
| `TimeoutError` | ✅ 可以 | 指数退避重试 | API 超时、网络抖动 |
| `429 Rate Limit` | ✅ 可以 | 指数退避 + jitter | 请求过多被限流 |
| `503 Service Unavailable` | ✅ 可以 | 指数退避重试 | 服务临时不可用 |
| `TypeError`（参数错误） | ❌ 不行 | 告诉 AI 调整参数 | 传了 int 给 string 参数 |
| `JSONDecodeError` | ❌ 不行 | 告诉 AI 参数无效 | AI 生成了非法 JSON |
| `KeyError`（数据不存在） | ❌ 不行 | 降级返回提示 | 查询不存在的城市 |
| `PermissionError` | ❌ 不行 | 降级返回提示 | 没有权限访问某资源 |

> **核心判断原则**（你抄下来的这句就是标准答案）：**可重试 = 临时性故障（可能自己恢复），不可重试 = 逻辑性错误（再试也一样）。**

**==Q2: 工具 Schema 中最重要的字段是什么？==**

> **description**。AI 靠它判断是否调用工具，写得越具体越准确。name 只是标识，parameters 决定怎么调用，但 AI 首先靠 description 决定"要不要调"。

## 一、Schema 设计四原则

| 原则 | 反例 → 正例 |
| :--- | :--- |
| **description 高信号低噪声** | ❌"获取信息" → ✅"查询指定城市指定日期的天气信息，包括天气状况和温度" |
| **类型和 required 明确** | `city` 必填就放 `required`；`date` 可选就写 `default` |
| **函数名有语义** | ❌`func1` → ✅`get_weather`、`plan_trip` |
| **Schema 简洁精准** | ❌ 参数堆到 20 个 → ✅ 只留模型真正需要判断的字段 |

> ⚠️ **description 决定工具被"选中"的概率**。写得好，AI 就聪明；写得差，AI 就困惑——这是工具设计的第一号坑。

### `parameters` 三个关键子字段

| 字段 | 作用 | 写错会怎样 |
| :--- | :--- | :--- |
| `type` | 参数类型（string/integer…） | AI 可能传错类型 → `TypeError` |
| `description` | 参数含义 + 示例 | AI 猜不出该填什么 |
| `required` | 哪些必填 | 漏了必填项 → 调用失败 |

## 二、重试机制：指数退避

```python
for attempt in range(max_retries + 1):
    try:
        return call_tool(...)
    except TimeoutError:
        if attempt < max_retries:
            wait_time = 2 ** attempt      # 1s → 2s → 4s
            time.sleep(wait_time)
        else:
            return {"error": "服务暂时不可用，已重试 N 次，建议稍后再试"}
```

**为什么是"指数"而不是"固定间隔"**

| 策略 | 问题 |
| :--- | :--- |
| 失败后立即重试 | 服务没恢复，等于白打，还可能加重负担 |
| 固定间隔（如都等 1s） | 大量客户端会同时重试 → **惊群 / 雪崩** |
| **指数退避（2^n）** | 给服务恢复时间，同时指数级拉开重试密度 |
| **指数退避 + jitter（随机抖动）** | 进一步打散重试时刻，生产环境标配 |

## 三、三种策略怎么选（决策流程）

```
工具调用
   ├─ 成功 ──▶ 返回结果
   └─ 异常 ──▶ 是临时性故障吗？
                ├─ 是（Timeout / 429 / 503）──▶ 指数退避重试
                │                                   └─ 重试次数耗尽 ──▶ 优雅降级
                └─ 否（参数错 / 无权限 / 数据不存在）──▶ 把错误信息告诉 AI
                                                        （让 AI 换工具 / 改参数 / 道歉）
```

**"让 AI 知道"为什么是关键设计**

> 不要自己吞掉错误。把 `{"error": "...", "expected_params": "..."}` 作为**观察结果**回填给模型，
> 模型下一轮就有机会自己修正——这是 Agent 容错能力的来源，也是"观察"这一步的真正价值。

| 做法 | 位置 | 要点 |
| :--- | :--- | :--- |
| 兜底所有未预期异常 | `except Exception` | 降级返回通用提示，**不暴露内部细节**（防信息泄露） |

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| Schema 里 `name` 最重要 | **`description` 最重要**——它决定 AI 要不要调 |
| Schema 越复杂越好 | 越简洁精准越好；字段太多会干扰模型判断 |
| 所有错误都重试 | 逻辑性错误（参数错/权限不足）重试永远一样，应**告诉 AI 或降级** |
| 重试间隔固定即可 | 固定间隔会引发惊群，用**指数退避 + jitter** |
| 工具报错直接抛异常让它崩 | 应捕获后**作为观察结果告诉 AI**，让 AI 决定下一步 |
| 错误信息越详细越好 | 对外降级提示**不要暴露内部细节**（异常栈、路径） |

## 🎤 面试怎么答（口述模板）

> **问：工具 Schema 里哪个字段最重要？**
> "`description`。AI 是**靠 description 判断要不要调这个工具**的——`name` 只是标识符，`parameters` 决定怎么调，但第一步的'要不要调'完全由 description 决定。所以写工具的时候，description 要具体到能区分场景，比如'查询指定城市指定日期的天气信息'，而不是泛泛的'获取信息'。写得含糊，模型就会选错工具或者该调不调。"

> **追问：工具调用失败了怎么处理？**
> "先分类。**临时性故障**——超时、限流、503——用指数退避重试，1 秒 2 秒 4 秒，生产环境还要加随机 jitter 防止惊群。**逻辑性错误**——参数类型错、没权限、数据不存在——重试没用，要么降级返回有意义的提示，要么**把错误信息作为观察结果回填给模型**，让它自己决定换工具、改参数还是跟用户道歉。核心判断就是一句话：可重试 = 临时性故障，不可重试 = 逻辑性错误。"
