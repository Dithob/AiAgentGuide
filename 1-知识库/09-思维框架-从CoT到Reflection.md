# 09 · 思维框架：从 CoT 到 Reflection

## 🎯 30 秒结论

1. 四种框架是**递进关系**，不是互斥选项：每一层在前一层上加一种能力。
2. 递进链：**CoT（推理）→ ReAct（+行动）→ Plan & Execute（+全局规划）→ Reflection（+自我审查）**。
3. **框架不是越复杂越好，而是越匹配越好**：纯推理用 CoT 就够，要工具才上 ReAct，探索型才用 ToT。
4. 消耗随复杂度递增：CoT 低 → ReAct / Plan&Execute 中 → Reflection 高。
5. ReAct 能处理 CoT 处理不了的任务（需要实时数据/外部计算），代价是 Token 与延迟更高。

**==Q12：CoT、ReAct、ToT 三种思维框架的递进关系是什么？==**

> 递进关系：① **CoT**（纯推理）——学会一步步思考，适合数学、逻辑推理；② **ReAct**（推理+行动）——在 CoT 上加了工具调用，边想边做；③ **ToT**（推理+行动+探索）——在 ReAct 上加了多路径探索和回溯，适合复杂规划。此外还有 **Reflection**（反思）机制——自我审查并修正输出。框架不是越复杂越好，而是越匹配任务越好。详细内容见第 6 章「ReAct：让 Agent 学会思考」。

## 🔆 强化延伸（你标了 `==` 的 Q12）

### 把"递进"讲成一张能力叠加表

面试官问"递进关系"，本质是在问：**每往上一层，多出来的是哪一种能力？** 答不出"多什么"，就只是在背顺序。

| 框架 | 在前一层上加的能力 | 典型推理形态 | 一句话标志 |
| :--- | :--- | :--- | :--- |
| **CoT** | —（起点：把答案拆成中间步骤） | 思考 → 思考 → 答案 | "一步步想" |
| **ReAct** | **+ 行动**（工具调用，能接触外部世界） | 思考 → 行动 → 观察 → 思考… | "边想边做" |
| **ToT** | **+ 探索**（多路径展开 + 回溯剪枝） | 分叉 → 评估 → 回退 → 再分叉 | "多想几条路，挑最好的" |
| **Plan & Execute** | **+ 全局规划**（先出完整计划再执行） | 规划 → 逐步执行 | "先画图纸再施工" |
| **Reflection** | **+ 自我审查**（生成后批判并修正） | 生成 → 批判 → 重写 | "写完再改一遍" |

> ⚠️ 教程里同时出现过 **"四种"（CoT/ReAct/Plan&Execute/Reflection）** 和 **"CoT→ReAct→ToT"** 两套列举，**不要背成互斥的**。统一记法：
> **主干是 CoT → ReAct → ToT（能力逐层叠加：推理 → +行动 → +探索）；Plan & Execute 和 Reflection 是"可插拔的增强模块"**——前者加在 ReAct 之前（先规划），后者加在 ReAct 之后（再审查）。

### 选择决策树（口述版）

```
需要外部信息/精确计算吗？
├── 不需要 ──▶ 任务有确定答案吗？
│              ├── 有 ──▶ CoT（要更稳就 Self-Consistency 多次投票）
│              └── 没有（开放创作）──▶ 直接答 / 少量 Few-Shot
└── 需要 ──▶ 步骤多且互相依赖吗？
             ├── 不多，走一步看一步即可 ──▶ ReAct
             └── 多且依赖强 ──▶ Plan & Execute
                      │
        （解空间大、需要试错回溯？──▶ 换 ToT：规划 / 博弈 / 创意搜索）
        （输出质量比成本重要？──▶ 叠一层 Reflection）
```

### 三个必须能答的追问

| 追问 | 要点 |
| :--- | :--- |
| **ReAct 的失败模式有哪些？** | ①工具选错（工具描述含糊）②陷入循环（重复同一动作）③误读观察结果 ④Token 爆炸（每轮都要重发历史） |
| **ToT 的代价是什么？** | 分支数 × 深度 的指数级增长，Token 和延迟都难控。真实项目里常用"**浅 ToT**"——只展开 2~3 条分支，不做全树搜索 |
| **什么时候不该用这些框架？** | 流程确定、步骤可枚举的任务——直接用工作流引擎/状态机，比任何思维框架都便宜可靠 |

**自测（3 道）**

- [ ] ReAct 相比 CoT 多出来的核心能力是什么？→ **行动（工具调用）**，使它能获取外部信息/执行操作。
- [ ] ToT 相比 ReAct 多出来的是什么？→ **多路径探索 + 回溯**（不是"更多工具"）。
- [ ] 判断：框架越复杂效果越好。→ 错。**越匹配越好**；复杂框架在简单任务上更贵更慢，还会引入新的失败模式。

## 一、四种框架对比

| 框架 | 一句话 | 做什么 | 消耗 |
| :--- | :--- | :--- | :--- |
| **CoT** 思维链 | 逐步推理 | 纯思考，不行动 | 低 |
| **ReAct** | 推理 + 行动 | 思考 → 调工具 → 观察，边想边做 | 中 |
| **Plan & Execute** | 先计划后执行 | 全局规划，有序执行 | 中 |
| **Reflection** 反思 | 自我审查 | 先生成，再检查修正 | 高 |
| **ToT** 思维树 | 多路径探索 | 探索多条推理路径取最优（CoT/ReAct 的进阶变体） | 高 |

---

## 二、递进关系

```
CoT ──加"行动"──▶ ReAct ──加"全局规划"──▶ Plan & Execute ──加"自我审查"──▶ Reflection
 │
 └──加"多路径探索+回溯"──▶ ToT（探索型任务的进阶变体）
```

| 进阶 | 新增的能力 | 解决的问题 |
| :--- | :--- | :--- |
| CoT → ReAct | 行动（工具调用） | CoT 无法与外部世界交互：需要实时数据/精确计算时无能为力 |
| ReAct → Plan & Execute | 全局规划 | ReAct 是"走一步看一步"，多步任务可能反复绕路 |
| Plan & Execute → Reflection | 自我审查 | 生成一次就交付，缺少质量把关 |
| CoT → ToT | 多路径探索 + 回溯 | 单一推理链可能走死胡同 |

> 教程在 §1.8 里同时出现过"四种框架"和"CoT→ReAct→ToT"两种列举，**按四种记，ToT 视为 CoT 的进阶变体**。

## 三、选择原则（面试常问）

| 任务特征 | 选什么 | 理由 |
| :--- | :--- | :--- |
| 数学题、逻辑推理，不需要外部信息 | **CoT** | 纯推理，最省 |
| 需要查实时数据 / 调 API / 执行代码 | **ReAct** | 必须能行动 |
| 任务长、步骤多且互相依赖 | **Plan & Execute** | 全局规划避免绕路 |
| 输出质量要求高、可承受多次调用 | **Reflection** | 用成本换质量 |
| 解空间大、需要试错（规划/博弈/创意） | **ToT** | 多路径探索 + 回溯 |
| 什么框架都不用 | 固定流程任务 | 用工作流引擎，别用 Agent |

## 四、为什么 CoT 有效 / ReAct 为什么更强

| 框架 | 有效的原因 | 边界 |
| :--- | :--- | :--- |
| CoT | ①扩展推理空间（每步为下一步提供更多上下文）②减少错误传播（中间步骤可自检） | 无法获取外部信息、无法执行动作 |
| ReAct | 在推理链中插入 Action，把工具返回的 Observation 作为新的推理输入 | Token 消耗更多、延迟更高、实现更复杂；**依赖工具质量与工具描述** |
| Reflection | 对已有输出做批判性检查，捕捉一次生成的疏漏 | 成本高；若模型自身能力不足，反思也可能"自我强化错误" |

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 四种框架必须选一个、互斥 | 是**递进**关系，生产里常组合使用 |
| 框架越复杂效果越好 | 越匹配越好；简单任务上复杂框架可能更差（还会多花钱） |
| CoT 能解决需要实时数据的问题 | 不能。CoT 不与外部世界交互，那需要 ReAct 的 Action |
| ReAct 一定比 CoT 好 | 不需要工具的任务上，ReAct 只是更贵更慢 |
| Reflection 总是能纠错 | 如果模型自身判断力不足，反思可能固化错误 |

## 🎤 面试怎么答（口述模板）

> **问：CoT、ReAct、ToT 的递进关系是什么？**
> "它们是给模型逐步加能力。CoT 只让模型一步步推理，适合数学逻辑这类纯思考任务，但它不能和外部世界交互。ReAct 在 CoT 上加了'行动'——推理和工具调用交替，所以需要实时数据或者精确计算的任务它能做，CoT 做不了。再往上，Plan and Execute 是对多步任务先做全局规划，避免走一步看一步反复绕路；Reflection 是生成之后再自我审查，用成本换质量。ToT 则是多路径探索加回溯，适合解空间大的规划类问题。核心原则是**越匹配越好，不是越复杂越好**。"

> **追问：那你怎么选？**
> "先看任务需不需要外部信息——不需要就用 CoT，最省。需要就上 ReAct。再看步骤是不是长且互相依赖，是的话先规划。如果输出质量比成本重要，再加 Reflection。"
