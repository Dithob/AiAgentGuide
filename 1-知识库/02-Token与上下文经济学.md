## 🎯 30 秒结论

1. **Token 是最小单位**，由 Tokenizer 按 BPE 切分，≠ 字 ≠ 词。英文 ≈ 字符/4，中文 ≈ 字符/2。
2. **中文比英文贵 1.5~2 倍**，因为词表以英文为核心——这是词表偏置，不是模型歧视。
3. **输出 Token 比输入贵 3~4 倍**（输入是"读"，输出是"逐 Token 生成"）→ 控制输出长度比压输入更省钱。
4. **窗口大 ≠ 理解强**，存在 Lost in the Middle：中段信息注意力显著下降。
5. **Prompt Cache 靠"前缀完全相同"命中**，所以：固定内容放最前、动态内容放最后。

**ch00 Q7：什么是上下文窗口？窗口满了怎么处理？**

> 上下文窗口是模型一次能处理的最大 Token 数量（输入+输出）。窗口满了有四种处理策略：①**截断策略**——保留最新的消息，截断最早的历史；②**摘要策略**——用 LLM 把旧对话压缩成摘要，释放空间；③**向量检索策略**——将历史对话存入向量库，按需检索相关片段注入；④**滑动窗口**——维护固定长度的对话窗口，旧消息自动移出。Agent 系统通常组合使用摘要 + 向量检索。

**ch01 🎯 Prompt Cache：如何更有效命中缓存**

> OpenAI 的 **Prompt Caching**（前缀缓存）机制：当多个请求的 Prompt 前缀相同时，系统会缓存前缀的 KV 计算结果，后续请求只需计算新增部分。缓存命中的 Token 价格约为正常的 **50%**。
> 缓存命中条件：**前缀完全相同**。任何一字之差都会导致缓存失效，从零开始计算。所以设计的关键是**把不变的放前面，变化的放后面**。

你摘录的「✅ 正确顺序」原文：

```text
System Prompt（角色+规则）        ← 🔒每次相同，缓存100%命中
工具Schema（Function定义）      ← 🔒每次相同，缓存100%命中
Skill触发词（available_skills）  ← ⚠️同会话内相同，缓存命中
记忆注入（长期记忆片段）        ← ❌每轮可能不同，不命中
对话历史（多轮记录）            ← ❌逐轮增长，旧部分可命中
用户当前输入                    ← 每次不同，不命中
```

> ⚠️ **本篇是你的错题集中区**：你在「上下文窗口 128K 的 Token 分配」（多选）上把 **B 对话历史**、**D 记忆召回** 也选成了"固定不变可缓存"（`~~ACD~~ AC`）。根因是没把"固定 / 半固定 / 动态"三层分清——见下面「三、128K 窗口的 Token 分配」和「🔆 错题根治」。

### 🔆 错题根治：一眼分清"能不能缓存"

判断某个内容能否命中前缀缓存，只问一句话：**它在这次请求里，和上次请求的对应位置是不是逐字节相同？**

| 层 | 内容 | 变化频率 | 能否缓存 | 记忆钩子 |
| :--- | :--- | :--- | :--- | :--- |
| **固定层** | System Prompt、工具 Schema | 整个会话不变 | ✅ 100% 命中 | "会话内一个字节都不动" |
| **半固定层** | Skill 触发词列表、会话级配置 | 同会话内基本不变 | ⚠️ 多轮后开始命中 | "同会话内稳定" |
| **动态层** | **对话历史**、**记忆召回片段**、**工具返回结果**、**用户当前输入** | **每轮都变** | ❌ 不命中 | "每轮都要重写" |

**记法**：`System + 工具 Schema` 是"印在纸上的"，`对话历史 + 记忆召回` 是"每轮新写的"。**只有印在纸上的能缓存。**

- 对话历史为什么不行？→ **逐轮增长**，前缀一直在变。
- 记忆召回为什么不行？→ **按需检索**，每轮召回的片段可能完全不同，插在中间会把后面所有内容的前缀全部打断。

> ✅ 一句话答案（可背）：**System Prompt 和工具 Schema 整个会话内不变，放在 Prompt 前缀处可 100% 命中缓存；对话历史逐轮增长不可缓存，记忆召回每轮可能变化不可缓存。**

## 一、Token 是什么

| 项 | 说明 |
| :--- | :--- |
| 定义 | LLM 处理文本的最小度量单位 |
| 切分方式 | Tokenizer 按 **BPE（Byte Pair Encoding）** 自动切分 |
| 粒度 | 介于"字"和"词"之间，由**词表**决定；不同模型词表不同 → 同一句话 Token 数不同 |
| 计费单位 | 按 Token 计费，**不按字符** |

**BPE 直觉**：从单个字符开始，反复把出现频率最高的相邻符号对合并成一个新符号，直到达到目标词表大小。所以高频词/常见搭配会变成一个 Token。

**估算公式**

```
Token 数 ≈ 字符数 ÷ 4   （英文）
Token 数 ≈ 字符数 ÷ 2   （中文）
```

---

## 二、中英文 Token 密度

| 文本 | 字符数 | GPT-4.1 Token 数 | 每字符 Token 比 |
| :--- | --: | --: | --: |
| Hello World | 11 | 2 | 0.18 |
| The quick brown fox jumps | 25 | 5 | 0.20 |
| 你好世界 | 4 | 4~6 | 1.0~1.5 |
| 我爱学习人工智能 | 8 | 8~12 | 1.0~1.5 |
| 人工智能是未来（含标点） | 9 | 10~14 | 1.1~1.6 |

**结论**：英文 1 词 ≈ 1~1.3 Token；中文 1 字 ≈ 1.5~2 Token。同样长度内容，中文成本约为英文的 **1.5~2 倍**，且更占上下文窗口。

**缓解手段**：用中文优化模型（Qwen / GLM）；缓存固定前缀；约束输出格式。

## 三、上下文窗口

**定义**：模型一次能"看到"的最大 Token 数（**输入 + 输出**）。超出会被截断或需特殊处理。

| 模型 | 上下文窗口 | 约等于中文字数 |
| :--- | :--- | :--- |
| GPT-4.1 / GPT-4.1-mini | 1M | ~670K 字 |
| Claude Sonnet 4.5 | 200K（可扩 1M） | ~130K 字 |
| Gemini 2.5 Pro | 1M | ~670K 字 |
| DeepSeek-V3 | 128K | ~85K 字 |
| Qwen 2.5 | 128K | ~85K 字 |

> 注：教程不同表格里 Gemini 2.5 Pro 写过 1M 和 2M 两个值，以官方文档为准。

**窗口越大越好的三个反例**

| 反例 | 说明 |
| :--- | :--- |
| 成本线性增长 | 每次请求都要为全部输入付费 |
| **Lost in the Middle** | 模型对上下文中段的信息注意力显著下降 |
| 延迟上升 | 输入越长，首 Token 延迟越高 |

**窗口满了怎么办（四种策略）**

| 策略 | 做法 | 代价 |
| :--- | :--- | :--- |
| 截断 | 保留最新消息，丢掉最早的 | 丢历史，可能丢关键上下文 |
| 摘要 | 用 LLM 把旧对话压成摘要 | 一次额外 LLM 调用，有信息损失 |
| 向量检索召回 | 历史入向量库，按需检索注入 | 要维护向量库，检索有延迟 |
| 滑动窗口 | 固定长度窗口，旧消息自动移出 | 简单，但同样丢历史 |

> 生产实践：**摘要 + 向量检索组合**。

## 四、计费模型

### 4.1 Input vs Output

| 模型 | Input ($/M) | Output ($/M) | 倍数 |
| :--- | --: | --: | --: |
| GPT-4.1 | $2.00 | $8.00 | 4x |
| GPT-4.1-mini | $0.40 | $1.60 | 4x |
| Claude Sonnet 4.5 | $3.00 | $15.00 | 5x |
| Gemini 2.5 Pro | $1.25 | $10.00 | 8x |
| DeepSeek-V3 | $0.27 | $1.10 | 4x |
| Qwen 2.5（开源） | $0.15 | $0.60 | 4x |

```
总成本 = 输入Token × 输入单价 + 输出Token × 输出单价
```

### 4.2 五条计费规则

| # | 规则 | 说明 |
| :-- | :--- | :--- |
| 1 | 输入输出分别计费 | 输出通常贵 3~5 倍 |
| 2 | 缓存 Token 有折扣 | 命中缓存的输入 Token 约半价 |
| 3 | 按 Token 不按字符 | 同样 1000 字符，中文更贵 |
| 4 | 工具调用 Token 也累积 | 返回的 JSON 参数算输出，工具结果算下一轮输入 |
| 5 | **流式输出不省钱** | Streaming 只改观感，Token 总数与费用完全相同 |

### 4.3 成本估算锚点（面试直接背）

| 场景 | Token 量 | GPT-4.1 成本 |
| :--- | :--- | :--- |
| 简单问答（1 轮） | ~500 | $0.003 |
| 代码解释 | ~4.5K | $0.023 |
| 代码修改 | ~12K | $0.060 |
| 复杂开发（5 轮工具调用） | ~65K | $0.275 |
| 全项目重构（20 轮+） | ~260K | $1.100 |

**代码行 → Token**：Python ≈ 15 Token/行，Java ≈ 25 Token/行，中文注释 ≈ 20 Token/行。
1000 行 Python ≈ 15K Token ≈ $0.03（输入）；若让模型**生成** 1000 行，输出成本约 $0.15（4 倍）。

### 4.4 Token 优化四招

量化固定 → 缩短输出 → 缓存复用 → 分段处理

| 招 | 做法 | 效果 |
| :--- | :--- | :--- |
| 压缩 Prompt | 去掉冗余描述，用精炼指令 | 示例中省约 80% 输入 Token |
| 缩短输出 | 要求只输出关键信息、约束结构化格式 | 输出比输入贵，收益更大 |
| 缓存复用 | 固定前缀复用 Prompt Caching | 输入成本省 50%+ |
| 分段处理 | 长文档分块处理，避免一次塞满 | 规避窗口与中段遗忘 |

## 五、上下文窗口的 Token 预算与缓存设计

### 5.1 128K 窗口的典型分配

| 组成部分 | 典型 Token | 占比 | 性质 | 缓存友好度 |
| :--- | :--- | :--- | :--- | :--- |
| System Prompt（角色+规则） | 500~2,000 | 0.4~1.6% | 🔒 固定 | ✅ 最易命中 |
| 工具 Schema | 1,000~5,000 | 0.8~4% | 🔒 固定 | ✅ 最易命中 |
| Skill 触发词列表 | 500~3,000 | 0.4~2.3% | ⚠️ 缓慢变化 | ⚠️ 多轮后命中 |
| 记忆注入（长期记忆召回） | 1,000~5,000 | 0.8~4% | ⚠️ 按需动态 | ❌ 不可缓存 |
| 对话历史 | 5,000~50,000+ | 4~39% | 🔄 逐轮增长 | ❌ 新内容不可缓存 |
| 工具返回结果 | 2,000~20,000 | 1.6~16% | 🔄 每轮新增 | ❌ 不可缓存 |
| 模型输出预留 | 剩余 | **30~50%** | 📝 生成用 | — |

**关键发现**：固定部分只占 **2~8%**，但**每次请求都要重发**——所以缓存命中这部分收益极大。

### 5.2 缓存友好结构（核心考点）

```
✅ 正确顺序（命中率最大化）
  System Prompt（角色+规则）      ← 🔒 每轮相同，100% 命中
  工具 Schema（Function 定义）    ← 🔒 每轮相同，100% 命中
  Skill 触发词（available_skills）← ⚠️ 同会话内相同
  记忆注入（长期记忆片段）        ← ❌ 每轮可能变
  对话历史（多轮记录）            ← ❌ 逐轮增长（旧部分可命中）
  用户当前输入                    ← ❌ 每次都不同

❌ 错误顺序
  用户输入 → 对话历史 → 工具 Schema → System Prompt
  （前缀从第一个 Token 就变了，缓存全部失效）
```

**三条缓存设计准则**

1. **固定前缀放最前** —— System Prompt + 工具 Schema + Skill 描述放开头。
2. **动态内容放最后** —— 对话历史、记忆召回、用户输入。
3. **合并固定层** —— 把 System Prompt 和工具定义合并成**一条 system 消息**，增加前缀连续性；OpenAI 要求**至少 5 条消息**才触发缓存，合并后更容易达标。

**命中率直觉**：固定 2K + 半固定 2K + 10 轮对话 8K + 当前 500
→ 第 5 轮命中 ≈ 50%；第 10 轮命中 ≈ 70%。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 中文一个字固定 3 个 Token | 那是 UTF-8 字节数。实际 1~2 个，由词表决定 |
| 流式输出更省钱 | Token 与费用与非流式完全相同 |
| 上下文窗口越大越好 | 成本线性涨、中段遗忘、延迟升高 |
| 窗口内的信息模型一定能记住 | Lost in the Middle：中段最容易被忽略 |
| 压缩输入是省钱重点 | 输出贵 3~4 倍，**约束输出更有效** |
| 缓存折扣只有一个数字 | 两种口径要分清（见下方专题） |

### ❗ 缓存折扣的两种口径（教程内部不一致，务必分清）

| 口径 | 数字 | 出处 | 含义 |
| :--- | :--- | :--- | :--- |
| 单价口径 | 约 **50%** | §1.1 正文、计费规则五条 | 缓存命中的 Token **单价**约为正常的 50%（如 GPT-4.1 缓存输入 $1.0/M vs 正常 $2.0/M） |
| 成本降幅口径 | 约 **90%** | ch01 课后题 Q26 解析 | 缓存命中时某档位**总输入成本**下降约 90%（例：$5/M → $0.5/M） |

> 答题规则：**问"单价折扣"答 50%，问"成本降低多少"看清题目给的基线**。不要在面试里把两个数字混着说。

## 🎤 面试怎么答（口述模板）

> **问：为什么同样一段中文比英文更贵？**
> "因为 Token 是计费单位，而主流模型的词表以英文为核心。英文一个单词大概 1 到 1.3 个 Token，中文一个字要 1.5 到 2 个，所以同样长度的内容中文 Token 数更多、成本更高，也更占窗口。工程上我会用中文优化的模型，或者把固定前缀做成可缓存的。"

> **问：上下文窗口 128K，系统提示词占了多少？剩下的怎么分配？**
> "固定部分是 System Prompt 加工具 Schema 加 Skill 触发词，大概只占 2% 到 8%，但每次请求都要发，所以这部分最适合缓存。动态部分是记忆注入和对话历史，占 20% 到 55%，不能缓存但可以通过压缩和按需召回控制。最后要留 30% 到 50% 给模型输出。设计上我会把固定前缀放最前面，最大化缓存命中。"

> **问：一次 Agent 对话大概花多少钱？**
> "给三个锚点：简单问答大概 500 Token、三厘钱；一次代码修改大概一万多 Token、六分钱；复杂的 5 轮工具调用 Agent 大概 65K Token、两毛七。具体取决于轮数和工具调用次数。"
