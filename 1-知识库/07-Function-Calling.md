## 🎯 30 秒结论

1. Function Calling 让 LLM 从"只会说话"变成"能办事情"——是 Agent 能用工具的**技术基石**。
2. 核心突破：模型不再输出自然语言让你解析，而是直接输出**符合 JSON Schema 的结构化调用**。
3. ⚠️ **LLM 只负责"决定"，不负责"执行"**——真正执行由开发者的代码完成，结果再注入回模型。
4. `strict` 模式可强制模型 100% 遵守 Schema，减少格式错误。
5. 工具描述本身要占上下文 Token，写得差会直接导致选错工具 / 参数错。

**Q6: Function Calling 的底层原理是什么？**

> Function Calling 的本质是 **LLM 经过训练后能输出结构化的函数调用 JSON**。训练阶段，模型学习了大量"用户意图→函数调用"的样本；推理阶段，模型根据用户消息和可用工具列表，判断是否需要调用工具，如果需要则输出符合 JSON Schema 的函数名和参数。需要注意的是：**LLM 只负责"决定"调用什么，不负责"执行"**。执行由开发者的代码完成，结果再注入回 LLM 继续对话。strict 模式可以强制模型 100% 遵守 Schema，减少格式错误。

> 你原文里的三个抓手，正好是这题的三层得分点：**①训练出来的能力**（不是内置规则）→ **②只决定不执行**（工程边界）→ **③strict 模式兜格式**（工程手段）。面试按这三层答，比背定义强。

## 一、核心概念

| 项 | 说明 |
| :--- | :--- |
| 定义 | LLM 根据用户意图，自动生成结构化的函数调用（**函数名 + 参数 JSON**） |
| 输入 | 用户消息 + **可用工具列表**（每个工具含名称、描述、JSON Schema） |
| 输出 | 结构化的 tool call（函数名 + 参数） |
| 执行者 | **不是 LLM**，是开发者的代码 |
| 收益 | 从"聊天"到"执行"的关键跨越 |

**对比**

```
❌ 没有 Function Calling：
   用户："北京天气怎么样？"
   模型："我觉得你应该去查一下北京的天气。"        ← 只是一句建议

✅ 有 Function Calling：
   模型 → get_weather(city="北京", date="2026-07-01")   ← 结构化、可程序化执行
```

## 二、完整调用循环（五步闭环）

```
① 用户提问
      ▼
② 模型判断是否需要工具 → 输出 tool_call（函数名 + 参数 JSON）
      ▼
③ 开发者代码解析并【执行】真实函数 / API
      ▼
④ 把执行结果作为新消息（role = tool）追加回对话
      ▼
⑤ 模型基于结果生成最终自然语言回答
（如需要多步，回到 ②，形成 Function Calling 循环）
```

> Agent 与"一次对话"的区别就在这里：**步骤 ②~④ 会循环多次**，这就是 Agentic Loop 的工具层实现。

---

## 三、底层原理

| 阶段 | 发生了什么 |
| :--- | :--- |
| **训练阶段** | 模型学了大量"用户意图 → 函数调用"的样本，学会把自然语言意图映射到结构化调用 |
| **推理阶段** | 模型读用户消息 + 工具列表（JSON Schema 也在上下文里），判断是否需要工具、需要哪个、参数是什么 |
| **执行阶段** | 由外部系统执行，模型不参与 |
| **回填阶段** | 执行结果注入上下文，模型继续推理或收尾 |

**strict 模式**：强制模型严格遵守 JSON Schema（100% 符合），显著减少格式错误导致的解析失败。

---

## 四、工程注意点

| 注意点 | 说明 |
| :--- | :--- |
| 工具描述是成本 | 工具列表写在上下文里，每次请求都要发 → 工具越多，输入 Token 越多 |
| 工具描述质量决定正确率 | 描述含糊 → 选错工具或参数填错（这是工具设计的第一号坑） |
| 工具数量有上限 | 工具过多会导致模型选择困难 → 需要**工具路由**（按意图先筛一批候选工具） |
| 权限与安全 | 工具是"动作"，会触碰真实世界 → 必须做权限判定与人工确认（详见第 24 章安全） |
| 并发 | 多个工具调用可并发，但必须保证上下文修改的顺序一致性 |

---

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| LLM 会执行函数并返回结果 | LLM 只输出调用指令，**执行在开发者代码里** |
| LLM 只能调用预置函数，不能自定义 | 工具是开发者自定义并在请求里声明的，模型只是"选择器" |
| Function Calling 是模型联网 | 它是输出结构化参数，联网是某个工具的实现细节 |
| 加更多工具总是更好 | 工具描述占 Token，且工具过多会降低选择准确率 |
| 有了 Function Calling 就等于有了 Agent | 还需要循环控制、记忆、权限——Function Calling 只是"手" |

## 🎤 面试怎么答（口述模板）

> **问：Function Calling 的底层原理是什么？**
> "本质是模型经过训练后能输出结构化的函数调用 JSON。训练阶段它见过大量'用户意图→函数调用'的样本；推理阶段，它根据用户消息和上下文里的工具列表，判断要不要调工具、调哪个、参数是什么，然后输出符合 JSON Schema 的调用。这里最关键的一点是：**模型只负责决定，不负责执行**。真正执行的是开发者的代码，执行结果再作为工具消息注入回上下文，模型基于结果继续往下走。如果要严格保证格式，可以开 strict 模式强制它完全遵守 Schema。"

> **追问：那它和 Agent 是什么关系？**
> "Function Calling 是 Agent 的'手'，是必要条件但不充分。要成为 Agent 还需要循环控制（多步）、记忆（跨轮和跨会话）、以及权限判定。有了 Function Calling 但只有一问一答，那是第二代 Tool-Enabled AI，还不是 Agent。"
