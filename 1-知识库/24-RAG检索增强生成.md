## 🎯 30 秒结论

1. **RAG 的本质**：把"知识"从参数里搬到上下文里——**知识更新不用重训，答案可溯源，幻觉可抑制**。判据是"量大且需要筛选"的知识。
2. **三种相似度度量**：余弦（只看方向，文本最常用）/ 欧氏（绝对距离，图像）/ 内积（考虑模长，**归一化后等价于余弦**）。
3. **纯向量检索的硬伤是关键词匹配差**（搜 "GPT-4o" 可能召回 "GPT-4"），所以要 **BM25 + 向量混合检索**，经验权重 **0.4 / 0.6**。
4. **HyDE**：短问题语义不足 → 先让 LLM 生成"假回答" → 用假回答去检索 → 再用检索结果生成真回答。
5. **Agentic RAG** = 把 RAG 包成一个工具，让 Agent 自己决定"要不要检索"——省 Token、可多轮、可验证、可溯源。
6. **GraphRAG** 解决向量 RAG 的死穴：**只能检索局部相似片段，答不了全局性问题**（"整个系统有哪些模块？"）。代价是构建成本高、维护复杂、实体歧义。
7. **HNSW** 是向量检索能落地的关键：多层图 + 贪心，**10 万向量从 10 万次距离计算降到约 17 次**（≈2ms vs 200ms，快 100 倍），本质是**空间换时间**。
8. **评估分两段**：检索看召回率/精确率/MRR，生成看忠实度/相关性/完整性（Ragas 可自动化）。
9. **生产级 RAG 是闭环**：数据接入 → 索引构建 → 智能检索 → 答案生成 → **持续评估优化**，不是"切块+嵌入+查"三步走。

**① 三种相似度度量（原文表）**

| 度量 | 公式 | 特点 | 适合 |
| :--- | :--- | :--- | :--- |
| **余弦相似度** | cos(A,B) = A·B / (\|A\|\|B\|) | 只看方向，不看大小 | 文本检索（最常用） |
| **欧氏距离** | d = √Σ(Ai-Bi)² | 看绝对距离 | 图像检索 |
| **内积** | IP = A·B | 考虑向量大小 | 归一化后的向量 |

**② 混合检索（原文）**

> 纯向量检索的弱点：**关键词匹配能力差**。比如搜"GPT-4o"，向量检索可能返回"GPT-4"的内容（语义相似但不是同一个模型）。**BM25**（关键词检索）正好互补。

```python
# 1. 向量检索器（语义匹配）
vector_retriever = Chroma(collection_name="knowledge_base",
                          embedding_function=embeddings).as_retriever(search_kwargs={"k": 10})
# 2. BM25 检索器（关键词匹配）
bm25_retriever = BM25Retriever.from_documents(chunks); bm25_retriever.k = 10
# 3. 混合检索器（加权融合）
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.4, 0.6])   # BM25 占 40%，向量占 60%
```

**③ HyDE 流程（原文）**

> **用户问题**："RAG 怎么做？" → **LLM 生成假回答**："RAG 是检索增强生成技术……" → **用假回答向量检索**（假回答比短问题语义更丰富）→ **用检索结果生成真回答**

**④ Agent + RAG 的优势（原文）**

> - **智能路由**：简单问题不检索，省 Token、降延迟
> - **多轮检索**：复杂问题可以多次检索不同关键词
> - **结果验证**：Agent 可以判断检索结果是否相关，不相关则换关键词重搜
> - **引用来源**：Agent 可以在回答中标注"根据 [文档名] ..."

**⑤ 生产级 RAG 闭环（原文）**

> 生产级 RAG 的核心是构建一条从**数据接入、索引构建、智能检索、答案生成到持续评估优化**的完整闭环：先对多源文档进行清洗和元数据提取，再通过分块、向量化和向量数据库完成可增量、可版本化的知识索引；查询时结合 Query 改写、BM25 与向量混合检索、重排序和上下文组装提升召回质量；生成阶段通过 Prompt 模板、LLM 和后处理降低幻觉并补充引用；最后利用检索准确率、回答忠实度和用户反馈持续迭代系统效果。

**⑥ GraphRAG 的代价与黄金场景（原文）**

> ⚠️ **代价**：构建成本高（LLM 抽取实体关系消耗大量 Token）；维护复杂（文档更新需同步更新图谱）；实体歧义（"苹果"是公司还是水果）；不适合简单问答（杀鸡用牛刀）。
> ✅ **黄金场景**：多跳推理问答（"A 公司的 CEO 毕业于哪所大学？"）；关系分析（"这个故障影响了哪些下游服务？"）；全局摘要（"整个系统架构包含哪些模块？"）；因果追溯（"为什么这个指标下降了？"）

**⑦ tree-sitter 符号感知分块（原文）**

> **tree-sitter** 是一个增量解析库，能将源码解析为 **AST**。核心能力：**增量解析**（只重解析变化部分）、**多语言支持**（40+）、**AST 节点类型**（function_declaration / class_declaration / method_definition）、**错误恢复**（有语法错误也能解析）。
> 符号感知分块：**不按字符切，按 AST 符号边界切**。每个 chunk 是一个完整的符号，并附带元数据：

| 元数据字段 | 说明 | 示例 |
| :--- | :--- | :--- |
| `symbol_name` | 符号名称 | `handle_messages` |
| `symbol_kind` | 符号类型 | `function` / `class` / `method` |
| `line_start` / `line_end` | 起止行号 | `42` / `120` |
| `signature` | 函数签名 | `fn handle_messages(msg: Message) -> Result` |
| `docstring` | 文档注释 | `/// Process incoming messages and route to handlers` |

**⑧ HNSW（原文）**

> **HNSW（Hierarchical Navigable Small World）** 是目前最流行的近似最近邻搜索（ANN）算法。核心思想：**构建多层图结构，上层稀疏（高速公路），下层稠密（城市道路），搜索时从上层快速定位区域，再在下层精细搜索**。
> 步骤：① 从顶层入口节点开始算距离；② **贪心搜索**，邻居更近就移过去；③ 本层没有更近的了就下降一层；④ 到底层（Layer 0）用**优先级队列**维护 Top-K；⑤ 返回 Top-K。
> 性能：10 万向量线性扫描 O(n) = 10 万次距离计算 ≈ 200ms；HNSW O(log n) ≈ 17 次 ≈ 2ms，**快了 100 倍**。余弦距离 = 1 - cosine_similarity。

**⑨ Deep Research vs Agentic RAG（原文表）**

| 维度 | Agentic RAG | Deep Research |
| :--- | :--- | :--- |
| **核心循环** | 检索 → 反思 → 再检索 | 检索 → 分析 → 追问 → 再检索 → 综合 |
| **侧重** | 信息够不够 | 信息全不全 |
| **思维模式** | 答题思维 | 调研思维 |
| **输出** | 简短回答 | 综合报告 |
| **典型场景** | "限流策略和降级策略分别是什么？" | "分析所有模块的技术选型和设计权衡" |
| **迭代次数** | 通常 ≤ 3 轮 | 通常 3-10 轮 |

**⑩ 八股 Q4 / Q5 原文**

> **RAG 系统如何评估**：检索质量看召回率、精确率、MRR；生成质量看忠实度、相关性、完整性。可用 Ragas 框架自动化评估。
> **检索不到相关文档怎么办**：① Query 改写；② HyDE；③ 调整分块策略（太大不精确、太小语义不完整，试 512-1024）；④ 混合检索加 BM25；⑤ 增加召回量——先召回 Top-20，再用 Reranker 精选 Top-5。

## 一、检索三度量：什么时候用哪个

| 度量 | 值域 | 归一化后 | 选型理由 |
| :--- | :--- | :--- | :--- |
| **余弦相似度** | [-1, 1] | 不变 | **只看方向**——文本长度差异不影响，最常用 |
| **欧氏距离** | [0, +∞) | 与余弦单调相关 | 看绝对距离，适合**图像/特征尺度有意义的场景** |
| **内积（点积）** | (-∞, +∞) | **等价于余弦** | 未归一化时受模长影响，容易被"长向量"主导 |

> ⚠️ 你在这里栽过一次（见 [06](06-Embedding与向量检索.md)）：**余弦相似度下界是 -1 不是 0**——它是方向类指标，可以为负；距离类指标才非负。
> 🔑 **内积那条的关键前提**：向量**归一化之后** |A|=|B|=1，内积 = 余弦。所以很多向量库（含 HNSW 实现）会先归一化再用内积，省掉除法。

## 二、从"检索"到"检索得准"：五张牌

| 手段 | 解决什么 | 代价 / 注意 |
| :--- | :--- | :--- |
| **混合检索（BM25 + 向量）** | 向量**关键词匹配弱**（"GPT-4o" ↔ "GPT-4"） | 需要维护两套索引；权重经验值 **0.4 / 0.6** |
| **Query 改写** | 用户问法与文档写法不一致 | 多一次 LLM 调用；可并行多查询 |
| **HyDE** | **短问题语义信息不足** | 假回答可能 hallucinate，方向偏了会检索到错的邻域 |
| **调 chunk_size** | 太大不精确、太小语义不完整 | 经验区间 **512~1024**；代码另说（见 §五） |
| **Reranker 重排** | 召回多了噪音也多 | 做法：**先召回 Top-20，再精选 Top-5**——用两阶段换精度 |

**为什么"先多召回再精选"是标准打法**：召回阶段要**便宜且全**（向量/BM25 都能毫秒级跑 Top-20），精选阶段要**贵但准**（Cross-Encoder Reranker 逐对精算，只算 20 个）。把贵的模型用在少量候选上，是检索系统的通用性价比结构。

## 三、Agentic RAG：把"每次都检索"改成"该检索才检索"

```python
tools = [Tool(name="knowledge_search",
              description="搜索内部知识库，获取产品文档、技术文档、FAQ等信息。当需要查找具体信息时使用。",
              func=rag_search)]
agent = create_react_agent(llm, tools, prompt)
# 用户："你好" → 不检索，直接回答
# 用户："我们的 API 限流策略是什么？" → 调用 knowledge_search
```

| 维度 | Naive RAG（每次都检索） | Agentic RAG（RAG 作为工具） |
| :--- | :--- | :--- |
| **触发** | 无条件检索 | Agent 自主判断（智能路由） |
| **成本** | 每个问题都付检索 + 更长 Prompt | 简单问题零检索，**省 Token、降延迟** |
| **复杂问题** | 一轮定生死 | 可**多轮检索**、换关键词重搜 |
| **质量保障** | 检索到什么用什么 | 可**判断相关性**，不相关就重搜 |
| **可信度** | 答案无来源 | 可**标注引用来源** |

> **和前面条目的接口**：这里"RAG 作为工具"的注册方式，就是 [07](07-Function-Calling.md) 的 Function Calling + [14](14-工具Schema与异常处理.md) 的 `description` 决定选中率——**`description` 写得含糊，Agent 就不会在该用的时候用它**。

## 四、GraphRAG：补上"局部相似"的死穴

| 维度 | 向量 RAG | GraphRAG |
| :--- | :--- | :--- |
| **检索对象** | 文本块（"像"的内容） | 实体 + 关系（"有关联"的内容） |
| **检索方式** | 语义相似度搜索 | 建图后**子图检索与图遍历** |
| **擅长** | 事实性问答、单点查询、毫秒级、构建便宜 | **多跳推理**、关系分析、全局摘要、因果追溯 |
| **不擅长** | 跨文档全局性问题 | 简单问答（杀鸡用牛刀） |
| **代价** | 低 | **高**：LLM 抽实体关系烧 Token、文档更新要同步图谱、**实体歧义**（"苹果"是公司还是水果） |

> **最佳实践（可直接背）**：**混合使用**——向量 RAG 做日常问答（约 90% 场景），GraphRAG 做复杂关联分析（约 10%）。**不是替代，是互补。**
> **一句话区分**：向量 RAG 找"**像**"的，GraphRAG 找"**有关联**"的。

## 五、代码知识库：tree-sitter 符号感知分块

| 维度 | 按字符切（通用文档做法） | 按 AST 符号切（代码做法） |
| :--- | :--- | :--- |
| **切分单位** | 固定长度 chunk（512~1024） | **完整符号**：函数 / 类 / 方法 / 结构体 / 接口 / 枚举 |
| **典型问题** | 一个函数被切成两半，检索到一半没头没尾 | 不会切断语法单元 |
| **附加信息** | 无 | `symbol_name` / `symbol_kind` / `line_start` / `line_end` / `signature` / `docstring` |
| **为何可行** | — | tree-sitter：**增量解析** + 40+ 语言 + **错误恢复**（语法错误也能解析） |

> **为什么代码要特殊处理**：代码的语义单位是**符号与调用关系**，不是连续文本。切半个函数，等于把答案切走了一半——这也是"代码检索"和"文档检索"最大的工程差异。
> 附加元数据的价值不只是排序：`line_start/line_end` 让 Agent 能**精确定位并跳转**，`signature` 让它在不看全文时就知道要不要展开。

### HNSW：让"检索"这件事快到可用

```
Layer 2（最稀疏 · 高速公路）：   ●───────────●───────────●
                                  │           │
Layer 1（中间层）：          ●────●─────●─────●─────●
                             │    │     │     │     │
Layer 0（最稠密 · 城市道路）：●●●●●●●●●●●●●●●●●●●●●●●●●●
     入口 → 上层快速定位区域 → 逐层下降 → 底层用优先级队列精搜 Top-K
```

| 对比 | 线性扫描 | HNSW |
| :--- | :--- | :--- |
| **复杂度** | O(n) | O(log n) |
| **10 万向量的距离计算次数** | 100,000 次 | 约 **17 次** |
| **实测耗时** | ≈ 200ms | ≈ **2ms**（快约 100 倍） |
| **代价** | 无额外内存 | **额外内存存邻居指针**（空间换时间） |

> 原文实现细节：余弦距离 = 1 - cosine_similarity；可纯手写 HNSW + bincode 序列化到本地文件，**不依赖外部向量数据库**。

## 六、Deep Research：从"答题"到"调研"

| 维度 | Agentic RAG | Deep Research |
| :--- | :--- | :--- |
| **核心循环** | 检索 → 反思 → 再检索 | 检索 → 分析 → **追问** → 再检索 → 综合 |
| **侧重** | 信息**够不够** | 信息**全不全** |
| **思维模式** | **答题思维** | **调研思维** |
| **输出** | 简短回答 | 综合报告 |
| **迭代轮次** | 通常 ≤ 3 | 通常 3~10 |

> **一句话区分**：Agentic RAG 优化**宽度**（够不够答），Deep Research 优化**深度**（有没有漏）。**互补，不是替代。**

## 七、评估：两段指标 + Ragas

| 阶段 | 指标 | 问的问题 |
| :--- | :--- | :--- |
| **检索质量** | 召回率 Recall | 相关文档**是否被检索到**（漏了就没救） |
| | 精确率 Precision | 检索结果里**有多少是相关的**（噪音多会带偏生成） |
| | MRR | 第一个相关结果**排在第几** |
| **生成质量** | 忠实度 Faithfulness | 回答**是否基于检索内容**（幻觉检测） |
| | 相关性 Relevance | 回答**是否切题** |
| | 完整性 | 是否**覆盖了问题的所有方面** |

> **Ragas** 是把上面这些指标**自动化**的框架（用 LLM 给 LLM 的答案打分）。
> **排障顺序很重要**：先看检索，再看生成——**如果检索没召回（Recall 低），换模型、改 Prompt 都救不回来**。这也是 §二"先多召回再精选"的理由。

## 🔆 强化延伸（你标了 `==` 的三处）

### 🔆1｜检索内容互相冲突，Agent 怎么取舍？（`==Q6==`）

企业知识库文档版本多、来源杂，**冲突是常态**。三重保障，**不要只答"取最新的"**：

| 策略 | 怎么做 | 解决什么 |
| :--- | :--- | :--- |
| **① 元数据加权排序** | 按发布时间 + 权威等级双重加权，优先采信**高权威 + 最新** | 单点裁决，成本低，覆盖 80% 情况 |
| **② 多智能体辩论** | 让不同 Agent 分别代表冲突的文档互相论证，梳理矛盾点，筛出逻辑最通顺的 | 用"辩论"替代"单点裁决"，暴露隐含矛盾 |
| **③ 强制溯源** | 要求答案必须附检索来源，把最终裁决权交回人类 | 兜底：模型拿不准时至少人能核对 |

> **面试要点**：三重是**组合**不是三选一——加权解决大多数，辩论处理难分歧，溯源保证可审计。
> **追问准备**："如果两篇文档权威等级相同、时间相同呢？" → 答：这时不该由系统裁决，走**强制溯源 + 把矛盾显式呈现给用户**（这正是不硬撑"取最新"的价值）。

### 🔆2｜新闻/股价这类实时知识，RAG 怎么适配？（`==Q8==`）

三个机制覆盖**全链路**：判断要不要实时 → 怎么更新 → 怎么保证不过期。

| 机制 | 做法 | 对应环节 |
| :--- | :--- | :--- |
| **① 动态路由 Agent** | 先判断问题是否需要实时数据：需要 → 优先调搜索/实时 API，**不查静态向量库**；不需要 → 正常走向量库 | **判断要不要实时**（类似"先思考再行动"的分发） |
| **② 流式增量更新** | 用消息队列监听知识库变动，**动态新增/更新向量**，不全量重构 | **怎么更新**（增量，效率高） |
| **③ 缓存失效机制** | 高频问题设缓存时效，元数据一更新就清空旧缓存 | **怎么保证不过期** |

> **面试要点**：按"**路由 → 增量 → 失效**"这条链路答，体现的是**全链路思维**，而不是只会说"加个实时接口"。
> **易漏点**：只讲增量更新，忘了**缓存失效**——索引更新了但答案还是缓存里的旧内容，是最典型的 bug。
> **与 §三 的接口**：动态路由就是 **Agentic RAG** 的思路延伸——不是"要不要检索"，而是"**检索哪个源**"。

### 🔆3｜HNSW 的原理，为什么不直接线性扫描？（`==Q13==`）

| 层 | 作用 | 类比 |
| :--- | :--- | :--- |
| **上层（稀疏）** | 快速跨越大距离，定位目标区域 | 高速公路 |
| **下层（稠密）** | 精细搜索，维护 Top-K | 城市道路 |

**搜索五步**：顶层入口 → 贪心移动（邻居更近就过去）→ 本层无更近则下降一层 → Layer 0 用**优先级队列**精搜 → 返回 Top-K。

> **为什么不线性扫描**：10 万向量线性要 **10 万次**距离计算（≈200ms），HNSW 约 **17 次**（≈2ms）——**快 100 倍**。RAG 是要交互的，200ms 单次检索在多轮/多查询场景下会直接变成秒级延迟。
> **代价是什么**：**空间换时间**——每个节点要存邻居指针，构建图要多占内存。
> **一句话收尾**：HNSW 的价值是把向量检索从"**理论上可行**"变成"**工程上可用**"；代价远小于收益。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 余弦相似度值域 [0,1] | **[-1,1]**——方向类指标可以为负（你错过这道题） |
| 内积和余弦完全不同 | **归一化后等价**；未归一化时内积受模长影响 |
| 向量检索能搞定一切 | **关键词匹配弱**（"GPT-4o" vs "GPT-4"），必须配 **BM25** |
| chunk 切得越细越准 | 太小**语义不完整**，太大**不精确**；经验区间 **512~1024**，代码改按 AST 符号切 |
| RAG 就是"切块+嵌入+查询" | 生产级是**五段闭环**：接入 → 索引 → 检索 → 生成 → **持续评估** |
| 检索不到就换更强的 LLM | 先查**检索侧**：Query 改写 / HyDE / 混合检索 / 先召回 Top-20 再 Rerank |
| GraphRAG 会替代向量 RAG | **互补**：向量做 90% 日常问答，GraphRAG 做 10% 复杂关联分析 |
| GraphRAG 没有缺点 | 构建成本高（抽实体烧 Token）、维护复杂、**实体歧义**、简单问答杀鸡用牛刀 |
| 检索内容冲突就取最新的 | 三重保障：**元数据加权 + 多 Agent 辩论 + 强制溯源** |
| 实时数据只要做增量更新 | 还要**动态路由**（判断要不要实时）与**缓存失效**（防止答案过期） |
| HNSW 没有代价 | **空间换时间**：额外内存存邻居指针 |
| 忠实度是检索指标 | 是**生成**指标（有没有幻觉）；检索侧看召回率/精确率/MRR |

## 🎤 面试怎么答（口述模板）

> **问：RAG 是什么？为什么不直接把文档塞进上下文？**
> "RAG 是检索增强生成——**把知识从参数搬到上下文**：先检索相关片段，再让模型基于片段作答。相比直接塞全文，它解决三个问题：**窗口装不下**、**注意力被稀释**（长上下文里中间部分容易被忽略）、以及**成本**（每次都带全文太贵）。相比微调，它的优势是**知识更新不用重训、答案可溯源、幻觉可抑制**。
> 相似度一般用**余弦**（只看方向，不受文本长度影响），值域是 **[-1,1]** 不是 [0,1]。"

> **追问：你们怎么提升召回质量？**
> "五张牌：**混合检索**（BM25 加向量，权重经验 0.4/0.6，因为纯向量关键词匹配弱——搜 GPT-4o 可能召回 GPT-4）；**Query 改写**（用户问法和文档写法不一致）；**HyDE**（短问题语义不足，先让 LLM 生成假回答再拿假回答去检索）；**调 chunk_size**（512 到 1024，代码库改成按 AST 符号切）；**两阶段检索**（先召回 Top-20 再用 Reranker 精选 Top-5，把贵的模型只用在少量候选上）。"

> **追问：检索到的内容互相冲突怎么办？**
> "企业知识库里版本多、来源杂，冲突是常态，我不会只说'取最新的'，而是三重保障：**元数据加权**（发布时间加权威等级双重排序）、**多智能体辩论**（让代表不同文档的 Agent 互相论证，暴露隐含矛盾）、**强制溯源**（答案必须附来源，最终裁决权交回人）。如果两篇文档权威和时间都相同，正确做法不是让系统硬选，而是**把矛盾显式呈现给用户**。"

> **追问：做实时知识（新闻、股价）怎么适配？**
> "三个机制覆盖全链路：**动态路由**——先判断问题是否需要实时数据，需要就走搜索或实时 API、不查静态向量库；**流式增量更新**——用消息队列监听变动，增量更新向量而不是全量重构；**缓存失效**——高频问题设缓存时效，元数据一更新立刻清缓存。三个分别对应'要不要实时''怎么更新''怎么保证不过期'，只讲增量更新是最常见的漏项。"

> **追问：GraphRAG 了解吗？什么时候该上？**
> "它补的是向量 RAG 的死穴：**只能检索局部相似片段，答不了全局性问题**。GraphRAG 先从文档抽实体和关系建图，检索时做**图遍历**找'有关联'的信息，而不是找'像'的文本。适合**多跳推理**（A 公司 CEO 毕业于哪所大学）、**关系分析**（故障影响哪些下游服务）、**全局摘要**、**因果追溯**。
> 但它代价不小：构建要烧大量 Token 抽实体关系、文档更新要同步图谱、还有**实体歧义**问题（苹果是公司还是水果）。所以最佳实践是**混合**：向量 RAG 做 90% 日常问答，GraphRAG 做 10% 复杂关联分析——不是替代是互补。"
