## ⚡ TL;DR（先看这三行，下面正文是参考资料）

- **一句话**：决策中枢只做两件事：**对任务分类**（复杂度 → 执行路径）和**选执行方式**（单 Agent vs 多 Agent）。

## 🎯 30 秒结论

1. 决策中枢做两件事：**对任务分类**（复杂度 → 执行路径）和**选执行方式**（单 Agent vs 多 Agent）。
2. 真实用户的一句话往往包含**复合意图**，必须先拆解再排序——拆解的本质是"把一句自然语言变成一张带条件的执行计划"。
3. 工具多到几十上百个时，全量注入工具描述会 token 爆炸 → **Tool RAG**：按意图只检索最相关的 K 个工具描述注入。
4. 单 Agent 有三个结构性瓶颈：**上下文爆炸**、**能力冲突**、**串行瓶颈**。它们正是多 Agent 的存在理由。
5. 多 Agent 的**两个核心收益**：**上下文隔离**（每个 Agent 只看自己需要的信息）+ **并行执行**（独立子任务同时跑）。
6. 决策矩阵一句话：**步数 > 5 且有并行子任务 / 需要多角色 / 工具 > 10 个分组** → 多 Agent；否则单 Agent 更简单更便宜。

**① 复合意图拆解（原文示例）**

> 用户："帮我查下北京明天天气，顺便订个闹钟提醒我带伞"
>
> **意图拆解：**
> ① 查询意图 → 调用天气 API → 获取北京明天天气
> ② 判断意图 → 根据天气判断是否需要带伞
> ③ 执行意图 → 调用闹钟 API → 设置明早提醒
>
> **Agent 执行计划：**
> Pipeline：`Step 1: call weather_api(city="北京", date="明天")`
> `Step 2: if rain_probability > 0.3 → call alarm_api(msg="带伞")`
> `Step 3: return "北京明天小雨，已设闹钟提醒带伞"`

**② Tool RAG（原文）**

> 当 Agent 注册了几十个甚至上百个工具时，把所有工具描述都塞进 Prompt 会导致 Token 爆炸。解决方案是 **Tool RAG**——根据用户意图，只检索最相关的工具描述注入 Prompt。

**③ 单 Agent 的三大瓶颈（原文）**

> - **上下文爆炸**：任务越复杂，需要的工具/记忆/中间结果越多，Prompt 膨胀导致 Token 超限
> - **能力冲突**：一个 Agent 同时扮演"搜索者"和"写作者"，System Prompt 冲突，角色混乱
> - **串行瓶颈**：所有步骤串行执行，无法并行处理独立子任务

**④ 任务分类矩阵（原文）**

| 任务类型 | 复杂度      | 执行路径                           | 示例                    |
| :------- | :---------- | :--------------------------------- | :---------------------- |
| 简单问答 | Low         | direct_answer（纯模型推理）        | "什么是 Transformer"    |
| 代码解释 | Medium      | analyze_explain（读取+分析）       | "这段代码什么意思"      |
| 代码修改 | Medium-High | locate_modify（定位+修改+验证）    | "帮我修复这个 bug"      |
| 复杂开发 | High        | decompose_execute（拆解+多步执行） | "帮我搭建一个 REST API" |

**⑤ 单 Agent / 多 Agent 决策矩阵（原文）**

| 维度     | 单 Agent          | 多 Agent                       |
| :------- | :---------------- | :----------------------------- |
| 任务步数 | ≤ 5 步            | > 5 步或有并行子任务           |
| 工具数量 | ≤ 10 个           | > 10 个，可分组                |
| 角色需求 | 单一角色          | 多角色（搜索者+写作者+审核者） |
| 上下文   | 可放入一个 Prompt | 超出单 Prompt 容量             |
| 延迟要求 | 串行可接受        | 需要并行加速                   |

**⑥ 八股 Q7：决策中枢的七步链路（原文）**

> ①**感知**（接收输入）→ ②**意图识别**（理解用户目标）→ ③**任务分类**（判断复杂度）→ ④**任务规划**（拆解子任务）→ ⑤**工具路由**（选工具）→ ⑥**执行调度**（调模型/工具）→ ⑦**上下文管理**（压缩/记忆）。
> 这七步循环运行，就是 Agent Loop。每一轮的上下文管理结果会反馈到下一轮的感知阶段，形成闭环。

## 一、七步链路 vs 八步链路：两套说法的关系（必须先讲清）

你在 ch02 记的是**8 步链路**（已沉淀进 [11](11-运行时链路与意图调度.md)），ch08 八股给的是**7 步链路**。面试被问到"几条链路"时，如果两套都答不出来会显得没体系。**它们只是切分粒度不同，不是两套环。**

| ch08 七步 | 对应 ch02 八步 | 差异说明 |
| :--- | :--- | :--- |
| ① 感知 | ① 输入接收 | 同一件事：接原始输入并格式化 |
| ② 意图识别 | ② 意图识别 | 完全对应 |
| ③ 任务分类 | ③ 任务分类 | 完全对应 |
| ④ 任务规划 | ④ 任务拆解 | 同一件事，**且同样是条件步骤**（简单任务跳过） |
| ⑤ 工具路由 | ⑥ 工具调用 | ch08 把"**选哪个工具**"单独拎出来（Tool RAG 的用武之地） |
| ⑥ 执行调度 | ⑤ 执行调度 | ch08 更强调"调模型还是调工具"这一次决策 |
| ⑦ 上下文管理 | ⑦ 结果整合 + ⑧ 输出返回 | ch08 用"上下文管理"把"缝答案 + 写记忆 + 压缩"统一收口 |

```
ch08 七步：感知 → 意图识别 → 任务分类 → 任务规划 → 工具路由 → 执行调度 → 上下文管理
                                                              │
                                        ┌─────────────────────┘
                                        ▼  （上下文管理结果反馈回感知）
ch02 八步：输入 → 意图识别 → 任务分类 → 任务拆解 → 执行调度 → 工具调用 → 结果整合 → 输出
                                                              │
                                        └──── 回边：工具返回新信息时重新理解意图 ────┘
```

> **答题建议**：面试时说"**七步和八步是同一套链路的不同切分**"，然后给出上面这张映射表——比背下某一个版本更能体现体系感。

## 二、复合意图拆解：从"一句话"到"一张计划"

用户一句话常含多个意图，**且它们之间有依赖和条件**：

| 步骤 | 原文示例 | 意图类型 | 关键点 |
| :--- | :--- | :--- | :--- |
| ① | 查北京明天天气 | **查询意图** | 需要外部数据 → 调工具 |
| ② | 根据天气判断是否带伞 | **判断意图** | 需要推理 → 调模型 |
| ③ | 订闹钟提醒 | **执行意图** | 有副作用的工具 → 需权限（见 [12](12-权限与可逆性分级.md)） |

**这张计划里藏了三个面试考点**

| 考点 | 例子里的体现 |
| :--- | :--- |
| **条件执行** | `if rain_probability > 0.3` —— ②③ 不是无条件执行，取决于 ① 的结果 |
| **异质步骤混合** | 同一条链里既有"调工具"（①③）又有"调模型"（②）——呼应当调度器"模型思考、工具行动" |
| **副作用分级** | ③ 是写操作（设置闹钟），可逆性低于查询——**权限判定要按步骤粒度做，不能按整条链做** |

> 📌 **一个容易被忽略的坑**：如果 ① 失败（天气 API 超时），② 的条件判断就没有输入。这时不能让 ③ 无条件执行——**条件链的失败必须向下传播**，否则用户会收到一个"设了闹钟但不知道要不要带伞"的荒谬结果。

## 三、Tool RAG：工具多了怎么选

**问题**：工具 > 20 个时，把全部工具描述塞进 Prompt → token 爆炸，而且**工具描述之间互相干扰，选错工具的概率反而上升**。

**做法**：把工具描述向量化入索引，按用户意图检索 **Top-K 个最相关工具**，只注入这几个。

| 维度 | 全量注入 | Tool RAG |
| :--- | :--- | :--- |
| Prompt 占用 | 随工具数线性增长 | 恒定（只注入 Top-K） |
| 选工具准确率 | **工具越多越容易选错**（描述互相干扰） | 候选集更小更聚焦 |
| 新增工具 | 直接推高每次调用的 token | 增量入索引，不影响 Prompt 体积 |
| 实现成本 | 0 | 需要工具描述的向量索引 + 检索 |
| 风险 | — | **检索漏掉了真正该用的工具** → 需兜底（关键词命中 / 全量回退） |

> **它其实是 RAG 思想在"工具"上的复用**：把"从海量文档找相关段落"换成"从海量工具找相关工具"，底层用的是同一套 [Embedding 与向量检索](06-Embedding与向量检索.md) 机制。

## 四、任务分类矩阵：复杂度 → 执行路径

| 任务类型 | 复杂度 | 执行路径 | 示例 | 需要的工程能力 |
| :--- | :--- | :--- | :--- | :--- |
| 简单问答 | Low | `direct_answer`（纯模型推理） | "什么是 Transformer" | 无工具 |
| 代码解释 | Medium | `analyze_explain`（读取+分析） | "这段代码什么意思" | 只读工具 |
| 代码修改 | Medium-High | `locate_modify`（定位+修改+验证） | "帮我修复这个 bug" | 读写工具 + **验证环节** |
| 复杂开发 | High | `decompose_execute`（拆解+多步执行） | "帮我搭建一个 REST API" | 拆解 + 循环 + 状态管理 |

**与 [11 §三](11-运行时链路与意图调度.md) 的四个判别维度互补**：11 给的是"用什么问题判断复杂度"（是否需外部数据 / 是否多步 / 输入复杂度 / 步骤间依赖），这里给的是"复杂度落到哪条执行路径"。

> 关键：**`locate_modify` 比 `analyze_explain` 多了一个"验证"**——写操作必须闭环验证。这正是"改 bug 的 Agent 比解释代码的 Agent 难做"的原因，也和 [12](12-权限与可逆性分级.md) 的可逆性分级对上。

## 五、单 Agent 的三个瓶颈 → 多 Agent 的两个收益

**瓶颈（为什么单 Agent 不够）**

| 瓶颈 | 机制 | 具体表现 |
| :--- | :--- | :--- |
| **① 上下文爆炸** | 任务越复杂 → 需要的工具/记忆/中间结果越多 | Prompt 膨胀导致 token 超限（呼应 [18](18-上下文工程与消息裁剪.md)） |
| **② 能力冲突** | 一个 Agent 同时扮演"搜索者"和"写作者" | **System Prompt 冲突**，角色混乱，两边都不像 |
| **③ 串行瓶颈** | 所有步骤串行执行 | 独立子任务无法并行，总延迟 = 各步延迟之和 |

**收益（多 Agent 买到了什么）**

| 收益 | 机制 | 对应解决的瓶颈 |
| :--- | :--- | :--- |
| **上下文隔离** | **每个 Agent 只看自己需要的信息** | ① 上下文爆炸 |
| **并行执行** | 独立子任务同时跑 | ③ 串行瓶颈 |
| **角色专精** | 每个 Agent 一套独立 System Prompt | ② 能力冲突 |

> **注意**：多 Agent 不是"更先进"，是**买隔离和并行要付的代价**——多了通信开销、状态同步、结果整合（还有"谁来综合判断"的问题，呼应 [19 §五 Fork 四规则](19-ReAct循环与推理范式家族.md) 的"不推诿理解"）。

**决策矩阵（可直接背）**

| 维度 | 单 Agent | 多 Agent |
| :--- | :--- | :--- |
| 任务步数 | ≤ 5 步 | **> 5 步或有并行子任务** |
| 工具数量 | ≤ 10 个 | **> 10 个，可分组** |
| 角色需求 | 单一角色 | **多角色**（搜索者+写作者+审核者） |
| 上下文 | 可放入一个 Prompt | 超出单 Prompt 容量 |
| 延迟要求 | 串行可接受 | 需要并行加速 |

## ❓ 你的疑问解答

> 你在 ch08 记录区写下的疑问：
> **「这道题难道不是选 A 吗，答案选 B 是不是有点太浅显了？」**
> （原题：Tool RAG 的核心目的是什么？A 提高工具调用准确率 / B 减少 Token 消耗 / C 增加工具数量 / D 提升工具执行速度）

**先说结论：你的直觉不完全错，但这道题考的是"设计动机"，而且这两个选项之间其实有因果关系。** 这里把三种层次分开讲。

### 第一层：这道题在考什么

题目问的是"**核心目的**"——也就是**当初为什么要造这个东西**，而不是"它带来了哪些好处"。

| 选项 | 属于 | 判断 |
| :--- | :--- | :--- |
| B 减少 Token 消耗 | **设计动机**（出发点是问题驱动） | ✅ 原答案 |
| A 提高工具调用准确率 | **附带收益**，而且是有条件的 | ❌ 不是"核心目的" |
| C 增加工具数量 | 事实相反——Tool RAG 是为了**在工具多的情况下还能用**，不是为了增加 | ❌ 明显错误 |
| D 提升工具执行速度 | 检索工具描述跟工具执行速度无关 | ❌ 无关选项 |

原文的叙述逻辑也在暗示这一点：**"当 Agent 注册了几十个甚至上百个工具时，把所有工具描述都塞进 Prompt 会导致 Token 爆炸。解决方案是 Tool RAG"**——**问题是 token 爆炸，方案是 Tool RAG**。问题的定义决定了目的。

### 第二层：为什么 A 不是"核心目的"——A 是**有条件的**收益

这是你的直觉真正有价值的地方。A 成立需要额外前提：

| 场景 | 工具全量注入 | Tool RAG |
| :--- | :--- | :--- |
| 工具少（≤10）、描述清晰、彼此不重叠 | 选得准 | 选得准（无差别） |
| 工具多、**描述语义重叠** | 干扰大，选错率高 | 候选集聚焦，**选得准** ✅ |
| 工具多、但**检索召回失败**（该用的工具没被检索出来） | 选得准 | **选错了** ❌ |

**关键：A 的收益依赖检索质量。** 检索召回率不满 100% 时，Tool RAG 反而可能选错工具。所以 A 是"**在检索可靠的前提下**才成立的收益"，而 B（省 token）是**无条件成立的结构性收益**——不管检索准不准，注入的描述都少了。

> 换句话说：**B 是这个机制的定义性收益，A 是它的衍生收益。** 题目问"核心目的"，选 B 是合理的。但——

### 第三层：这道题本身出得不够好（可以这么跟面试官说）

**诚实评价：这题问得偏浅，而且"核心目的"这个词有歧义。** 两个选项在工程现实中是**互为因果、共同驱动**的：

```
工具数量增长 ──┬─► token 爆炸 ──► 塞不下 ──┐
               │                            ├─► Tool RAG
               └─► 描述互相干扰 ──► 选错 ────┘
```

更准确的说法应该是：

> **Tool RAG 的直接目的是控制工具描述的注入开销（省 token）；间接收益是把候选集收窄，从而在大量工具下提升选择准确率。二者不是竞争关系，是一体两面。**

**如果面试官问这题，推荐这样答（L3→L4）**：

> "如果只能选一个，我选 B——因为**问题是 token 爆炸，Tool RAG 是解法**，这是设计动机。但我想补一句：**A 是一个真实且重要的收益**，前提是检索本身可靠。工具描述语义重叠严重时，全量注入的干扰会让选错率上升，收窄候选集确实能提升准确率。反过来说，如果检索召回失败、把该用的工具漏掉了，Tool RAG 反而更差——所以工程上必须配兜底，比如关键词命中兜底、或对高置信度任务回退到全量注入。
> 所以我的表述是：**省 token 是定义性收益，提准确率是衍生收益，而两者都被"检索召回率"这个新引入的故障点约束着。**"

> **一句话收尾**：这道题的正确打开方式不是"选哪个"，而是**"为什么 A 依赖前提、B 无条件成立"**——能把这一层说出来，比选对字母值钱。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 七步链路和八步链路是两套不同的机制 | 是**同一套链路的不同切分**：七步把"选工具"单列，把"缝答案+写记忆"收进"上下文管理" |
| 多 Agent 比单 Agent 先进，能拆就拆 | 多 Agent 是**为隔离和并行付代价**：多了通信、状态同步、结果整合的开销 |
| Tool RAG 的核心目的是提高准确率 | **核心目的是省 token**；准确率提升是**有条件的衍生收益**（依赖检索召回率） |
| 工具越多越该全量注入（信息更全） | 工具多时描述互相干扰，**全量注入反而更容易选错** |
| 复合意图拆解完就可以无条件顺序执行 | 拆解出的步骤常带**条件依赖**（`if rain_prob > 0.3`）；条件链的失败必须向下传播 |
| 权限判定按整条调用链做一次就够 | 同一条链里可能既有读（可逆）又有写（不可逆），**权限要按步骤粒度判** |
| "代码修改"和"代码解释"只是复杂度差一点 | 前者多了**验证环节**（`locate_modify` vs `analyze_explain`）——写操作必须闭环验证 |
| 上下文隔离只是"省 token" | 它同时解决**能力冲突**（每个 Agent 一套独立 System Prompt） |

## 🎤 面试怎么答（口述模板）

> **问：Agent 的决策中枢是怎么工作的？**
> "我按七步讲：**感知 → 意图识别 → 任务分类 → 任务规划 → 工具路由 → 执行调度 → 上下文管理**，这七步循环运行就是 Agent Loop，而且上下文管理的结果会反馈回下一轮的感知，形成闭环。
> 补充一点：这七步和常说的八步链路是**同一套链路的不同切分**——七步把'选哪个工具'单列出来，把'缝答案、写记忆、压缩'统一收口成'上下文管理'。面试里我倾向把两套都点一下，显得有体系。
> 决策中枢的核心动作是两个：**分类**（复杂度决定走哪条执行路径）和**选型**（单 Agent 还是多 Agent）。"

> **追问：工具特别多的时候怎么办？**
> "用 **Tool RAG**——把工具描述向量化建索引，按用户意图只检索 Top-K 个最相关的注入 Prompt。
> 它的**直接目的是控制注入开销**：工具几十上百个时，全量注入会 token 爆炸，而且描述之间互相干扰，反而更容易选错。收窄候选集顺带提升了准确率，但这是**有条件的衍生收益**——它依赖检索召回率。
> 如果检索把该用的工具漏掉了，Tool RAG 会比全量注入更差。所以工程上一定要配兜底：关键词命中兜底、或者对高置信度任务回退全量注入。"

> **追问：什么时候该拆成多 Agent？**
> "先看单 Agent 的三个瓶颈。①**上下文爆炸**——任务越复杂，工具、记忆、中间结果越多，Prompt 直接超限；②**能力冲突**——一个 Agent 同时当搜索者和写作者，System Prompt 是矛盾的，角色会乱；③**串行瓶颈**——所有步骤排队跑，独立子任务没法并行。
> 决策矩阵很简单：**步数 > 5 且有并行子任务、需要多角色、或者工具 > 10 个能分组** → 考虑多 Agent；否则单 Agent 更简单也更便宜。
> 多 Agent 买到的是**上下文隔离 + 并行执行 + 角色专精**，但代价是通信开销、状态同步和结果整合——尤其要小心'谁来综合判断'，**综合判断必须留在有全局视角的主 Agent 手里**。"
