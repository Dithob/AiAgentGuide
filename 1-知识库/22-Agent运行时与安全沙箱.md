## 🎯 30 秒结论

1. **三层嵌套**：Sandbox 在最外层（所有行为最终都在某个隔离环境中执行）→ Runtime 在中间层（提供基础设施）→ Agent Loop 在最内层（一个逻辑循环）。**决定"做什么 / 怎么做 / 在哪里做"分别是 Loop / Runtime / Sandbox。**
2. Agent Loop 是六步而非五步：**感知 → 推理 → 规划 → 执行 → 观察 → 评估**（比 ch03/ch13 的五步多了"评估"，把"是否完成"显式化）。
3. Runtime 是**五层架构**：LLM 管理层 / 工具注册层 / 记忆管理层 / 执行调度层 / 可观测层。它的职责**不包括执行 LLM 推理**——推理在模型服务端。
4. 沙箱隔离有五个级别，**没有免费的午餐**：进程级（毫秒、隔离弱）→ 容器级（秒级、中）→ 微虚拟机（125ms~秒、强）→ WASM → 云沙箱。
5. 黄金法则：**默认拒绝一切，按需开白**。绝不能暴露：宿主机 Docker Socket、云元数据 API、内网服务发现端口、SSH 私钥目录。
6. 工业级沙箱是**三层纵深防御**，不是单点：应用级命令静态分析（23+ 验证器 + AST）→ 权限决策引擎（三步决策）→ OS 级隔离（Seatbelt / Bubblewrap+seccomp）。
7. 一个真实攻击向量值得记住：**裸 Git 仓库的 `core.fsmonitor` 劫持**——`git status` 会自动执行你指定的脚本，绕过命令检查。

**① 三层嵌套架构（原文）**

> 🔄 **Agent Loop**：LLM 驱动的感知→推理→规划→执行→观察→评估的 6 步循环。决定 Agent **做什么**——如何决策、迭代和自我纠正。
> ⚙️ **Runtime**：为 Loop 提供工具调用、记忆管理、多 Agent 协作、可观测性等基础设施。决定 Agent **怎么做**——把逻辑语义转化为可执行计算。
> 🔒 **Sandbox**：在代码执行、工具调用等不可信行为发生前，提供进程/容器/虚拟机级别的隔离保护。决定 Agent **在哪里做、在什么约束下做**。
> 三者呈现严格的嵌套关系——Sandbox 在最外层，Runtime 在中间层，Agent Loop 在最内层。

**② Agent Loop 六步（原文表）**

| 步骤              | 职责                     | 典型输入                     | 典型输出                |

## 一、三层嵌套：一张表记住"谁决定什么"

| 层 | 决定什么 | 一句话 | 典型问题 |
| :--- | :--- | :--- | :--- |
| **Agent Loop**（最内） | **做什么** | LLM 驱动的决策循环 | "下一步该调工具还是该回答？" |
| **Runtime**（中间） | **怎么做** | 把逻辑语义转成可执行计算的基础设施 | "工具参数合法吗？有权限吗？历史太长怎么办？" |
| **Sandbox**（最外） | **在哪里做、在什么约束下做** | 不可信执行前的隔离保护 | "这段代码能在什么范围内动我的系统？" |

```
┌───────────────────────────────────────────────────────────┐
│ 🔒 Sandbox（进程/容器/微虚拟机级别的隔离）                    │
│  ┌─────────────────────────────────────────────────────┐  │
│  │ ⚙️ Runtime（工具调用·记忆·协作·可观测）                │  │
│  │  ┌───────────────────────────────────────────────┐  │  │
│  │  │ 🔄 Agent Loop（感知·推理·规划·执行·观察·评估）  │  │  │
│  │  └───────────────────────────────────────────────┘  │  │
│  └─────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
```

> **嵌套不是"包含关系"的口头比喻**——它对应真实的执行栈：Loop 的一次 Act，最终必然落到 Runtime 的某个工具 handler，再落到 Sandbox 的某个隔离环境里。**Sandbox 的边界就是这次 Act 能造成影响的最大范围。**

**Runtime 类比编程语言的运行时**：JVM 为 Java 提供、V8 为 Node.js 提供——**这门语言「能写出来的东西」和「实际能跑起来的东西」之间的那层**，就是 Runtime。

## 二、Agent Loop 六步：多出来的"Evaluate"为什么重要

| 步 | 与 ch03/ch13 五步的对应 | 新增/强化点 |
| :--- | :--- | :--- |
| Perceive 感知 | 感知用户消息 + 历史 | — |
| Reason 推理 | 决策（调工具 or 回答） | 输入明确为"完整上下文 + System Prompt" |
| Plan 规划 | （隐含在决策里） | **显式化**：把决策展开成工具调用序列 |
| Act 执行 | 行动 | — |
| Observe 观察 | 观察（回填历史） | — |
| **Evaluate 评估** | **无对应** | **新增**：显式判断"完成 or 继续" |

> **为什么"评估"值得单列**：五步版里"是否结束"是靠 `tool_calls` 是否为空**隐式判断**的；六步版把它变成一个**显式的评估步骤**。工程含义很直接——**有了评估步，才挂得上"质量检查"**：输出是否满足需求？是否需要 Reflexion 那一轮反思（见 [19](19-ReAct循环与推理范式家族.md)）？是否需要回退重做？
> **没这一步的 Agent，只有"停止"，没有"判断"。**

## 三、Runtime 五层：职责边界速查

| 层 | 职责 | 关键组件 | 面试常问 |
| :--- | :--- | :--- | :--- |
| **LLM 管理层** | 模型路由、Token 管理、重试与降级 | Model Router / Token Counter / Retry Policy | 多模型怎么路由？降级链是什么？ |
| **工具注册层** | 工具定义、参数校验、权限控制、调用日志 | Tool Registry / Validator / Permission Guard | `description` 怎么影响选中率？参数校验谁做？ |
| **记忆管理层** | 短期（窗口）/ 长期（向量库）/ 工作记忆 | Context Window / Vector DB / Session Store | 三层记忆怎么协同？ |
| **执行调度层** | Loop 引擎、并发控制、超时与熔断 | Loop Engine / Concurrency Pool / Circuit Breaker | 怎么防死循环？ |
| **可观测层** | Tracing、Metrics、Logging、Debug | OpenTelemetry / Dashboard / Debug UI | 多步调用怎么定位是哪一步坏了？ |

> ⚠️ **最常考的一个"不包括"**：Runtime **不执行 LLM 推理计算（前向传播）**。推理由模型服务端（OpenAI API / 本地 vLLM）完成，**Runtime 只负责调用 API 并处理响应**。

**主流框架对比（了解即可，选型时用）**

| 框架 | 核心思路 | Loop 模式 | 记忆管理 | 工具生态 |
| :--- | :--- | :--- | :--- | :--- |
| **LangChain** | 链式组合、模块化 | ReAct + 自定义 | 短期/长期/工作记忆 | 200+ 内置工具 + MCP |
| **AutoGen** | 多 Agent 对话协作 | 对话式循环 | 对话历史压缩 | 自定义 + 代码执行 |
| **CrewAI** | 角色扮演、流程编排 | 顺序/并行/层级 | 短期记忆 | 工具定义装饰器 |
| **OpenAI Agents SDK** | 轻量级、Handoff 交接 | 单 Agent 循环 | 对话历史 | Function Calling |
| **Google ADK** | 端到端、多模态 | ReAct + 反思 | 内置记忆模块 | Google 工具生态 |

> 原文选型建议：企业级 / 多智能体协作推荐 **Google ADK**（原生多智能体编排 + 内置 Google 工具生态 + 清晰异步工作流）；多 Agent 协作也可考虑 AutoGen / CrewAI；追求轻量选 OpenAI Agents SDK；常规场景 LangChain 生态也能覆盖。

## 四、沙箱隔离技术：五级方案怎么选

| 级别 | 技术 | 隔离强度 | 启动 | 隔离边界 | 选它当 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **进程级** | `subprocess` + `ulimit`/`cgroups` | 🟡 低 | ⚡ 毫秒 | 同一内核、同一文件系统 | 简单代码执行、快速验证 |
| **容器级** | Docker / gVisor / Podman | 🟢 中 | ⚡ 秒级 | **共享宿主机内核**，隔离在进程/文件系统层 | Web 应用、API 服务、多租户 |
| **微虚拟机** | Firecracker / Kata Containers | 🔴 高 | ⏱ 125ms~秒 | **每个沙箱独立内核** | 金融/医疗等高安全场景 |
| **WebAssembly** | Wasmtime / Wasmer | 🟢 中 | ⚡ 毫秒 | 字节码级，无系统调用 | 浏览器端执行、轻量计算 |
| **云沙箱** | E2B / Modal / Daytona / CubeSandbox | 🟢 中高 | ⚡ 秒级（托管） | 由服务方维护 | 不想自建沙箱的开发者 |

**Docker vs Firecracker（八股 Q3，高频）**

| 维度 | Docker（容器级） | Firecracker（微虚拟机） |
| :--- | :--- | :--- |
| **隔离原理** | **共享宿主机内核**，隔离在进程/文件系统层面 | **每个沙箱运行独立内核** |
| **逃逸难度** | 内核漏洞可逃逸 | **内核级隔离，逃逸难度极高** |
| **启动速度** | 秒级 | 约 **125ms** |
| **资源开销** | 小 | **更大** |

> **选型原则（可直接背）**：金融/医疗等高安全场景选 **Firecracker**；一般 Web 场景 **Docker 够用**；不想自建选 **E2B / Modal 等云沙箱**。

**黄金法则：最小权限原则**

> **默认拒绝一切，按需开白。**

| 绝对不能暴露给 Sandbox 的资源 | 一旦暴露的后果 |
| :--- | :--- |
| **宿主机 Docker Socket**（`/var/run/docker.sock`） | 容器内一条命令就能起特权容器 → **彻底逃逸** |
| **云厂商元数据 API**（169.254.169.254） | 可读取实例的临时凭证 → 拿到云账号权限 |
| **内网服务发现端口** | 从沙箱横向移动到内网其他服务 |
| **SSH 私钥目录**（`~/.ssh`） | 直接拿到其他机器的登录权 |

## 五、工业级沙箱：Claude Code 的三层纵深防御

**为什么必须三层**：单层都有各自绕过路径——静态分析绕不过混淆、权限引擎绕不过 OS 漏洞、OS 隔离挡不住"合法命令的恶意效果"（如 `core.fsmonitor`）。**纵深 = 每层补另一层的漏。**

```

                         └──────────┬───────────┘

                                    ▼
                  ┌─────────────────────────────────┐
                  │      第一层：命令安全检查       │

                  └──────────────┬──────────────────┘
                                 │
                    ┌────────────┴────────────┐
                    │                         │
                   通过                    检测到威胁
                    │                         │
                    ▼                         ▼
        ┌───────────────────────────┐    ┌────────────────────┐
        │    第二层：权限决策       │    │ 阻断：返回安全告警 │
        │  shouldUseSandbox()       │    └────────────────────┘
        │  三步决策                 │
        │  auto-allow / regular /   │
        │  disabled                 │
        └─────────────┬─────────────┘
                      │
              ┌───────┴───────────────┐
              │                       │

              │                       │
              ▼                       ▼
┌───────────────────────────────┐   ┌──────────────────────┐
│      第三层：OS 沙箱执行      │   │ 降级：要求用户确认   │
│ Seatbelt / Bubblewrap         │   └──────────────────────┘
│ + seccomp                     │
```

**① 第一层：命令安全检查（应用级静态分析）**

> 相当于在门口过安检，**完全在 JS/TS 代码中完成**——23+ 验证器 + AST 解析，检测注入、混淆、危险路径。

**② 第二层：权限决策引擎（沙箱入口）**

核心是 `shouldUseSandbox()` 的三步决策：

```
Step 1：沙箱是否启用？
│
├─ 否
│   └─→ 降级为 ask 模式（要求用户手动确认）
│
└─ 是
    ↓
Step 2：是否显式禁用沙箱？
│   - dangerouslyDisableSandbox
│   - 受 allowUnsandboxedCommands 限制
│
├─ 是（且允许禁用） └─→ 进入后续执行流程
│
└─ 否
    ↓
Step 3：是否在排除列表？
    - 匹配 excludedCommands
    - 用户便利功能，非安全边界
    - 支持复合命令拆分匹配
    ↓
进入沙箱执行
├─ auto-allow：自动执行
└─ regular：需用户确认
```

**三种沙箱模式**

| 模式 | 行为 | 适用场景 |
| :--- | :--- | :--- |
| **auto-allow** | 沙箱内命令自动执行，无需确认 | 可信项目、日常开发 |
| **regular** | 每条命令需用户确认后执行 | 新项目、敏感环境 |
| **disabled** | 不使用沙箱，所有命令需确认 | 沙箱不可用或用户显式关闭 |

> 注意 Step 3 那句话：**excludedCommands 是"用户便利功能，非安全边界"**——这句话本身是设计文档里的一句诚实说明。**把便利开关当成安全边界，是很多系统出事的根因。**

**③ 第三层：OS 沙箱执行（系统级隔离）**

| 平台 | 沙箱技术 | 原理 | 依赖 |
| :--- | :--- | :--- | :--- |
| **macOS** | Seatbelt（`sandbox-exec`） | 内核级沙箱配置文件，限制文件系统访问、网络、系统调用 | 系统内置，零安装 |
| **Linux/WSL2** | Bubblewrap + seccomp | `bwrap` 创建挂载命名空间（文件系统隔离），`seccomp` 过滤系统调用 | 需 `apt install bubblewrap socat` |
| **Windows** | PowerShell 沙箱包装 | `pwsh -NoProfile -NonInteractive -EncodedCommand` 预包装 | 系统内置 |

**文件系统三级控制（Bubblewrap 挂载命名空间）**

| 级别 | 参数 | 范围 | 例子 |
| :--- | :--- | :--- | :--- |
| **可写** | `--bind` | Agent 可读写 | 项目目录、`/tmp` |
| **只读** | `--ro-bind` | Agent 可读不可写 | 系统库、`/usr/bin` |
| **屏蔽** | `--dev-null` | Agent **完全不可见** | 敏感路径 |

> 特别地，Claude Code **禁止写入 `settings.json` 和 `.claude/skills/`**——**防止 Agent 修改自身配置实现沙箱逃逸**。
> 这条和 [17](17-Prompt模板化与PromptOps.md) 的模板化正好接上：**模板/Skill 是 Agent 的"行为定义"，允许它改，等于允许它重写自己的约束。**

**网络隔离：白名单代理，而不是断网**

| 通道 | 机制 | 作用 |
| :--- | :--- | :--- |
| **HTTP 代理**（`httpProxyPort`） | MITM 代理拦截 HTTP 请求，**只允许 `allowedDomains`** | 精确控制 HTTP 出站 |
| **SOCKS 代理**（`socksProxyPort`） | 拦截 TCP 连接，**非白名单域名直接拒绝** | 覆盖非 HTTP 的 TCP 流量 |
| **Unix Domain Sockets** | 通过 **seccomp 阻断** | 防 `/var/run/docker.sock` 逃逸 |

> 效果：Agent 可以 `npm install`（npm registry 在白名单里），但**不能 `curl http://evil.com`**。
> **设计取舍**：断网最安全但会废掉 Agent 的大部分能力；**白名单代理是"可用性 vs 安全"的折中**。

**🚨 裸 Git 仓库攻击防护（真实攻击向量，值得单独记）**

| 环节 | 内容 |
| :--- | :--- |
| **攻击手法** | 攻击者创建一个**裸 Git 仓库**，设置 `core.fsmonitor` 指向恶意脚本。当 Agent 在该仓库中执行 `git status` 时，**Git 会自动执行 `core.fsmonitor` 指定的脚本** |
| **为什么危险** | 它**绕过了沙箱的命令检查**——被检查的是 `git status`（一个完全无害的命令），恶意行为发生在 Git 内部 |
| **防御** | `scrubBareGitRepoFiles()` 在**进入沙箱前**扫描并清除裸 Git 仓库的危险配置文件 |

> **这一类攻击的通用教训**：**"命令文本安全"不等于"命令行为安全"。** 可信工具（git、npm、make）本身会读配置、跑脚本——所以静态分析必须区分"我能检查的字面"和"工具会执行的副作用"。

## 六、Loop 稳定性：心跳、Checkpoint 与熔断

**心跳检测与空闲超时**

```javascript
// 空闲超时配置
const IDLE_TIMEOUT_MS = 10 * 60 * 1000; // 10 分钟

// Loop 中心跳检测
let lastActivityTime = Date.now();

function checkHeartbeat() {
  const idle = Date.now() - lastActivityTime;
  if (idle > IDLE_TIMEOUT_MS) {
    return {
      action: 'pause',
      reason: `空闲超过 ${IDLE_TIMEOUT_MS / 60000} 分钟,自动暂停`,
      canResume: true
    };
  }
  return { action: 'continue' };
}

// 用户交互时重置计时器
function onUserActivity() {
  lastActivityTime = Date.now();
}
```

> **关键设计：`canResume: true`。** 停不是"终止"而是"暂停"——否则用户回来发现任务没了，体验比烧点钱更糟。

**五种保障机制（与 [19 §四](19-ReAct循环与推理范式家族.md) 六件套互补）**

| 保障机制 | 解决的问题 | 关键参数 | 触发后 |
| :--- | :--- | :--- | :--- |
| **上下文溢出熔断** | Context 无限增长导致 API 报错 | `max_context_tokens = 120K` | 熔断并压缩（呼应 [18](18-上下文工程与消息裁剪.md)） |
| **死循环检测** | 工具反复失败导致 Loop 卡死 | `max_turns = 20`，`max_tool_errors = 3` | 终止并返回中间结果 |
| **压缩降级链** | 压缩失败导致历史丢失 | AI → 规则 → 硬截断 | 降级到下一档 |
| **Checkpoint 恢复** | 中断后无法继续任务 | 状态序列化 + 反序列化 | 从断点续跑 |
| **心跳检测** | 用户离开后 Agent 继续烧钱 | `idle_timeout = 10min` | 暂停（可恢复） |

> **Checkpoint 是"长时间任务"的门槛能力**：没有序列化，Agent 只要中断一次，之前所有步都白跑——这是"能演示"和"能交付"的分界线之一。

**三者协同（原文的集成代码骨架）**

```python
class SecureAgent:
    """完整集成：AgentLoop + Runtime（ToolRegistry + Memory） + SandboxExecutor"""

    def __init__(self, llm, sandbox: SandboxExecutor):
        self.loop = AgentLoop(llm, tools=[], memory=InMemoryMemory(), max_turns=10)
        self.registry = ToolRegistry()
        self.sandbox = sandbox

        # 注册工具：代码生成（在 Sandbox 中执行）
        self.registry.register(
            name="execute_code",
            description="在安全沙箱中执行Python代码",
            parameters={"code": {"type": "string", "required": True, "description": "Python代码"}},
            handler=lambda args: self.sandbox.execute_in_sandbox(
                "code_execution", "execute_code", args["code"]),
            allowed_roles=["assistant"],
        )

        # 注册工具：搜索
        self.registry.register(
            name="web_search",
            description="搜索网页内容",
            parameters={"query": {"type": "string", "required": True}},
            handler=lambda args: search_web(args["query"]),
            allowed_roles=["*"],
        )

        self.loop.tools = self.registry.tools

    def run(self, user_input: str) -> str:
        """运行完整的 Agent 系统"""
        return self.loop.run(user_input)
```

> **这段代码的看点是 `handler` 和 `allowed_roles`**：
> - `handler=lambda args: self.sandbox.execute_in_sandbox(...)` —— **危险工具的执行被强制绑到沙箱**，不是"记得调沙箱"，而是**工具定义里就写了沙箱**。
> - `allowed_roles=["assistant"]` vs `["*"]` —— **同一次注册里就区分了权限粒度**：执行代码只给 assistant，搜索谁都能用。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| Runtime 层负责执行 LLM 推理计算 | **不包括**。推理由模型服务端完成，Runtime 只调 API 并处理响应 |
| Loop / Runtime / Sandbox 是并列的三层 | 严格**嵌套**：Sandbox 最外 → Runtime 中间 → Loop 最内 |
| Agent Loop 就是五步 | 六步——多了 **Evaluate 评估**；五步版把"是否结束"隐含在 `tool_calls` 里，六步把它显式化 |
| Docker 和 Firecracker 差不多，都是"容器" | Docker **共享宿主机内核**（可逃逸）；Firecracker **每个沙箱独立内核**（逃逸极难），代价是资源开销更大 |
| 沙箱就是要"断网" | 断网会废掉大部分能力；工业做法是**代理 + 域名白名单**（能 `npm install`，不能 `curl evil.com`） |
| 命令文本安全 = 命令行为安全 | **不等价**。`git status` 会执行 `core.fsmonitor` 指向的脚本——这是绕过命令检查的真实路径 |
| `excludedCommands` 是安全边界 | 原文自己写明：**"用户便利功能，非安全边界"**——把它当安全边界是出事根因 |
| 隔离强度越高越好 | 强度与启动速度/资源开销成反比（微虚拟机 125ms~秒级、开销更大）；**按场景选** |
| 记忆分页 / Checkpoint 是可选项 | 长时间任务里 Checkpoint 是**门槛能力**——中断即全部白跑 |
| 心跳超时就直接终止任务 | 应该是**暂停且可恢复**（`canResume: true`），否则用户体验比多花点钱更糟 |

## 🎤 面试怎么答（口述模板）

> **问：Agent 的 Runtime 是什么？和 Agent Loop 什么关系？**
> "我会用三层嵌套来回答：**Sandbox 在最外层，Runtime 在中间，Agent Loop 在最内层**，它们是严格的嵌套关系而不是并列。
> 分工是：**Agent Loop 决定"做什么"**——LLM 驱动的感知、推理、规划、执行、观察、评估六步循环；**Runtime 决定"怎么做"**——把逻辑语义转成可执行计算的基础设施；**Sandbox 决定"在哪里做、在什么约束下做"**。
> Runtime 本身是五层架构：LLM 管理层（模型路由、token 管理、重试降级）、工具注册层（定义、参数校验、权限、日志）、记忆管理层（短期/长期/工作）、执行调度层（Loop 引擎、并发、超时熔断）、可观测层（Tracing、Metrics）。
> 有一点容易答错：**Runtime 不执行 LLM 推理的前向传播**——推理在模型服务端，Runtime 只负责调 API 和处理响应。"

> **追问：沙箱方案怎么选？**
> "看隔离强度和启动开销的权衡。**进程级**（subprocess + ulimit）毫秒级但隔离弱，只适合简单验证；**容器级**（Docker/gVisor）秒级、隔离中等、开销小，适合 Web 应用和多租户；**微虚拟机**（Firecracker/Kata）每个沙箱跑独立内核，逃逸难度极高，代价是启动 125ms 到秒级、资源开销更大，适合金融医疗这类高安全场景；还有 **WASM**（毫秒级、适合轻量计算）和**云沙箱**（E2B/Modal，不想自建就用托管）。
> 核心区别是 **Docker 共享宿主机内核，内核漏洞可以逃逸；Firecracker 每个沙箱独立内核**。"

> **追问：只用一个沙箱够吗？**
> "不够，单层都有绕过路径，工业级是**三层纵深**。第一层是**应用级的命令静态分析**——23 个以上验证器加 AST 解析，查注入、混淆、危险路径。第二层是**权限决策引擎** `shouldUseSandbox()` 的三步决策：沙箱启没启用、有没有显式禁用、在不在排除列表，最后落到 auto-allow / regular / disabled 三种模式。第三层是 **OS 级隔离**——macOS 用 Seatbelt，Linux 用 Bubblewrap 建挂载命名空间加 seccomp 过滤系统调用，文件系统分三级：`--bind` 可写、`--ro-bind` 只读、`--dev-null` 完全屏蔽。
> 还有个必须提的点：**命令文本安全不等于命令行为安全**。有个真实攻击向量是在裸 Git 仓库里设置 `core.fsmonitor` 指向恶意脚本——Agent 跑 `git status` 时 Git 会自动执行那个脚本，完全绕过命令检查。防御是在进沙箱前扫描清除裸仓库的危险配置。
> 另外网络隔离不是断网，而是 **HTTP/SOCKS 代理加域名白名单**，这样 Agent 能 `npm install`，但不能 `curl evil.com`。"

> **追问：长时间运行的 Agent 要注意什么稳定性问题？**
> "五个机制：**上下文溢出熔断**（`max_context_tokens` 到 120K 就熔断压缩）、**死循环检测**（`max_turns=20`、连续工具错误 3 次终止）、**压缩降级链**（AI → 规则 → 硬截断）、**Checkpoint 恢复**（状态序列化，中断后从断点续跑）、**心跳检测**（空闲 10 分钟自动暂停）。
> 我觉得 **Checkpoint 是"能演示"和"能交付"的分界线**——没有序列化，Agent 中断一次前面全白跑。还有心跳要设计成**暂停且可恢复**，不是直接终止，否则用户回来发现任务没了，体验比多花点钱更糟。"
