## 🎯 30 秒结论

1. **LLM-Wiki 的一句话定义**：用**文件系统代替向量检索**，用**自然语言代替微调**——知识被编译一次并持续维护，而不是每次查询重新推导。
2. **三层架构**：`Raw Sources`（原始资料，不可变）→ `Wiki`（LLM 提取整理、互相链接的知识页）→ `Schema`（结构规则，元知识）。
3. **三个操作**驱动整个系统：**Ingest（消化）/ Query（查询）/ Lint（检查）**。
4. **和 RAG 的关系是互补不是互斥**：**LLM-Wiki 适合"规则少但重要"，RAG 适合"量大但需要筛选"**。工程上通常组合：AGENTS.md 放核心规则 + RAG 放海量文档 + LLM-Wiki 放整理过的知识体系。
5. **两种实现形态**：**Agent 内嵌式**（Markdown/Skill，轻量、人机共读、易迁移）vs **独立知识系统**（UI + 索引 + API/MCP，多数据源、可视化、多 Agent 共享）。区别不在"Skill 还是桌面应用"，而在**知识是 Agent 的一部分还是独立基础设施**。
6. **AGENTS.md 是项目的"宪法"**（身份/规则/红线/工具偏好/环境/流程），**SOUL.md 是人格**（语气与风格，通常 System Prompt 第一段，可被 prompt cache 缓存）。
7. **四信号关联度**：直接链接 ×3.0、来源重叠 ×4.0、Adamic-Adar ×1.5、类型亲和 ×1.0。
8. **多阶段检索管线**：分词 → 向量语义（可选）→ 图谱扩展（2 跳衰减）→ **预算控制**（Wiki 60% / 历史 20% / 索引 5% / 系统提示 15%）→ 上下文组装（编号引用 [1][2]）。
9. **两步 CoT Ingest**：先分析出结构化 JSON，再生成 Wiki 文件——**分析与生成是不同认知任务，分开后各自质量更高**。
10. **Lint 是知识库的体检**：孤立页面、断链、索引一致性、AI 级矛盾检测、置信度标注（EXTRACTED/INFERRED/AMBIGUOUS/UNVERIFIED）。

**① 起源与一句话定义（原文）**

> LLM-Wiki 最初由 Andrej Karpathy 在其 [llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) 中提出，核心理念是：**用文件系统代替向量检索，用自然语言代替微调，让知识被编译一次、持续维护**。传统 RAG 每次查询都从头检索和回答，而 LLM-Wiki 让 LLM 增量构建并维护一个持久化的知识库——知识只编译一次并持续更新，而非每次查询都重新推导。
>
> **一句话定义**：LLM-Wiki = 存放在项目目录中的 Markdown 文件体系，Agent 启动时自动读取并注入 System Prompt，让 Agent 无需微调就能"知道"项目的一切。延伸到广义实现，LLM-Wiki 也是一种让 AI 持续构建和维护个人知识库的方法论。

**② 三层架构（原文）**

> **Raw Sources（原始资料层）**：用户提供的文档、链接、笔记，存放在 `raw/` 目录，不可变。这是知识的"源头"。
> **Wiki（知识页面层）**：LLM 从原始资料中提取、整理、互相链接的知识页面。包含实体页、主题页、资料摘要页。每次有新素材加入，Wiki 增量更新而非重建。
> **Schema（规则层）**：定义 Wiki 的结构规则、页面类型、分类方式。Schema 是"元知识"——关于知识本身的知识。
>
> 三个核心操作：**Ingest（消化）**新素材进入，LLM 分析并生成 Wiki 页面；**Query（查询）**基于已有 Wiki 内容回答问题，而非重新阅读原始文件；**Lint（检查）**定期检查 Wiki 健康度——孤立页面、断链、矛盾信息。

**③ 与 RAG 的边界（原文）**

> **LLM-Wiki 适合"规则少但重要"的知识，RAG 适合"量大但需要筛选"的知识**。两者互补，不互斥。在实际工程中，Agent 项目通常组合使用：AGENTS.md 放核心规则，RAG 放海量文档，LLM-Wiki 知识库管理系统放整理过的知识体系。

**④ 两种形态对比（原文）**

> 形态一 **Agent 内嵌式**：轻量（只要 Markdown 和目录结构）、Agent 原生（与代码同处一个工作空间）、易于迁移（与模型解耦）、人机共读（可用 Obsidian 管理）。知识库是 **Agent 工作环境的一部分**。
> 形态二 **独立知识系统**：知识服务独立化（自建解析/索引/检索）、多数据源（PDF/DOCX/PPTX/网页）、可视化管理（知识树、全文搜索、关系图谱）、Agent 解耦（多 Agent 通过 API/MCP 共享同一套知识库）。
> 真正的区别：**Knowledge = Agent 的一部分** vs **Knowledge = 独立基础设施**。前者强调**让 Agent 自己拥有知识**，后者强调**把知识能力建设成 Agent 可以调用的服务**。

**⑤ AGENTS.md 核心内容（原文）**

> **项目身份**：这是什么项目、用什么语言/框架
> **行为规则**：代码风格、提交规范、测试要求
> **安全红线**：不能删除的数据、不能修改的配置
> **工具偏好**：用 `pnpm` 不用 `npm`，用 `trash` 不用 `rm`
> **环境信息**：Node 版本、Python 版本、数据库类型
> **工作流程**：先跑测试再提交、先建分支再开发

**⑥ SOUL.md 示例（原文）**

```markdown
# SOUL.md
你是一个务实、高效的工程助手。
## 语气
- 直接给方案，不废话
- 用代码说话，不用文字描述代码
- 犯了错就认，不找借口
## 风格
- 先问"要解决什么问题"，再给方案
- 涉及破坏性操作必须确认
- 不确定的事情说"不确定"，不编造
```

> SOUL.md 在 Agent 框架中通常作为 System Prompt 的第一段注入，影响 Agent 的所有后续交互。Claude Code 的 System Prompt 分区设计中，SOUL.md 对应静态全局段——内容固定，可被 prompt cache 缓存。

**⑦ 标准目录结构（原文）**

```text
my-wiki/
├── purpose.md        # 研究方向：目标、关键问题、研究范围
├── schema.md         # Wiki 结构规则：页面类型、分类方式
├── index.md          # 内容目录（LLM 导航入口）
├── log.md            # 操作历史（可解析的时序记录）
├── overview.md       # 全局概要（每次 ingest 后自动更新）
├── raw/              # 原始素材（不可变）
│   ├── articles/ ├── tweets/ ├── wechat/ ├── pdfs/ ├── notes/ └── assets/
├── wiki/             # AI 生成的知识库
│   ├── entities/  ├── topics/  ├── sources/
│   ├── comparisons/ ├── synthesis/ └── queries/
├── .wiki-schema.md   # 配置文件
└── .wiki-cache.json  # SHA256 去重缓存
```

**⑧ 四信号关联度模型（原文表）**

| 信号 | 权重 | 描述 |
| :--- | :--- | :--- |
| **直接链接** | ×3.0 | 通过 `[[wikilinks]]` 链接的页面 |
| **来源重叠** | ×4.0 | 共享同一原始资料的页面（通过 frontmatter `sources[]`） |
| **Adamic-Adar** | ×1.5 | 共享共同邻居的页面（按邻居度数加权） |
| **类型亲和** | ×1.0 | 相同页面类型的加分（实体↔实体，概念↔概念） |

**⑨ 多阶段检索管线（原文）**

> **阶段 1 分词搜索**：英文分词 + 停用词过滤；中文 **CJK 二元组**分词；标题匹配加分（+10）；同时搜索 `wiki/` 和 `raw/sources/`
> **阶段 1.5 向量语义搜索（可选）**：任意 OpenAI 兼容 `/v1/embeddings` 端点；存 **LanceDB** 做 ANN；余弦相似度发现无关键词重叠的语义相关页
> **阶段 2 图谱扩展**：搜索结果作种子；四信号关联度发现相关页；**2 跳遍历带衰减**
> **阶段 3 预算控制**：上下文窗口 4K→1M 可配；比例 **60% Wiki / 20% 聊天历史 / 5% 索引 / 15% 系统提示**；按"搜索分 + 图谱关联度"综合排序
> **阶段 4 上下文组装**：编号页面附**完整内容**（非仅摘要）；系统提示含 purpose.md、语言规则、引用格式、index.md；LLM 按编号引用 [1][2]

**⑩ Lint 与隐私边界（原文）**

> **Lint**：孤立页面（无双向链接）· 断链（指向不存在页面的 `[[wikilink]]`）· 索引一致性（index.md 与实际文件是否匹配）· **AI 级矛盾检测**（不同页面间的事实矛盾）· 置信度标注（EXTRACTED / INFERRED / AMBIGUOUS / UNVERIFIED）
> **隐私边界**：知识库文件和离线图谱输出**始终留在本地机器**；请求 Agent 回答/摄入时，prompts、选中引用、检索片段、工具输出和生成产物**可能发送到模型提供商**；**API 密钥不存储在 llm-wiki 自身配置中**；本地工作台访问需同时通过来源检查和启动凭据检查。

**⑪ 八股 Q4（原文）**

> **两步思维链摄入**：Karpathy 原始设计是单步摄入——LLM 同时阅读和写入。工业级实现拆两步：Step 1（分析）LLM 阅读素材输出结构化分析 JSON（关键实体、核心论点、与现有 Wiki 的关联、矛盾、结构建议）；Step 2（生成）LLM 基于分析结果生成 Wiki 文件。好处：① 分析和生成是不同认知任务，分离后各自质量更高；② 分析结果可被缓存和审查；③ 支持长内容的链式思考。工程上还配合 **SHA256 增量缓存和持久化队列**。

## 一、为什么需要 LLM-Wiki：RAG 补不上的那块

| 维度 | RAG | LLM-Wiki |
| :--- | :--- | :--- |
| **适配知识** | **量大但需要筛选** | **规则少但重要** |
| **知识形态** | 海量文档 → 切块 → 向量 | 少量高价值知识 → 编译成结构化页面 |
| **每次查询** | 重新检索 + 重新推导 | 读已编译好的页面（**编译一次，持续维护**） |
| **强项** | 覆盖广、能处理海量资料 | **稳定、可审计、人机共读、可增量维护** |
| **弱项** | 检索不准就全错；同一问题答案可能漂移 | 规模受限，不适合海量原始资料 |

> **关键差别的一句话**：RAG 是"**每次都从原料现场加工**"，LLM-Wiki 是"**加工一次存进仓库，之后取用并持续盘点**"。
> **为什么"规则少但重要"的那部分不能靠 RAG**：项目约定、安全红线、工具偏好这类内容，**每次检索都可能漏、或召回顺序一变答案就变**。它们需要的是**稳定注入**，不是相似度排序——所以它们进 AGENTS.md / Wiki 页，不进向量库。

## 二、三层架构与三个操作

```
raw/  （原始资料 · 不可变 —— 知识的源头）
   │  Ingest：LLM 分析 + 生成
   ▼
wiki/ （实体页 · 主题页 · 资料摘要页 · 对比页 · 综合分析页）
   │  Query：基于已有页面回答，不重读原始文件
   ▼
 答案（带 [[wikilink]] 与来源引用）
   ▲
   └── Lint：孤立页 / 断链 / 索引一致性 / 矛盾检测 / 置信度标注

schema.md + purpose.md 贯穿全程：前者定结构，后者定方向
```

| 层 / 操作 | 关键点 | 容易忽略的设计理由 |
| :--- | :--- | :--- |
| **Raw Sources** | `raw/` **不可变** | 保留可追溯的证据链——Wiki 错了能回到源头重编 |
| **Wiki** | **增量更新而非重建** | 重建会丢失人工修订，也会让成本随资料量线性爆炸 |
| **Schema** | 页面类型与分类方式 | "元知识"——**没有它，LLM 每次生成的页面结构都不一样，无法互相链接** |
| **Ingest** | 新素材 → 分析 → 生成页面 | 两步法（见 §五） |
| **Query** | 基于 Wiki 回答，**不重读原始文件** | 这正是"编译"的收益：查询成本与资料总量解耦 |
| **Lint** | 五项健康检查 | **知识库不体检就会腐烂**——和代码不 lint 一样 |

## 三、两种实现形态：怎么选

```
                LLM-Wiki
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     Agent 内嵌式          独立知识系统
          │                   │
   Knowledge =            Knowledge =
   Agent 的一部分          独立基础设施
          │                   │
   Markdown / Skill       UI + Index + API/MCP
```

| 维度 | Agent 内嵌式 | 独立知识系统 |
| :--- | :--- | :--- |
| **形态** | 项目里的 Markdown / Skill / 规则文件 | 独立应用（解析 + 索引 + 检索 + UI + API） |
| **轻量性** | ✅ 只要文件和目录，无后端 | ❌ 要装应用、要维护索引 |
| **数据源** | 主要是 Markdown | ✅ PDF / DOCX / PPTX / 网页等多源 |
| **人机共读** | ✅ Obsidian 直接打开 | ✅ 知识树 / 全文搜索 / 关系图谱 / 预览 |
| **多 Agent 共享** | 靠文件复制或软链 | ✅ 多 Agent 经 API / MCP 共享同一套 |
| **迁移性** | ✅ 与模型、平台解耦 | 取决于应用 |
| **适合** | **个人 / 单项目的知识内嵌** | **规模更大的个人知识库或团队知识系统** |

> **面试要点**：别把区别说成"Skill 和桌面应用的区别"——**本质是"知识是 Agent 的一部分"还是"知识是 Agent 可调用的服务"**。前者让 Agent 自己拥有知识，后者把知识能力做成基础设施。

## 四、AGENTS.md 与 SOUL.md：一个管规则，一个管人格

| 文件 | 管什么 | 内容 | 工程细节 |
| :--- | :--- | :--- | :--- |
| **AGENTS.md** | **项目"宪法"**（硬规则） | 项目身份 · 行为规则 · **安全红线** · 工具偏好 · 环境信息 · 工作流程 | 通常放项目根目录，Agent 启动时读取注入 |
| **SOUL.md** | **人格**（软风格） | 语气 · 风格 · 交互准则（如"涉及破坏性操作必须确认""不确定的事情说不确定"） | System Prompt **第一段**；对应 Claude Code 分区里的**静态全局段** → 内容固定 → **可被 prompt cache 缓存** |

> **为什么 SOUL.md 要单独拆出来、并放在 System Prompt 最前面**（呼应 [17](17-Prompt模板化与PromptOps.md)）：**prompt cache 只对前缀生效**，把最稳定的人格段放在最前，后面变化的部分才不会让整段缓存失效。
> **AGENTS.md 里的"安全红线"要单列**：它和 [23](23-Harness工程与六大组件.md) 的 approval-hook 是**互补的两道**——AGENTS.md 让 Agent **不想**做，Hooks 让它 **做不了**。

**标准目录里几个容易被问到的文件**

| 文件 | 作用 | 为什么需要 |
| :--- | :--- | :--- |
| **purpose.md** | 目标、关键问题、研究范围、演进中的论点 | Karpathy 原始设计有 Schema 却没有"**为什么存在**"；purpose 是**方向意图**，schema 是**结构规则** |
| **index.md** | 内容目录 + **LLM 导航入口** | LLM 先读 index 才知道有哪些页面、该读哪些——**相当于知识库的"目录页缓存"** |
| **log.md** | 时序操作记录（可解析） | 审计与回溯：每次 ingest/query/lint 都有据可查 |
| **overview.md** | 全局概要 | **每次 ingest 后自动重生成**，反映最新状态 |
| `.wiki-cache.json` | **SHA256 去重缓存** | 同一素材不重复 ingest，省 Token |

## 五、四信号关联度 + 多阶段检索管线

### 四信号关联度模型

| 信号 | 权重 | 直觉解释 |
| :--- | :--- | :--- |
| **来源重叠** | **×4.0** | 出自同一篇原始资料 → 最强关联（同一份证据） |
| **直接链接** | ×3.0 | 作者/LLM 显式写的 `[[wikilink]]` → 显式关联 |
| **Adamic-Adar** | ×1.5 | 共享共同邻居，**按邻居度数加权**（共同邻居越"稀有"越可信） |
| **类型亲和** | ×1.0 | 实体↔实体、概念↔概念加分（弱信号，只做微调） |

> **权重顺序值得记**：**来源重叠 > 直接链接 > 共同邻居 > 类型亲和**。理由是"出自同一份资料"是**客观证据**，而链接是**主观判断**——客观证据权重更高。

### 多阶段检索管线

| 阶段 | 做什么 | 关键设计 |
| :--- | :--- | :--- |
| **1 分词搜索** | 英文分词 + 停用词；中文 **CJK 二元组**；标题匹配 **+10** | 中文不做二元组分词就会漏召回（中文无空格） |
| **1.5 向量语义（可选）** | OpenAI 兼容 `/v1/embeddings` + **LanceDB** ANN | 补"**没有关键词重叠但语义相关**"的页面 |
| **2 图谱扩展** | 以搜索结果为种子，四信号关联度 + **2 跳带衰减** | 衰减是为了**不让弱关联无限扩散** |
| **3 预算控制** | Wiki **60%** / 聊天历史 **20%** / 索引 **5%** / 系统提示 **15%** | 呼应 [18](18-上下文工程与消息裁剪.md)——**上下文是预算，不是容器** |
| **4 上下文组装** | 编号页面附**完整内容**；要求按 [1][2] 引用 | 附全文而非摘要，是为了**可溯源** |

> **与 RAG 管线的对照**：RAG 是"检索 → 重排 → 组装"，LLM-Wiki 多了一层**图谱扩展**和一层**预算分配**——因为它的检索对象既有关键词/向量结果，还有**结构化页面之间的关系**。

### 两步 CoT Ingest：为什么要拆

| | Step 1 分析 | Step 2 生成 |
| :--- | :--- | :--- |
| **输入** | 原始素材 + 现有 Wiki 上下文 | Step 1 输出的结构化 JSON |
| **输出** | 关键实体 / 核心论点 / 与现有 Wiki 的关联 / 矛盾 / 结构建议 | 资料摘要页、实体页、概念页、索引更新 |
| **认知任务** | **理解与判断** | **写作与组织** |

> **拆分的三条好处**：① 分析和生成是**不同认知任务**，分开后各自质量更高；② 分析结果**可被缓存和审查**（人能先检查 JSON 再决定要不要生成）；③ 支持**长内容的链式思考**。工程上再配 **SHA256 增量缓存 + 持久化队列**，就不会重复烧 Token、也不会中途丢任务。

## 六、Lint 与隐私边界

| Lint 项 | 检查什么 | 类比 |
| :--- | :--- | :--- |
| **孤立页面** | 没有任何双向链接的页面 | 代码里的"死代码" |
| **断链** | 指向不存在页面的 `[[wikilink]]` | 代码里的"空引用" |
| **索引一致性** | `index.md` 与实际文件是否匹配 | 目录与文件对不上 |
| **AI 级矛盾检测** | 不同页面间的**事实矛盾** | 只有 LLM 能做——传统 linter 查不出语义冲突 |
| **置信度标注** | EXTRACTED / INFERRED / AMBIGUOUS / UNVERIFIED | 标注知识来源可信度，避免把"推断"当"事实" |

> **置信度标注最容易被忽略，但最有价值**：它把"这篇内容是从原文提取的"和"这是 LLM 推断的"区分开——**没有它，Wiki 用久了就分不清哪些是真知识、哪些是模型编的**。

**隐私边界（三条，可直接背）**

1. **知识库文件和离线图谱输出始终留在本地机器**；
2. 但**请求 Agent 回答/摄入/生成时**，prompts、选中引用、检索片段、工具输出和生成产物**可能发往模型提供商**；
3. **API 密钥不存储在应用自身配置中**；本地工作台访问需同时通过**来源检查 + 启动凭据检查**，不受信任的网页读不到也改不了。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| LLM-Wiki 是 RAG 的替代品 | **互补**：规则少但重要 → LLM-Wiki；量大需筛选 → RAG；工程上组合使用 |
| 两种形态的区别是"Skill vs 桌面应用" | 区别是 **Knowledge = Agent 的一部分** vs **Knowledge = 独立基础设施** |
| `raw/` 可以随手改 | **不可变**——它是证据链源头，Wiki 错了要能回溯 |
| Schema 和 purpose 是一回事 | Schema 是**结构规则**，purpose 是**方向意图**（Karpathy 原设计只有前者） |
| SOUL.md 和 AGENTS.md 差不多 | AGENTS.md 是**项目宪法**（硬规则），SOUL.md 是**人格**（软风格，System Prompt 首段、可缓存） |
| 新知识进来就重建 Wiki | **增量更新**，重建会丢人工修订且成本随资料量爆炸 |
| 单步摄入就够了 | 工业级拆**两步**：分析和生成是不同认知任务；且分析结果可缓存、可审查 |
| 图谱扩展跳数越多越好 | **2 跳带衰减**——不衰减会让弱关联无限扩散，污染上下文 |
| 上下文按比例随便分 | 有明确预算：**Wiki 60% / 历史 20% / 索引 5% / 系统提示 15%** |
| 检索到页面就塞摘要 | 阶段 4 附**完整内容**并编号，因为要**可溯源** |
| 知识库建完就不用管了 | 要**定期 Lint**：孤立页 / 断链 / 索引一致性 / 矛盾 / 置信度 |
| 用了本地知识库就不会有数据出网 | **问答/摄入时**的 prompts、引用、检索片段仍可能发往模型提供商 |

## 🎤 面试怎么答（口述模板）

> **问：什么是 LLM-Wiki？和 RAG 有什么区别？**
> "LLM-Wiki 是 Karpathy 提出的一种知识组织方式：**用文件系统代替向量检索，用自然语言代替微调**，让知识**编译一次、持续维护**，而不是每次查询重新推导。它有三层：**Raw Sources**（原始资料，不可变）、**Wiki**（LLM 提取整理、互相链接的知识页）、**Schema**（结构规则，属于元知识），靠 **Ingest / Query / Lint** 三个操作运转。
> 和 RAG 的区别我记一句话：**LLM-Wiki 适合'规则少但重要'的知识，RAG 适合'量大但需要筛选'的知识**，两者互补不互斥。像项目约定、安全红线这类内容，交给 RAG 检索每次都可能漏、答案还会漂移，它们需要的是**稳定注入**而不是相似度排序。工程上一般组合用：AGENTS.md 放核心规则，RAG 放海量文档，LLM-Wiki 放整理过的知识体系。"

> **追问：实现上有哪两种形态？怎么选？**
> "**Agent 内嵌式**和**独立知识系统**。内嵌式就是把知识库作为 Markdown / Skill 放进 Agent 的工作环境，轻量、Agent 原生、易迁移、人机共读（Obsidian 能直接打开）；独立系统是把知识能力拆出来做成服务，自建解析索引检索，支持 PDF/DOCX/网页等多源，有知识树和关系图谱，多个 Agent 可以通过 API 或 MCP 共享同一套。
> 选型的本质不是'用 Skill 还是用桌面应用'，而是——**知识是 Agent 的一部分，还是独立基础设施**。前者强调让 Agent 自己拥有知识，后者强调把知识能力做成可调用的服务。个人、单项目用内嵌式就够；规模更大或者要团队共享，就上独立系统。"

> **追问：AGENTS.md 和 SOUL.md 分别是什么？**
> "**AGENTS.md 是项目的宪法**——项目身份、行为规则、安全红线、工具偏好、环境信息、工作流程；**SOUL.md 是人格**——语气和交互风格，比如'直接给方案不废话''涉及破坏性操作必须确认'。
> 工程上有个细节：SOUL.md 通常作为 **System Prompt 的第一段**注入，对应 Claude Code 分区里的**静态全局段**，内容固定所以**能被 prompt cache 缓存**——因为缓存只对前缀生效，最稳定的内容放最前，后面变化时才不会让整段缓存失效。"

> **追问：知识库怎么保证质量不腐烂？**
> "靠 **Lint** 定期体检：孤立页面（没有双向链接的）、断链（指向不存在页面的 wikilink）、索引一致性（index.md 和实际文件对不对得上）、**AI 级矛盾检测**（不同页面之间的事实冲突，这个只有 LLM 能做），还有**置信度标注**——EXTRACTED / INFERRED / AMBIGUOUS / UNVERIFIED。
> 我觉得置信度标注最容易被忽略但最有价值：它区分了'从原文提取的'和'模型推断的'，不标的话 Wiki 用久了就分不清哪些是真知识、哪些是模型编的。
> 摄入侧还有个关键设计：**两步 CoT Ingest**——先让 LLM 输出结构化分析 JSON（实体、论点、与现有 Wiki 的关联、矛盾），再基于 JSON 生成页面。拆开是因为分析和生成是不同的认知任务，分开质量更高，而且分析结果可缓存、可人工审查，工程上再配 SHA256 增量缓存和持久化队列。"
