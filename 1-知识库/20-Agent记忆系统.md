## 🎯 30 秒结论

1. 记忆的**物理载体**是向量数据库 + 语义检索；但**工程难点不在存，在"召回什么"。**
2. 一个可用的 Agent 记忆是**三层协同**的：短期记忆（当前对话，过长自动压缩）+ 工作记忆（当前任务状态与中间变量）+ 长期记忆（历史摘要/交互，语义检索召回）——三者最后一起拼进 Prompt。
3. 长期记忆必须再分**静态 / 动态**两档：静态的（用户偏好、系统规则、领域事实）almost 不变，**直接注入 System Prompt**；动态的（对话摘要、执行经验、行为模式）持续更新，**走向量库按相关性检索**。
4. 召回决策不是单看相似度，是**三维综合评分**：意图匹配（语义相似度）+ 时间衰减（`e^(-λΔt)`）+ 频率加权（`log(1+成功召回次数)`）。
5. **召回太多比召回太少更危险**——三大危害：注意力稀释、指令冲突、token 浪费。四道防线：数量上限（≤5 条）、相关性阈值（<0.7 不召回）、冲突检测（取最新）、优先级排序。
6. 治理黄金法则：**写入要慷慨、检索要精准、压缩要保守、淘汰要渐进、指标要量化。**
7. CLI Agent（无服务端状态）的解法是**纯文件系统记忆 + LLM 驱动自动压缩**，写入原则只有一句：**只存无法从当前项目状态推导的上下文。**

**② 完整记忆系统架构（原文说明）**

> 这段代码实现了一个**三层记忆协同的 Agent 记忆系统**：短期记忆保存当前对话上下文，并在内容过长时通过 LLM 自动摘要压缩；工作记忆保存当前任务执行中的临时状态和中间变量；长期记忆则借助 ChromaDB 和 Embedding 将历史对话与摘要向量化存储，并在新问题到来时按语义相似度检索相关记忆。最终，Agent 会把**短期上下文 + 工作状态 + 检索到的长期记忆**一起注入 Prompt，让模型既能记住当前聊了什么，也能保留任务进度，还能按需"回忆"过去的重要信息。

**③ 记忆类型与元数据标签（原文表）**

> 反思记忆和情景记忆都存储在**长期记忆**（向量数据库）中，但它们的元数据标签不同，检索时可以按类型过滤。

| 记忆类型 | 存储内容         | 元数据标签                           | 检索场景                 |
| :------- | :--------------- | :----------------------------------- | :----------------------- |
| 短期记忆 | 原始对话轮次     | 无(直接拼接)                         | 当前对话上下文           |
| 反思记忆 | 提炼的经验教训   | `{type: "reflection", task: "xxx"}`  | 遇到相似任务时参考经验   |
| 情景记忆 | 完整事件的5W1H   | `{type: "episodic", timestamp: "xxx"}` | 需要历史上下文时参考事件 |
| 工作记忆 | 当前任务中间变量 | 无(Scratchpad)                       | 多步推理过程中的状态     |

**④ 静态 vs 动态长期记忆（原文对比表）**

| 维度     | 静态长期记忆                 | 动态长期记忆                 |
| :------- | :--------------------------- | :--------------------------- |
| 典型内容 | 用户偏好、系统规则、领域知识 | 对话摘要、执行经验、行为模式 |
| 变化频率 | 极低，几乎不变               | 高，持续更新                 |
| 存储方式 | 本地配置文件(YAML/JSON)      | 向量数据库(Chroma/Milvus)    |
| 召回方式 | **直接注入 System Prompt**   | 按相关性语义检索             |
| 压缩策略 | 不压缩(本身已精炼)           | 定期压缩摘要 + 淘汰过时内容  |
| 更新触发 | 用户明确修改偏好时           | 每轮有价值交互后             |

**⑤ 召回决策：三维综合评分公式（原文）**

```text
recall_score = intent_similarity × w1 + time_decay_weight × w2 + frequency_weight × w3

其中:
  intent_similarity  = cosine_similarity(query_embedding, memory_embedding)
  time_decay_weight  = e^(-λ × days_since_creation)
  frequency_weight   = log(1 + successful_recall_count)
  w1 + w2 + w3 = 1（权重归一化）
```

**⑥ 记忆治理的黄金法则（原文）**

> - **写入要慷慨**：宁可多存，后续靠检索和淘汰来筛选
> - **检索要精准**：JIT 原则，只在需要时取需要的量
> - **压缩要保守**：保护核心指令和行动-结果对，只压缩中间推理
> - **淘汰要渐进**：先降优先级再删除，给"冷记忆"一个回暖的机会
> - **指标要量化**：追踪命中率、压缩率、检索延迟，用数据驱动治理策略

**⑦ 有效上下文窗口公式（原文）**

```text
有效上下文窗口 = 模型上下文窗口 - max(maxOutputTokens, 20000) - AUTOCOMPACT_BUFFER
```

> 例如 200K 窗口的模型，maxOutputTokens 可能是 8192，但安全起见取 `max(8192, 20000) = 20000`。再减去 `AUTOCOMPACT_BUFFER_TOKENS = 13,000`（压缩触发预留），有效窗口 = 200,000 - 20,000 - 13,000 = **167,000 token**。

**⑧ 八股 Q18：Claude Code 的记忆系统如何分类？（原文）**

> **四类型**：①**user**（用户画像与偏好，如"用户是 Java 开发者"）；②**feedback**（用户纠正的反馈，记录失败和成功案例）；③**project**（项目上下文，如"本项目用 pnpm"）；④**reference**（外部引用，如 API 文档链接）。
> **关键原则**：只存无法从当前项目状态推导的上下文。如果信息可以从 package.json 读到，就不写记忆文件。

## 一、三层记忆：各自解决什么问题

| 层 | 存什么 | 生命周期 | 存储 | 超限时 |
| :--- | :--- | :--- | :--- | :--- |
| **短期记忆** | 原始对话轮次 | 单次会话 | messages 数组 | **LLM 自动摘要压缩** |
| **工作记忆** | 当前任务的临时状态、中间变量 | 单次任务 | Scratchpad（内存变量） | 任务结束即释放 |
| **长期记忆** | 历史摘要、交互记录、经验 | 跨会话 | 向量数据库 | 按相关性检索 + 淘汰 |

**关键区分：工作记忆 ≠ 短期记忆**

> 短期记忆是"**聊了什么**"（对话历史），工作记忆是"**任务进行到哪一步了**"（进度 + 中间产物）。
> 二者都放在上下文里，但性质不同：短期记忆可以压缩（压掉寒暄、压掉推理链），**工作记忆几乎不能压**——丢掉任务状态等于任务从头再来。

## 二、长期记忆的静态 / 动态二分（最重要的一张表）

| 判据 | 静态长期记忆 | 动态长期记忆 |
| :--- | :--- | :--- |
| 一句话 | 一本"个人手册"——定义交互的基本规则 | 一本"工作日记"——记录成长轨迹 |
| 典型内容 | 用户偏好（"偏好简洁中文回答"）、系统规则（"回答必须附引用"）、领域事实（"API Base URL 是 …/v2"） | 历史对话摘要、任务执行经验（"上次 pandas 读 CSV 遇到编码问题，解法是指定 `encoding='utf-8'`"）、用户行为模式（"通常在下午 3 点后提问"） |
| 召回方式 | **直接注入 System Prompt**（无需检索） | 按相关性语义检索 |
| 存哪 | 本地配置文件 YAML/JSON | 向量数据库 |

> **工程含义**：静态记忆**不该进向量库**——它几乎不变，检索只是白花钱，直接写进 System Prompt 的静态区就能命中前缀缓存（呼应 [17](17-Prompt模板化与PromptOps.md) §五）。**把静态记忆塞进向量库是常见的新手错误。**

## 三、召回决策：三维评分，不是单看相似度

| 维度 | 含义 | 公式 | 直觉 |
| :--- | :--- | :--- | :--- |
| **① 意图匹配** | 当前对话意图与记忆标签的语义相似度 | `cosine_similarity(query_emb, memory_emb)` | "问 CSV 编码问题" ↔ 记忆标签"CSV 编码" → 该召回 |
| **② 时间衰减** | 越近期权重越高 | `e^(-λ × days_since_creation)` | λ 是衰减系数，Δt 是距今时间；**3 天前的经验比 3 个月前的更有参考价值** |
| **③ 频率加权** | 多次被召回且验证有效的权重更高 | `log(1 + successful_recall_count)` | 被召回 5 次且每次都有帮助 → 高价值；从未被召回 → 低权重 |

```text
recall_score = intent_similarity × w1 + time_decay_weight × w2 + frequency_weight × w3
              （w1 + w2 + w3 = 1）
```

**为什么不能只看相似度**

| 只看相似度的失败场景 | 三维评分怎么救 |
| :--- | :--- |
| 一条三个月前的高相似度记忆，早已过时 | **时间衰减**把它压下去 |
| 一条从未被验证过的相似记忆，可能是错的 | **频率加权**让它排在"被验证过"的记忆之后 |
| 相似但答非所问的记忆挤掉真正有用的 | 三个维度综合后排序，而非单指标阈值 |

> 注意 `frequency_weight` 用的是 **成功**召回次数，不是召回次数——如果一条记忆被召回 10 次但都没帮上忙，它不该涨权重。**"被召回"和"被召回且有效"是两件事。**

## 四、召回治理：为什么"召回太多"比"召回太少"更危险

**三大危害（八股 Q12）**

| 危害 | 机制 | 后果 |
| :--- | :--- | :--- |
| **① 注意力稀释** | 模型关注无关内容 | 忽略核心问题 |
| **② 指令冲突** | 多条记忆互相矛盾（"偏好简洁" vs "要求详细"） | 模型无所适从，输出摇摆 |
| **③ Token 浪费** | 无关记忆消耗窗口 | 挤掉真正该保留的 P0/P1 |

**四道防线**

| 防线 | 规则 | 为什么是这个值 |
| :--- | :--- | :--- |
| **① 数量上限** | 每次召回 ≤5 条，**简单问题 ≤3 条** | 记忆是 P2/P3 级内容，不该挤占 P0 |
| **② 相关性阈值** | 相似度 **< 0.7 的不召回** | 宁可留空，也不要"聊胜于无"的噪声 |
| **③ 冲突检测** | 多条矛盾记忆**取最新的** | 简单有效；更复杂可做优先级裁决 |
| **④ 优先级排序** | 核心指令 > 最近经验 > 补充信息 | 与 [18](18-上下文工程与消息裁剪.md) 的 P0~P4 裁剪表对齐 |

**JIT Context（Just-in-Time）**

> 核心原则：**不在一开始就塞满上下文，而是在每一步只注入当前需要的信息**——像 JIT 生产，零库存、按需供应。

| 对比 | 传统做法（预加载） | JIT Context |
| :--- | :--- | :--- |
| 注入时机 | 会话开始时一次性召回 | **每一步按需注入** |
| 优点 | 实现简单 | 窗口占用最小、无关信息最少 |
| 代价 | 大量无关记忆长期占据窗口 | 需要在每个决策点判断"现在需要什么" |

## 五、工业级落地的六个机制（Claude Code 案例）

CLI Agent 的特殊约束：**每次会话独立启动，无服务端状态，不能依赖外部向量服务**——所以它的解法是**纯文件系统记忆 + LLM 驱动的自动压缩**。

| 机制 | 做法 | 解决什么 |
| :--- | :--- | :--- |
| **① 轮次分割** | 按 user message 把对话切成多个轮次，**inline tool_result 不开新轮次** | 保证"轮次"语义正确（工具返回不算一轮对话） |
| **② 三层压缩触发** | 主动（80%）→ 后台（60%）→ 反应式（413） | 正常路径 / 空闲时预压 / 被拒后紧急压缩三条通道 |
| **③ AI 摘要 vs 规则摘要** | AI 质量高但贵，规则零成本但糙，**AI 失败降级为规则** | 可用性与成本的降级链（呼应 [18](18-上下文工程与消息裁剪.md)） |
| **④ 增量压缩** | 上次压缩水平的 **80%** 才再压缩 | 避免频繁压缩白烧 token |
| **⑤ Provider/Reducer 架构** | 可插拔设计，按场景组合不同的上下文来源与裁剪策略 | 上下文来源与裁剪策略解耦 |
| **⑥ 双作用域记忆** | **User Scope** 跨项目 / **Project Scope** 仅当前项目，**LRU 淘汰** | 记忆的作用域与容量治理 |

**"有效上下文窗口"：为什么 200K ≠ 可用 200K**

```text
有效上下文窗口 = 模型窗口 - max(maxOutputTokens, 20000) - AUTOCOMPACT_BUFFER(13,000)
200,000 - 20,000 - 13,000 = 167,000
```

| 减项 | 为什么减 |
| :--- | :--- |
| `max(maxOutputTokens, 20000)` | 给**本轮输出**留空间；即使模型只声明 8192，也按 20000 保底（安全边际） |
| `AUTOCOMPACT_BUFFER = 13,000` | 给**压缩触发**留余量——不能等真满了才压，因为压缩动作本身要花 token |

> 一句话记忆：**"标称窗口"是上限，"有效窗口"是你能真正拿去装历史的量。**

## 六、主流记忆框架对比（面试加分项）

| 框架 | 核心设计 | 亮点 |
| :--- | :--- | :--- |
| **Mem0** | **三层记忆** | 见下表 |
| **Letta** | 自编辑记忆 + 记忆分页 | 记忆能被"修改"和被"换页" |
| **Zep** | 时序知识图谱 + 自动摘要 | 能回答"用户什么时候换的电脑"这类**时序问题** |

**Mem0 的三层记忆**

| 层 | 存什么 | 组织方式 |
| :--- | :--- | :--- |
| **Episodic（情景记忆）** | 具体的交互片段（"用户上周问了 X，Agent 答了 Y"） | 按时间线组织，支持回溯 |
| **Semantic（语义记忆）** | 从交互中提取的**结构化知识**（"用户偏好简洁风格""用户是 Java 开发者"） | **去重后存储**，支持增量更新 |
| **Procedural（过程记忆）** | 总结出的"**怎么做**"类知识（"处理 JSON 解析错误时，先检查编码再检查格式"） | 类似人类的技能记忆 |

**Letta 的两大核心机制**

| 机制 | 做法 | 类比 |
| :--- | :--- | :--- |
| **自编辑记忆** | Agent 可主动修改自己的记忆——发现旧记忆过时或矛盾时，**LLM 自行调用 `memory_edit` 工具更新**内容，而非简单追加 | 人类"纠正记忆" |
| **记忆分页** | 分 **Core Memory**（常驻上下文，类似 RAM）和 **Archival Memory**（外部存储，类似磁盘）；Core 满了把低优先级记忆**换出**到 Archival，需要时再换入 | **操作系统的页面置换**，几乎一模一样 |

**Zep 的两个核心设计**

| 设计 | 做法 | 解决什么 |
| :--- | :--- | :--- |
| **时序知识图谱** | 把对话中的实体、关系、事件抽成**带时间戳的三元组**。"我上个月换了一台 Mac" → 建一条 `(用户, 换设备, Mac, 2025-06)` 的图谱边 | 能回答"用户什么时候换的电脑"这类**时序问题**（纯文本存储答不了） |
| **自动摘要** | 每轮对话后自动生成摘要，**摘要本身也被图谱化**；旧摘要随时间衰减、新摘要权重更高 | 解决"半年前的摘要和昨天的摘要权重一样"的问题 |

> 三个框架的共性：**都在回答"记忆怎么被修改、怎么被淘汰"**——因为只写不治理的记忆库会变成噪声源。

## 七、Prompt Engineering → Context Engineering 的范式迁移

| | ❌ Prompt Engineering（旧范式） | ✅ Context Engineering（新范式） |
| :--- | :--- | :--- |
| 关注对象 | **单次请求**的措辞优化 | **整个上下文**的动态编排 |
| 问的问题 | "怎么写 prompt 让 LLM 回答更好？" | "在正确的时刻，为 LLM 提供正确的信息，不多也不少。" |
| 性质 | 一次性的、静态的 | 持续性的、动态的 |
| 典型动作 | 优化 System Prompt 措辞、设计 Few-shot、调 temperature/Top-P | 记忆的检索/压缩/淘汰、工具结果的格式化与过滤、多源信息的优先级排序 |

**动态 Prompt 的组装策略（口述版，你摘录的原文）**

> **静态 Prompt** = System Prompt（角色+规则+工具 Schema+Skill 触发词），整个会话不变，放 Prompt **最前面**，100% 命中缓存。
> **动态 Prompt** = 记忆召回片段 + Skill 完整指令 + 对话历史 + 用户当前输入，每轮都变，放 Prompt **后面**，按变化频率分层。
> **组装策略**：固定 → 半固定 → 动态 → 当前请求，四层叠放。核心原则：**不变的放前面最大化缓存，变化的放后面最小化缓存失效。**

> 这段话就是 [17 §五](17-Prompt模板化与PromptOps.md) 分区缓存的"记忆版"表述——**同一原则在两个章节出现，说明它是这个体系里的主干。**

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 记忆就是"把历史都存进向量库" | 静态记忆（偏好/规则/事实）**不该进向量库**，直接注入 System Prompt 更省更稳 |
| 召回靠相似度排序就够了 | 还要看**时间衰减**和**频率加权**；只看相似度会召回一堆过时记忆 |
| 召回得多一点总没坏处 | **召回太多比太少更危险**：注意力稀释 + 指令冲突 + token 浪费，必须设上限和阈值 |
| 工作记忆就是短期记忆 | 短期是"聊了什么"，工作记忆是"任务进行到哪一步"；**工作记忆几乎不能压缩** |
| `frequency_weight` 用召回次数 | 用**成功**召回次数——被召回但没帮上忙的不该涨权重 |
| Zep 的知识图谱和普通 RAG 一样 | 图谱带**时间戳**，能回答时序问题；纯文本相似度检索答不了"什么时候换的电脑" |
| 200K 窗口就能用 200K | 有效窗口 = 标称 − 输出预留 − 压缩缓冲，实测约 **167K** |
| Letta 的记忆分页是"分库存储" | 它是**换页机制**（Core ↔ Archival），本质是操作系统的页面置换 |
| 记忆只写不删 | 必须治理：写入慷慨但**淘汰渐进**，先降优先级再删，给冷记忆回暖机会 |

## 🎤 面试怎么答（口述模板）

> **问：Agent 的记忆系统你会怎么设计？**
> "先分三层。**短期记忆**存当前对话历史，过长时压缩；**工作记忆**存当前任务的状态和中间变量——注意这和短期记忆不是一回事，短期是'聊了什么'，工作记忆是'任务进行到哪一步了'，而且工作记忆几乎不能压，丢掉任务状态等于从头再来；**长期记忆**跨会话，用向量库 + 语义检索。
> 长期记忆内部还要再分两档：**静态的**（用户偏好、系统规则、领域事实）几乎不变，直接写进 System Prompt 的静态区——**它不该进向量库**，检索只是白花钱，而且写进前缀还能命中缓存；**动态的**（对话摘要、执行经验、行为模式）持续更新，走向量库按相关性检索。
> 最后把三者拼进 Prompt：短期上下文 + 工作状态 + 检索到的长期记忆。"

> **追问：召回的时候怎么决定取哪些？**
> "不能只看相似度，我用三维综合评分：**意图匹配**（query 和记忆的余弦相似度）、**时间衰减**（`e^(-λΔt)`，3 天前的经验比 3 个月前的更有参考价值）、**频率加权**（`log(1 + 成功召回次数)`——注意是'成功'召回，被召回但没帮上忙的不该涨权重）。三个维度加权归一化后排序。
> 更重要的是**召回治理**——召回太多比召回太少危险，三个危害：注意力稀释、指令冲突（"偏好简洁"和"要求详细"同时召回）、token 浪费。所以有四道防线：数量上限每次 ≤5 条、简单问题 ≤3 条；相似度 < 0.7 直接不召回；多条矛盾取最新；优先级排序按'核心指令 > 最近经验 > 补充信息'。还有一个 JIT 原则——不在会话开始就塞满，而是每一步只注入当前需要的。"

> **追问：无服务端的 CLI Agent 没有向量库怎么办？**
> "纯文件系统 + LLM 驱动压缩。Claude Code 就是这么做的，几个机制值得学：①**轮次分割**按 user message 切轮，inline tool_result 不算新轮；②**三层压缩触发**——主动 80%、后台 60%、反应式 413；③摘要降级链 AI → 规则；④**增量压缩**，到上次压缩水平的 80% 才再压，避免频繁压缩白烧 token；⑤**Provider/Reducer** 可插拔；⑥**双作用域记忆**，User Scope 跨项目、Project Scope 仅当前项目，LRU 淘汰。
> 它的记忆写入原则只有一句：**只存无法从当前项目状态推导的上下文**——能从 package.json 读到的（比如'本项目用 React'）就不写记忆。记忆四类型是 user / feedback / project / reference。
> 另外它算'有效上下文窗口'而不是用标称值：`有效 = 标称 - max(maxOutputTokens, 20000) - 压缩缓冲 13000`，200K 的模型实际只有约 167K 可用。"
