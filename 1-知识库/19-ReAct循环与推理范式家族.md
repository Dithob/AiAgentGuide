## 🎯 30 秒结论

1. **ReAct 的全部内核就 5 步**：LLM 生成 Thought+Action → 解析 Action → 执行工具 → 注入 Observation → 循环。50 行代码就能跑通。
2. 但 ReAct 有四个**结构性局限**：token 随步数**线性膨胀**、严格**串行**、**文本解析格式不稳定**、可能陷**死循环**。
3. 后续演进正是**逐条打这四个局限**：ReWOO 治 token，LLM Compiler 治串行，Structured Output / Function Calling 治解析，Reflexion 治"错了不知道"。
4. **ReWOO 的反直觉之处**：不要"边想边做"，而是**先想好全部步骤再统一执行**（Planner → Worker → Solver），用一次性的规划换掉每步的 Observation 注入。
5. **Reflexion = ReAct + Self-Reflection**，Attention 从"外部环境"转向"自己的推理过程"。
6. 到了生产环境，主循环要额外挂**六件套**：双模式、Token Budget、死循环保护、截断恢复、指数退避、413 压缩。**框架差距不在"能不能循环"，而在这六件套。**

**① 用 50 行代码实现 ReAct（你摘录的完整示例）**

```python
import re
from openai import OpenAI

client = OpenAI()
TOOLS = {"search": search_web, "lookup": lookup_keyword}

def react_agent(question, max_steps=10):
    messages = [{"role": "system", "content": REACT_PROMPT}]
    messages.append({"role": "user", "content": question})

    for step in range(max_steps):
        # 1. LLM 生成 Thought + Action
        response = client.chat.completions.create(
            model="gpt-4o", messages=messages
        )
        output = response.choices[0].message.content
        messages.append({"role": "assistant", "content": output})

        # 2. 解析 Action
        action_match = re.search(r'Action: (\w+)\((.*?)\)', output)
        if not action_match:
            break

        tool_name = action_match.group(1)
        tool_input = action_match.group(2).strip('"\'')

        # 3. 检查是否完成
        if tool_name == "finish":
            return tool_input

        # 4. 执行工具
        if tool_name in TOOLS:
            result = TOOLS[tool_name](tool_input)
        else:
            result = f"Error: tool {tool_name} not found"

        # 5. 注入 Observation
        messages.append({"role": "user", "content": f"Observation: {result}"})

    return "达到最大步数限制"
```

> 原文结论：核心就这几步——**LLM 生成 → 解析 Action → 执行工具 → 注入 Observation → 循环**。

**② ReWOO 的动机（原文）**

> ReAct 的核心循环是"边想边做"——每一步 Thought 之后立刻 Action，获得 Observation 后再想下一步。这很直观，但有一个严重的问题：**每一步的 Observation 都会被塞入上下文，随着步数增加，token 消耗线性膨胀。**
> ReWOO 提出了一个反直觉的思路：**先想好所有步骤，再统一执行。**

**③ ReAct 家族演进（你摘录的原文表）**

| 变体                   | 改进点                               | 核心机制                | 年份  |
| :--------------------- | :----------------------------------- | :---------------------- | :---- |
| ReAct                  | 原始版：Thought-Action-Observation   | 推理+行动交替循环       | 2022  |
| ReWOO                  | 先规划再执行，减少 token 消耗        | Planner→Worker→Solver   | 2023  |
| LLM Compiler           | 并行执行独立工具调用                 | 依赖图(DAG)编译+并行    | 2023  |
| Reflexion              | 加入自我反思，从失败中学习           | 执行→评估→反思→重试循环 | 2023  |
| LATS                   | 结合蒙特卡洛树搜索+ReAct             | 树搜索+推理行动         | 2023  |
| Function Calling ReAct | 用原生 Function Calling 替代文本解析 | 结构化工具调用          | 2023+ |

**④ 生产级 Agent 主循环设计（原文要点，六条）**

> **双模式**：Chat 简单高效，Agent 自动多轮，按场景选择避免浪费。
> **Token Budget**：全局预算防止烧钱，实时累加及时停止。
> **死循环保护**：连续 2 轮相同失败自动终止，阈值 2 平衡了灵敏度和容错。
> **截断恢复**：max_tokens 截断时注入 continue 自动续写，有限次恢复避免无限循环。
> **指数退避**：临时错误自动重试，2^n 秒退避避免雪崩，区分可重试和不可重试错误。
> **413 压缩**：请求过大时紧急压缩重试，是正常压缩的兜底方案。

**⑤ 八股 Q10：Fork 子代理增强（原文）**

> **局限**：①标准 ReAct 串行执行，独立子任务无法并行；②自我确认偏误——Agent 用自己的标准检查自己的代码，容易忽略错误；③自由推理容易导致任务遗漏和优先级漂移。
> **Fork 子代理增强**：主代理在 Thought 阶段判断子任务可委派，Fork 子代理后台执行。子代理继承主代理上下文，共享 prompt cache。完成后发通知，主代理整合结果。
> **Fork Prompt 四规则**：不偷看（通知到达前不访问 output_file）、不编造（不能猜结果）、不推诿理解（不能把综合判断推给子代理）、指令式而非背景介绍式（Fork 已继承上下文，不需要重复解释）。

## 一、ReAct 五步循环：把代码读成状态机

| 步 | 代码位置 | 做什么 | 关键点 |
| :--- | :--- | :--- | :--- |
| **1 生成** | `client.chat.completions.create` | LLM 输出 Thought + Action 文本 | 这一步是**唯一一次 LLM 调用**，也是成本来源 |
| **2 解析** | `re.search(r'Action: (\w+)\((.*?)\)')` | 从自由文本里正则抠出工具名和参数 | **最脆弱的一环**——格式一飘就解析失败 |
| **3 完成判定** | `if tool_name == "finish"` | 让模型用"调用 finish 工具"来表达结束 | 等价于 Function Calling 里的"不再请求 tool_calls" |
| **4 执行** | `TOOLS[tool_name](tool_input)` | 真正调外部能力 | 注意：**执行永远由代码完成，LLM 不执行** |
| **5 注入** | `messages.append({"role": "user", ...})` | 把 Observation 塞回历史 | **token 膨胀的根源**（见 §三） |

> 与 [13-Agent-Loop](13-Agent-Loop与多轮对话.md) 的关系：**13 是"工业版五步"（role=tool + tool_call_id），19 是"教学版五步"（纯文本正则解析）。** 差别只在第 2 步和第 5 步用什么协议。

**两个回收机制（代码里的"保险丝"）**

| 机制 | 代码 | 作用 |
| :--- | :--- | :--- |
| `max_steps=10` | `for step in range(max_steps)` | 循环次数上限，兜底死循环 |
| `tool not found` | `result = f"Error: tool {tool_name} not found"` | **把错误当 Observation 喂回去**——呼应 14 的"错误也要告诉 AI" |

## 二、ReWOO：为什么"先规划再执行"能省 token

| 维度 | ReAct | ReWOO |
| :--- | :--- | :--- |
| 执行节奏 | 边想边做（Thought → Action → Observation 交替） | 先想完再做（一次性出计划） |
| LLM 调用次数 | **每步 1 次**（步数 = 调用次数） | **固定 2~3 次**（Planner 1 + Solver 1，与步数无关） |
| token 增长 | **线性膨胀**（每步的 Observation 都进上下文） | 接近常数（Observation 不回流给 Planner） |
| 适应性 | 强（能根据中间结果改路线） | **弱（计划一旦生成不可动态调整）** |
| 失败恢复 | 边走边纠 | 只能靠 Solver 阶段补救或整体重来 |

**三阶段架构**

| 阶段 | 角色 | 输入 | 输出 |
| :--- | :--- | :--- | :--- |
| **Phase 1 Planner** | 规划器 | 用户问题 | 一份带 `#E1/#E2…` 工具占位符的计划文本 |
| **Phase 2 Worker** | 执行器 | 计划文本 | 各 `#E` 的实际执行结果（**不进 LLM 上下文**） |
| **Phase 3 Solver** | 求解器 | 计划 + 填充后的结果 | 最终答案 |

```
Planner ──► Plan: 推理1
            #E1 = search("...")
            Plan: 推理2（可引用 #E1 的结果）
            #E2 = calc("#E1")
                 │
                 ▼  （正则抠出全部 #E，批量执行；模型不参与）
Worker  ──► {#E1: ..., #E2: ...}
                 │
                 ▼  （把 #E 占位符原地替换成 [结果: ...]）
Solver  ──► 最终答案
```

> **核心洞察**：ReWOO 省 token 的方式不是"压缩上下文"，而是**让 Observation 根本不进入模型的 context**——它只出现在 Worker 的局部变量和 Solver 那一次调用的输入里。
> 代价也很明确：**计划不能动态调整**。所以 ReWOO 适合"步骤可预先枚举"的任务，ReAct 适合"需要临场应变"的任务。

**ReWOO 的两个硬约束（踩坑点）**

| 约束 | 说明 |
| :--- | :--- |
| 计划必须**可静态解析** | Worker 用正则抠 `#E`，格式飘了就抠不出来——所以 Planner 的 Prompt 里必须把格式写死 |
| 步骤间**不能有数据依赖的环** | `#E2` 可以引用 `#E1`，但 `#E1` 不能依赖 `#E2`，否则 Worker 的执行顺序无法确定 |

## 三、ReAct 的四个结构性局限，以及家族怎么逐个补

**这张表是本条目的主线**——把"演进"讲成"补漏"：

| ReAct 的局限 | 具体表现 | 是谁补的 | 补法 |
| :--- | :--- | :--- | :--- |
| **① token 线性膨胀** | 每步 Observation 都进上下文，步数越多单次调用越贵（呼应 15 的 token 递增） | **ReWOO** | 先规划再执行，Observation 不回流模型 |
| **② 严格串行** | 没有依赖关系的工具也必须排队，总延迟 = 各步延迟之和 | **LLM Compiler** | 把计划**编译成依赖图 DAG**，识别可并行分支，独立工具并发执行 |
| **③ 格式解析不稳定** | 正则抠 `Action:` 文本，模型格式一飘就崩 | **Structured Output / Function Calling ReAct** | 从文本协议换成**结构化工具调用**协议（JSON Schema 约束） |
| **④ 错了不知道** | 一路走到黑，没有"结果质量评估"环节 | **Reflexion** | 执行 → 评估 → 反思 → 重试，把失败变成经验 |

**LLM Compiler（2023, Kim 等）**

> 核心思想：将执行计划**编译成依赖图（DAG）**，识别可并行的步骤，同时执行没有依赖关系的工具调用，显著减少总执行时间。

| 对比 | ReAct | LLM Compiler |
| :--- | :--- | :--- |
| 执行模型 | 串行 | **DAG + 并行** |
| 适用 | 步骤间强依赖 | 存在多个独立子任务 |
| 代价 | — | 依赖之间仍不可并行；调度复杂度上升 |

**Reflexion（2023, Shinn 等）**

> = ReAct + Self-Reflection。执行完任务后**回头审视自己的推理过程**，评估结果质量，发现问题则重新尝试。通过多轮"执行→反思→改进"循环逐步提升答案质量。

| 对比 | ReAct | Reflexion |
| :--- | :--- | :--- |
| 反馈来源 | **外部环境**（Observation） | **自己的推理过程**（Self-Reflection） |
| 循环结构 | Thought-Action-Observation | 执行 → 评估 → 反思 → 重试 |
| 代价 | — | **反思轮次可能过多**，成本不可控 |
| 与 09 的关系 | — | Reflexion 就是 09 里 Reflection 那格的工程化落点 |

**LATS（2023）**：ReAct + **蒙特卡洛树搜索**——把"选下一步行动"变成树搜索，能回溯、能比较不同分支。

| 范式 | 搜索空间 | 成本 |
| :--- | :--- | :--- |
| ReAct | 单条路径，贪心前进 | 低 |
| ToT（见 09） | 多条路径，广度探索 | 中高 |
| LATS | 树搜索 + 推理行动联合 | 高 |

**Function Calling ReAct（2023+）**：**本质是"去掉 ReAct 的文本解析层"**——用模型原生的工具调用能力替代 `re.search`，格式稳定性从"取决于模型文风"变成"取决于 Schema 约束"。这是**当前生产环境的默认形态**，也是 `4-code/first_agent/agent.py` 用的方式。

## 四、生产级主循环六件套（面试的"落地"分水岭）

教学版循环（`while True` + 解析 + 执行）跑 demo 够用，上生产必须补齐这六件：

| 机制 | 解决的问题 | 关键设计 | 没有它会怎样 |
| :--- | :--- | :--- | :--- |
| **① 双模式** | 简单请求被强行多轮，浪费 token | Chat 模式（单轮直答）/ Agent 模式（自动多轮），按场景选 | 每句"你好"都走完整 Agent 循环 |
| **② Token Budget** | 单次任务成本失控 | 全局预算，实时累加，超限即停 | 一个死循环刷爆账单 |
| **③ 死循环保护** | 工具反复失败导致卡死 | **连续 2 轮相同失败**自动终止（阈值 2 平衡灵敏度与容错） | 同一个错误重试到 max_turns |
| **④ 截断恢复** | `max_tokens` 截断导致回答半途而废 | 注入 `continue` 自动续写，**限次**恢复 | 要么半截回答，要么续写无限循环 |
| **⑤ 指数退避** | 临时故障（超时/限流）直接失败 | `2^n` 秒退避 + **区分可重试/不可重试**错误 | 雪崩（重试风暴）或误重试逻辑错误 |
| **⑥ 413 压缩** | 请求体过大被拒 | 收到 413 时**紧急压缩后重试** | 请求反复被拒，任务失败 |

**三条设计心得（可以直接说给面试官）**

1. **阈值要"两轮"而不是"一次"**：一次失败就退出太敏感（网络抖动很常见），阈值越高容错越好但也越慢发现问题——**2 是灵敏度与容错的平衡点**。
2. **恢复一定要"限次"**：截断恢复、压缩重试都必须是**有限次**，否则就是换了个名字的死循环。
3. **错误必须分类，不能统一重试**：可重试 = 临时性故障（可能自己恢复）；不可重试 = 逻辑性错误（再试也一样）——呼应 [14-工具Schema与异常处理](14-工具Schema与异常处理.md)。

## 五、Fork 子代理：并发 + 破除自我确认偏误

**为什么需要**（三个局限都在"单 Agent 串行 + 自我评估"上）

| 局限 | 表现 |
| :--- | :--- |
| **串行** | 独立子任务无法并行 |
| **自我确认偏误** | Agent **用自己的标准检查自己的代码**，容易忽略自己的错误 |
| **优先级漂移** | 自由推理容易导致任务遗漏、优先级漂移 |

**机制**

```
主代理 Thought 阶段判断「这个子任务可委派」
        │
        ▼
Fork 子代理（后台执行，继承主代理上下文，共享 prompt cache）
        │
        ▼
完成 → 发通知 → 主代理整合结果
```

**Fork Prompt 四规则（重点，考的就是这个）**

| 规则 | 含义 | 违反后果 |
| :--- | :--- | :--- |
| **不偷看** | 通知到达前不访问 `output_file` | 提前读取到半成品，基于不完整信息决策 |
| **不编造** | 不能猜结果 | 主代理幻觉出一个"看起来对"的结果 |
| **不推诿理解** | 不能把综合判断推给子代理 | **子代理没有全局视角**，综合判断只能在主代理做 |
| **指令式而非背景介绍式** | Fork 已继承上下文，不需要重复解释 | 重复注入背景 → 浪费 token，且可能覆盖主代理的原始意图 |

> 第三条最容易答错：很多人以为"委派了就该让子代理自己判断"，但**子代理只看到局部上下文**，全局综合判断必须留在主代理手里。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| ReWOO 的收益是"更聪明" | 收益是**省 token**（Observation 不进模型上下文）；代价是**计划不可动态调整** |
| ReAct 可以自然支持多 Agent 协作 | **不能**。ReAct 是单 Agent 模式，多 Agent 需要额外框架（CrewAI / AutoGen 等） |
| Structured Output 可以替代 Reflexion | 是**两个维度**：前者解决输出**格式**可靠性，后者解决**推理质量与自我纠错**，不能互相替代 |
| 文本解析不稳定是"模型不够强"，等模型变强就好 | 这是**协议问题**不是能力问题——解药是换 Function Calling / Structured Output 这类结构化协议 |
| 三级（或更高）反思轮次越多效果越好 | 反思轮次可能过多导致成本失控，必须设上限 |
| 死循环保护阈值越大越安全 | 阈值越大，发现问题越晚，烧的钱越多；Claude Code 取 **2 轮**正是为了平衡灵敏度与容错 |
| 截断恢复可以无限续写 | 必须**限次**，否则是另一个死循环 |
| 委派给子代理后就让子代理自己综合判断 | 子代理只看到局部上下文；**综合判断必须留在主代理**（Fork 四规则之"不推诿理解"） |

## 🎤 面试怎么答（口述模板）

> **问：ReAct 是怎么工作的？**
> "ReAct 的内核就是五步：LLM 生成 Thought 和 Action → 代码解析出 Action → 执行工具 → 把 Observation 注入回历史 → 循环。终止条件是模型自己表达结束，比如调用一个 finish 工具，或者用原生 Function Calling 时不再请求 tool_calls；`max_steps` 只是保险丝。
> 有两个细节值得单独说：一是**执行永远由代码完成，模型只输出'要调什么'**；二是工具报错时不是崩溃或忽略，而是**把错误当成 Observation 喂回去**，让模型自己决定换工具、改参数还是道歉。"

> **追问：ReAct 有什么局限？后来怎么补的？**
> "四个结构性局限，而且后面的演进基本是一对一补漏。
> 第一个是 **token 线性膨胀**——每步的 Observation 都进上下文，步数越多单次调用越贵。ReWOO 就是用'先规划再执行'把它压下去：Planner 一次出计划，Worker 批量执行，Observation 根本不回流给模型，Solver 最后综合。代价是计划不能动态调整。
> 第二个是**严格串行**，没有依赖关系的工具也得排队。LLM Compiler 把计划编译成依赖图 DAG，独立的工具并发跑。
> 第三个是**格式解析不稳定**，靠正则抠 `Action:` 文本很脆——这是协议问题，解药是换成原生 Function Calling / Structured Output。
> 第四个是**错了不知道**，一路走到黑没有质量评估。Reflexion 加了自我反思，执行完回头审视自己的推理，形成'执行→评估→反思→重试'。再往上还有 LATS，把选行动变成蒙特卡洛树搜索，能回溯。"

> **追问：如果要把这个循环上生产，你还要加什么？**
> "六件套。①**双模式**——简单请求走 Chat 单轮，别每句'你好'都跑完整循环；②**Token Budget**——全局预算实时累加，超限即停；③**死循环保护**——连续 2 轮相同失败自动终止，取 2 是为了平衡灵敏度和容错；④**截断恢复**——被 max_tokens 截断时注入 continue 续写，但必须限次；⑤**指数退避**——临时错误 `2^n` 秒退避，而且要区分可重试和不可重试；⑥**413 压缩**——请求过大时紧急压缩重试，作为正常压缩的兜底。
> 三条心得：恢复一定要限次，否则是换个名字的死循环；错误一定要分类，不能统一重试；阈值不能太敏感，一次失败就退出会误杀网络抖动。"

> **追问：多 Agent 或子代理怎么和 ReAct 结合？**
> "一个真实形态是 Fork 子代理：主代理在 Thought 阶段判断子任务可委派，Fork 一个后台子代理，子代理继承主代理上下文、共享 prompt cache，完成后发通知，主代理整合。
> 它同时解决了三个问题：串行、**自我确认偏误**（Agent 用自己的标准检查自己的代码很难发现自己的错）、优先级漂移。但 Fork 的 Prompt 有四条规则必须遵守：不偷看（通知到之前不能读输出文件）、不编造（不能猜结果）、**不推诿理解**（综合判断不能推给子代理，因为它没有全局视角）、指令式而非背景介绍式（它已经继承了上下文，重述背景反而浪费 token 还可能覆盖原意）。"
