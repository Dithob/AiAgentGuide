**Q4: CoT（链式思考）如何提升推理能力？**

> CoT 通过要求模型"一步步推理"而非直接输出答案，让模型在生成最终答案前先产出中间推理步骤。这有两个好处：①**扩展了推理空间**——每生成一步推理就为下一步提供了更多上下文，降低了单步推理难度；②**减少了错误传播**——中间步骤可以自我检查，避免一步错步步错。研究表明 CoT 在数学推理上能提升 15-30% 的准确率。核心用法是在 Prompt 中加入"Let's think step by step"或"请一步步推理"。

**Q9: Self-Consistency 的原理是什么？**

> Self-Consistency（自一致性）是对 CoT 的增强：对同一个问题用 CoT 生成多个推理路径（通过设置 temperature > 0 多次采样），然后对所有答案进行多数投票（Majority Voting），选择出现次数最多的答案作为最终结果。原理是：正确的推理路径更可能收敛到同一个答案，而错误路径更可能发散。代价是需要多次 LLM 调用，成本是单次 CoT 的 N 倍（N 为采样次数，通常 5-10 次），适用于有确定答案的推理任务。

## 一、Prompt 三层结构

| 层 | 作用 | 生命周期 | API role |
| :--- | :--- | :--- | :--- |
| **System Prompt** | 设定"你是谁、该怎么做"：角色、行为规则、输出格式、安全约束 | 整个对话持续生效 | `role: "system"` |
| **User Prompt** | 表达"我要什么"：具体问题或任务 | 每次一换 | `role: "user"` |
| **Context** | 背景信息：检索到的资料、历史、工具返回 | 按需注入 | 混在 system / user 里 |

**示例（代码审查 Agent 的 System Prompt）**

```
你是一个专业的代码审查专家。
只关注代码的安全性和性能问题。
回答格式：先给出风险等级（高/中/低），再说明问题，最后给出修复建议。
```

**为什么 System Prompt 更重要**

| 原因 | 说明 |
| :--- | :--- |
| 定义行为边界与安全约束 | 是"AI 能做什么"的第一道闸门 |
| 多轮持续生效 | 避免用户靠后续提问绕过限制 |
| 提升输出一致性与质量 | 格式、风格、深度都由它锚定 |

> 在 Agent 架构里，Prompt 不只是人机交互入口，还是**决策的"方向盘"**——规划、工具选择、输出格式都受它控制。

## 二、六种高级技巧

| 技巧 | 原理 | 适用场景 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- | :--- |
| **角色扮演** Role | 指定模型扮演特定角色 | 专业领域问答 | 简单有效，提升专业度 | 对复杂推理帮助有限 |
| **思维链** CoT | 要求一步步推理 | 数学、逻辑、推理题 | 大幅提升复杂推理准确率 | 增加输出 Token |
| **少样本** Few-Shot | 给示例引导输出格式 | 格式约束、分类任务 | 输出格式可控性强 | 示例占输入 Token |
| **思维树** ToT | 探索多条推理路径取最优 | 规划、博弈、创意问题 | 能找到更全局的最优解 | Token 消耗大、速度慢 |
| **自一致性** Self-Consistency | 多次采样取多数票 | 有确定答案的推理题 | 在 CoT 上再提升准确率 | 需多次调用，成本 ×N |
| **ReAct** | 交替推理与工具调用 | Agent 核心模式 | 能调外部工具解决实际问题 | 依赖工具质量与描述 |

**CoT 为什么有效**

| 机制 | 说明 |
| :--- | :--- |
| 扩展推理空间 | 每生成一步推理，就为下一步提供更多上下文，降低单步难度 |
| 减少错误传播 | 中间步骤可自我检查，避免"一步错步步错" |
| 实测收益 | 数学推理任务上提升约 **15~30%** 准确率 |

**CoT 示例**

```
❌ 普通：小明有 15 个苹果，给了小红 1/3，又买了 8 个，现在有几个？

✅ CoT：请一步步推理：
   1. 先计算给了小红多少个
   2. 再计算剩余多少个
   3. 最后加上新买的
   给出最终答案。
```

**Self-Consistency 原理**

- 对同一问题用 CoT 生成**多条推理路径**（`temperature > 0` 多次采样）。
- 对答案做**多数投票**，取出现次数最多的。
- 依据：正确路径更易收敛到同一答案，错误路径更易发散。
- 代价：N 次调用 ≈ 单次的 N 倍成本（N 通常 5~10），适合**有确定答案**的任务。

## 三、Prompt 设计四原则

| 原则 | 做法 |
| :--- | :--- |
| **清晰** | 明确说要什么，别留歧义 |
| **具体** | 给足细节，减少模型猜测 |
| **约束格式** | 指定输出格式（JSON / 表格），便于程序解析 |
| **示例驱动** | 用例子代替描述，最直观（Few-Shot 的本质） |

> 实际项目里 Prompt 需要反复迭代调试。这与"把 Prompt 当参数调"是两回事——**Prompt 是设计，不是调参**。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| 梯度下降 / 反向传播是高级 Prompt 技巧 | 是**训练阶段**的优化算法，与 Prompt 无关（高频干扰项） |
| System 和 User Prompt 只是位置不同 | System 定"怎么做"、全程生效；User 定"做什么"、每次一换 |
| CoT 对所有任务都有益 | 对简单问答无益甚至有害，且大幅增加输出 Token |
| Self-Consistency 适合开放式创作 | 只适合**有确定答案**的推理任务，开放式任务没有"多数票" |
| ToT 可以随便用 | Token 消耗大、速度慢，只在需要探索/回溯时用 |
| Prompt 一次写好就行 | 需要迭代；但迭代 ≠ 调参，是设计迭代 |

## 🎤 面试怎么答（口述模板）

> **问：System Prompt 和 User Prompt 的区别？为什么 System 更重要？**
> "System Prompt 设定角色、规则和输出格式，在整个对话里持续生效，相当于工作手册；User Prompt 是用户每次的具体请求。System 更重要是因为它定义了行为边界和安全约束，而且它是多轮持续生效的——用户后面怎么绕都绕不开它。在 API 里它们对应两个不同的 role。"

> **追问：Prompt 改了没效果，你会怎么排查？**
> "先看是理解问题还是格式问题。理解问题就补 CoT 让他一步步想；格式问题就给 Few-Shot 示例、加 JSON Schema 约束。再看是不是指令太模糊，把'清晰、具体、约束格式、示例驱动'四条过一遍。如果都不行，可能是任务本身超出模型能力，那要换思路，比如拆成多步、或者补工具让它去查而不是硬答。"
