## 🎯 30 秒结论

1. **理解 Agent 的边界，比理解它的能力更重要**——这样才不会在该写普通程序的地方硬上 Agent。
2. 一条判据贯穿全章：**确定性任务不需要决策，而决策才是 Agent 的核心价值**。给不需要决策的任务加 Agent，等于**给计算器装个大脑——费钱还更慢**。
3. 传统程序完胜：CRUD、数学计算、格式转换、定时批处理、高并发低延迟 API。
4. Agent 完胜：自然语言交互、多步骤编排、灵活错误处理、跨领域问答、长尾场景。
5. 最佳实践是**混合架构**：确定性部分用代码，不确定性部分交给 Agent。
6. 即使该用 Agent，也要盯 **QPS × 单次成本** 这个乘积。

## 一、传统程序完胜的五个场景

| 场景 | 传统程序 | Agent | 胜者 |
| :--- | :--- | :--- | :--- |
| CRUD 操作（增删改查） | 确定性逻辑，100% 准确 | 可能理解错意图 | ❌ 传统 |
| 数学计算 | 精确无误 | LLM 算术不可靠 | ❌ 传统 |
| 格式转换（CSV → JSON） | 规则明确，速度快 | 没必要让 AI 决策 | ❌ 传统 |
| 定时批处理任务 | 稳定、低成本 | 每次调用都花钱 | ❌ 传统 |
| 高并发低延迟 API | 毫秒级响应 | 秒级响应，成本高 | ❌ 传统 |

## 二、Agent 完胜的五个场景

| 场景 | 传统程序 | Agent | 胜者 |
| :--- | :--- | :--- | :--- |
| 自然语言交互 | 要写大量解析规则 | 天然理解意图 | ✅ Agent |
| 多步骤编排（先查再规划） | 要硬编码所有流程 | 自主决定步骤顺序 | ✅ Agent |
| 灵活错误处理 | 每种错误写 if-else | 根据错误自行调整 | ✅ Agent |
| 跨领域问答 | 无法覆盖所有领域 | 通用推理能力 | ✅ Agent |
| 长尾场景（罕见情况） | 无法穷举 | 临场推理 | ✅ Agent |

> 两句话对照记忆：**"确定性任务不需要决策" → 用传统程序；"不确定性任务需要决策" → 用 Agent。**

## 三、混合架构（最佳实践）

不是"全用"或"全不用"，而是按确定性切分：

```
用户输入
   │
   ├── 意图理解 / 工具选择 / 异常调整  ──▶  Agent（LLM 推理）
   │
   └── 路线计算 / 报告格式化 / 数据校验  ──▶  传统程序（确定性函数）
```

**判定某个函数该放哪一边，只问一句话**：**它的输出是否唯一确定？**

| 函数 | 性质 | 归属 |
| :--- | :--- | :--- |
| `calculate_route(start, end)` | 输入确定 → 输出唯一 | **传统程序** |
| `format_weather_report(weather)` | 纯格式化 | **传统程序** |
| "理解用户到底想问什么" | 开放、有歧义 | **Agent** |
| "该调哪个工具、按什么顺序" | 需要推理 | **Agent** |

> 这也是工业界的主流形态：**LLM 负责"判断和编排"，代码负责"执行和保证"**——和条目 15 里你质疑的那句话是同一个道理。

## 四、成本陷阱：同一个需求，三种实现的账

| 实现方式 | 成本 | 延迟 | 准确率 |
| :--- | :--- | :--- | :--- |
| ① 直接调天气 API（传统程序） | **0** | 0.1s | 100% |
| ② 硬编码规则匹配（传统 + NLU） | **0** | 0.05s | 80%（处理不了"明天"这类模糊词） |
| ③ Agent（AI + 工具） | **$0.0001/次** | 1.5s | 95%（能理解"明天""后天"） |

**关键在规模**：

| 每天查询量 | Agent 日成本 | 判断 |
| :--- | :--- | :--- |
| 10 次 | $0.001 | 可以接受 |
| 10,000 次 | $1 | 需要考虑 |
| 1,000,000 次 | $100 | **必须用传统程序** |

> **判据：`QPS × 单次成本 > 预算` → 就该考虑传统程序或混合架构。**
> 注意这个账要按 **15 条目里的 token 递增**来算——多轮 Agent 的真实单次成本远高于"一轮问答"的估算。

## ⚠️ 易错点

| 常见错误说法 | 正解 |
| :--- | :--- |
| Agent 是更好的方案，能用就用 | 确定性任务上 Agent **更慢、更贵、还不准** |
| Agent 的劣势只是"贵" | 还有**延迟**（秒级 vs 毫秒级）和**准确率**（LLM 算术不可靠） |
| 高并发场景可以靠加机器解决 | QPS 上来后单次成本是乘数，加机器只会让账单线性上涨 |
| 混合架构是"折中、不够纯粹" | 它是**最佳实践**——LLM 判断 + 代码保证 |
| 该用 Agent 的场景就不用管成本了 | 该用也要盯 `QPS × 单次成本`，这正是成本陷阱 |
| 准确率高一点就一定值得 | 看规模：低频 95% 值得，百万次/天就要重新算 |

## 🎤 面试怎么答（口述模板）

> **问：什么场景不该用 Agent？**
> "有一条判据贯穿：**确定性任务不需要决策，而决策才是 Agent 的核心价值**。CRUD、数学计算、格式转换、定时批处理、高并发低延迟 API——这五类传统程序完胜，给它们加 Agent 就像给计算器装个大脑，费钱还更慢。
> 反过来该用 Agent 的是：自然语言交互、多步骤编排、灵活错误处理、跨领域问答、长尾场景——共同点是**需要临场决策**。
> 实际项目我倾向**混合架构**：先问'这个函数的输出是不是唯一确定'，是就写成确定性代码，不是才交给 LLM。LLM 负责判断和编排，代码负责执行和保证。"

> **追问：成本怎么评估？**
> "算 `QPS × 单次成本` 跟预算比。有个具体锚点：查天气这件事，直接调 API 成本是 0、延迟 0.1 秒；用 Agent 是 $0.0001 一次、延迟 1.5 秒。每天 10 次可以接受，一万次就要考虑，一百万次必须退回传统程序。而且 Agent 的单次成本要按 token 递增来算——每轮都重发历史，多轮任务的真实成本比'一轮问答'高得多。"
