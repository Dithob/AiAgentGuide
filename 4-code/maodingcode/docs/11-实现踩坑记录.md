# 11 · 实现踩坑记录

这一篇记录开发过程中**真实踩到**的 bug。都是写成文档比修复本身更有价值的类型：
它们不是笔误，而是"看起来对、跑起来错"的设计陷阱。

---

## 坑 1 · `Path("")` 让配置文件永远读不到

**现象**：`maodingcode.toml` 明明放在工作区根目录，但 `max_steps`、`permission_mode`
全都不生效，一直用默认值。

**原因**：

```python
# ❌ 有 bug 的写法
config_path = Path(overrides.pop("config_path", "") or "") or _find_config_file(workspace)
```

两个问题叠在一起：

1. `Path("")` 得到的是 `Path('.')`，不是"空路径"；
2. `Path` 没有定义 `__bool__`，而 `pathlib.PurePath` 定义了 `__fspath__`……
   总之 `bool(Path('.'))` 恒为 `True`。

于是 `A or B` 永远短路到 A，`_find_config_file()` 从来没被调用过。
更阴的是 `Path('.').is_file()` 返回 `False`，所以后面 `if config_path.is_file()`
的分支静默跳过——**不报错，只是不生效。**

**修复**：

```python
explicit_config = overrides.pop("config_path", None)
config_path = Path(explicit_config) if explicit_config else _find_config_file(workspace)
```

**教训**：`or` 短路配合"假值约定"在 Python 里要用得保守。
`Path('')`、`Path('.')`、空列表、`0` 都可能是合法的业务值。
"没传" 就用 `None` 显式判断，别靠真值测试。

## 坑 2 · 整轮丢弃只丢了一轮

**现象**：上下文严重超窗时（历史 6000 token，预算 4500），裁剪后仍然 5000+ token，
请求照样超窗。

**原因**：`_drop_rounds()` 只算了一个切点就返回：

```python
# ❌
cut = starts[1]          # 永远只丢第一轮
out = history[cut:]
return out, cut, ...
```

丢一轮省下的量是固定的（一轮的 token 数），
但"超出预算多少"是变化的。当超出量大于一轮能省下的量时，丢一轮根本不够。
上面那个例子里，需要连丢 4 轮才能装进预算。

**修复**：从最早的轮次开始逐个试算，找到**第一个**装得下的切点：

```python
counts = [count(m.content or "") for m in history]
prefix = [0]
for c in counts:
    prefix.append(prefix[-1] + c)      # 前缀和，让试算 O(1)
total_all = prefix[-1]

for start in starts[1:]:
    remaining = total_all - prefix[start]
    if remaining <= budget:
        return history[start:], start, remaining
return history[starts[-1]:], starts[-1], ...   # 兜底：至少留最后一轮
```

**为什么不能只丢一轮就检查**：因为预算检查和裁剪是**两个独立的量**，
不能假设"丢一点就够了"。必须循环到满足约束为止。

**教训**：任何"裁剪/限流/退避"逻辑，都要写成 `while 不满足约束` 的形式，
而不是 `if 不满足就处理一次`。

## 坑 3 · 安全下限把测试预期顶掉了

**现象**：写了测试验证"超预算时应该折叠历史"，参数设成
`max_context_tokens=1500`，结果折叠逻辑一次都没触发。

**原因**：`build()` 里有个安全下限：

```python
budget = int(max_context_tokens * (1 - output_reserve_ratio))   # 1500 * 0.75 = 1125
budget -= system_tokens + tool_schema_tokens
budget = max(budget, 2_000)                                     # ← 变成 2000
```

这个下限本身是**正确的设计**（预算再紧也要留出系统提示和最近一轮的空间），
但它意味着"把 `context_window` 配得很小"并不会让裁剪更激进——
下限兜住了。

我的测试用了 1500，预算被抬到 2000，历史总量（1882）根本没超，自然不触发折叠。

**修复**：测试参数改成 `max_context_tokens=6000`（预算 4497，在下限之上），
并且**拆成两个用例**分别覆盖两条路径：

- `test_context_folding`：`keep_recent_turns=1`，只靠折叠就够 → 断言 `dropped == 0`
- `test_context_dropping`：`keep_recent_turns=50`（覆盖全部轮次，折叠被禁止）
  → 断言 `folded == 0` 且 `dropped > 0` 且最终 token 在预算内

**教训**：一个"没触发"的测试比没有测试更危险——它会给你虚假的安全感。
写裁剪类测试时，必须**算清预算和总量**，让被测路径真的被执行。
另外：代码里的"安全下限 / 兜底 / 默认值"这类东西，
一定要写注释说明它会影响什么，否则排查时会浪费大量时间。

## 坑 4 · 策略层拿不到工具的可逆性

**现象**：`readonly` 模式下连 `read_file` 都被拒绝。

**原因**：测试里直接调 `policy.check("read_file", {...})`，
但策略层的可逆性表是靠 `ToolRegistry.register()` 回填的：

```python
def register(self, tool: Tool) -> Tool:
    ...
    self.policy.register_reversibility(tool.name, reversibility_of(tool))
```

没走注册，`tool_reversibility` 里查不到，`reversibility_of()` 就返回默认值
`REVERSIBLE`。`readonly` 模式下 `REVERSIBLE` → `DENY`。

**这不是 bug，是设计。** 而且默认应该是保守的：

> 查不到某个工具的性质时，按"写操作"处理。

`readonly` 模式下拒绝未知工具（fail-closed）比放行安全得多。

**修复**：测试改成先建 `ToolRegistry` 并注册工具，再调 `policy.check()`——
这才是真实调用路径。同时在测试里加注释说明这个默认行为是刻意的。

**教训**：测试要用**和产品代码相同的装配路径**。
绕过注册中心直接测底层组件，测的是"组件在错误配置下的行为"，
不是"系统在真实配置下的行为"。

## 小结：五类陷阱

| 坑 | 类型 | 防御手段 |
|---|---|---|
| 1 | 真值短路（`Path("")` 为真） | 用 `None` 显式表示"未传" |
| 2 | 单次处理代替循环收敛 | 裁剪/限流一律写成 `while 不满足约束` |
| 3 | 隐藏的安全下限 | 兜底逻辑必须写注释；测试要算清阈值 |
| 4 | 绕过真实装配路径 | 测试走完整装配流程 |
| 5 | `None` 当覆盖值用 | 判据是**值**不是**键** |

这四个坑都是 `tests/smoke_test.py` 里的用例抓出来的。
这也是为什么这个项目坚持"零依赖 + 可离线测试"——
如果测试需要真实 API Key 才能跑，上面第 1 和第 2 个坑很可能就漏到线上了。

## 坑 5 · 命令行没传的参数把配置清空了

**现象**：`4-code/.env` 里 `AI_API_KEY` 配得好好的，但 `python -m maodingcode`
就是报"缺少 API Key"。配置文件肉眼看着完全正确，`/config` 显示的却是空的。

**原因**：`_apply_overrides()` 按**键**挑字段，而不是按**值**：

```python
# ❌
provider_keys = {
    k: v for k, v in overrides.items()
    if k in {"base_url", "api_key", "temperature", "max_tokens", "context_window"}
}
```

调用方（CLI 的参数装配）总是把这些键**全都**放进 dict，
没传的那个值是 `None`。于是：

```python
overrides = {"api_key": None, "base_url": None, ...}   # 用户一个都没传
cfg.provider = replace(cfg.provider, api_key=None)     # ← 把 .env 读到的 key 覆盖成 None
```

`replace()` 不区分"这个键没出现"和"这个键的值是 None"，
它只管把传进来的字段写进去。所以 `.env` 里的值被静默清空，
而随后的一致性校验又正确地报了"缺少 API Key"——
报错是对的，但你看着 `.env` 里明明白白的 key，只会怀疑人生。

**修复**：判据换成**值**：

```python
provider_keys = {}
for key in ("base_url", "api_key", "temperature", "max_tokens", "context_window"):
    value = overrides.get(key)
    if value is not None and value != "":     # 空值 = 没传
        provider_keys[key] = value
```

同时保留 `stream` 用 `in` 判断的例外，因为 `False` 是它的合法取值。

**为什么这个 bug 特别值得记**：

1. **它是"静默失效"**。不崩、不报错、不留日志，只是行为不对。
   这类 bug 的排查成本远高于崩溃型 bug。
2. **它的触发路径是"最普通的用法"**。用户只要不显式传 `--api-key`
   就会命中——也就是 99% 的调用都会命中。
3. **它暴露了一个通用反模式**：用 `X or default` / 真值测试来处理
   "可选参数"，在值域包含 `None` / `""` / `False` / `0` 时必然出错。
   要么用哨兵对象区分"没传"，要么按值判断。

**现在的状态**：`tests/smoke_test.py::test_overrides_do_not_clobber_env`
把三种情况都钉死了——未传不覆盖、显式传要生效、`stream=False` 能覆盖。
