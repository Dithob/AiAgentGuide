# 06 · Skills 技能系统

代码：`maodingcode/skills/loader.py`

## 工具 vs 技能

想清楚这个区分，整个设计就顺了：

| | 工具（Tool） | 技能（Skill） |
|---|---|---|
| 回答 | 能做什么 | 该怎么做 |
| 载体 | Python 代码 | Markdown 文档 |
| 谁维护 | 开发者 | 用户自己就能加 |
| 生效方式 | 注册进 registry | 注入上下文 |

举例：`run_shell` 是工具（能执行命令），
"代码审查要按正确性/安全/可维护/性能四个维度查，输出分级问题清单"是技能。

**技能本质上是一种按需加载的提示词包。**

## 为什么要按需加载

如果 20 个技能全部塞进系统提示，会发生什么：

- 系统提示膨胀几万 token，**每轮都发**，成本直接翻几倍；
- 大部分内容与当前任务无关，稀释注意力，反而降低效果。

所以分两步：

```
启动时：discover() 扫描目录 → 只解析 frontmatter 的 name/description
       ↓
常驻：  只把「名字 + 一句话说明」放进系统提示（几 KB）
       ↓
按需：  模型判断相关时调用 use_skill(name) → 才把正文读进上下文
```

加 100 个技能，系统提示也只涨几 KB。这是技能机制能规模化的关键。

## SKILL.md 格式

```markdown
---
name: code-review
description: 对一个文件或一段改动做代码审查，输出分级问题清单。当用户要求"审查代码""review 一下"时使用。
---

# 代码审查

## 步骤
1. 先用 run_shell 执行 git diff --stat 了解范围
2. ...

## 输出格式
...
```

`description` 写得好不好直接决定这个技能会不会被用上。
**必须写清楚"什么时候用"**，因为模型就是靠这句话做判断的。

目录布局支持两种：

```
skills/
├── code-review/
│   ├── SKILL.md          ← 推荐：可以带脚本、模板等资源
│   └── scripts/check.sh
└── quick-fix.md          ← 单文件技能
```

## frontmatter 解析

```python
meta, body = parse_frontmatter(text)
# {'name': 'code-review', 'description': '...'}, '# 代码审查\n...'
```

只支持 `key: value` 和 `key: [a, b]`，刻意不引入 PyYAML——
技能头部就这么几个字段，多一个依赖不值得。

## 两个暴露给模型的工具

```python
use_skill(name)   # 加载完整正文
list_skills()     # 列出全部技能（含路径），用于确认装了哪些
```

`Skill.render()` 会把技能**目录路径**也带上：

```
# 技能：code-review

技能目录：/workspace/skills/code-review
（该目录下的脚本与模板可用相对路径直接引用）

# 代码审查
...
```

这一点很重要：技能正文里可以写"运行 `scripts/check.sh`"，
模型拿到技能目录后就能用 `run_shell` 正确解析相对路径。

正文超过 20000 字符会截断——技能不是文档仓库，太长说明该拆分。

## 与系统提示的配合

`index_for_prompt()` 生成的索引里有这段引导语：

> 下面是按需加载的做事方法。当某个技能的适用场景与用户当前诉求吻合时，
> 调用 use_skill 把它的完整内容读进上下文，再照着做。**不要凭技能名猜测内容。**

最后一句是踩过坑加的：不写这句话，模型有时会看到 `code-review` 这个名字
就凭想象开始"审查"，而不是先加载技能看真实步骤。

## 什么时候该写成技能而不是工具

| 场景 | 选择 |
|---|---|
| 需要调用外部系统、有确定输入输出 | 工具 |
| 是一套流程、判断标准、输出格式约定 | 技能 |
| 需要权限检查、有副作用 | 工具 |
| 纯方法论、靠提示词就能改变行为 | 技能 |
| 逻辑复杂、需要单元测试 | 工具 |

两者可以组合：技能里可以要求模型调用某些工具，
比如 `code-review` 就要求先调 `run_shell` 跑 `git diff --stat`。

## 示例技能

`skills/code-review/SKILL.md` 展示了完整写法，值得注意的几个点：

- 明确写了**四个检查维度**，而不是笼统说"仔细审查"；
- 定义了**分级标准**（BLOCKER / MAJOR / MINOR / NIT），让输出可比较；
- 明确说"**不要为了凑数而报问题**"——不写这句，模型倾向于硬找问题；
- 明确说"**不要顺手改代码**，先出报告"——约束模型的行为边界。
