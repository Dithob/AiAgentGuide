# 03 · 上下文工程

代码：`maodingcode/core/context.py`

## 一次请求到底发出去了什么

```
┌─────────────────────────────────────┐
│ system      系统提示（每轮都发）        │  ← 最贵的常量
├─────────────────────────────────────┤
│ user        历史对话（会被裁剪）        │
│ assistant                              │
│ tool                                   │
├─────────────────────────────────────┤
│ tools       工具 schema（每轮都发）     │  ← 第二贵的常量
└─────────────────────────────────────┘
```

上下文工程的三个问题：**装什么、装多少、怎么省。**

## 装什么：系统提示分区装配

系统提示不是一大坨字符串，而是分区块管理：

```python
sections = {
    "identity":    "你是谁、工作方式",        # 必填
    "environment": "工作区路径、平台",        # 必填
    "conventions": "代码规范、行为约束",      # 必填
    "memory":      MAODING.md 的内容,       # 有才注入
    "skills":      技能索引,                 # 有才注入
}
```

`_rebuild_system_prompt()` 按固定顺序拼接，保证提示的**前缀稳定**。

前缀稳定这件事很关键：多数模型服务做 prompt caching 是按前缀匹配的。
如果每轮系统提示的开头都在变，缓存命中率会掉到 0，成本直接翻几倍。
所以动态内容（技能索引、记忆）都放在后面，静态内容（身份、环境）放在前面。

**系统提示刻意写得短。** 它每轮都发，堆得越多，用户真正的问题能分到的注意力就越少。
`default_system_sections()` 里三段加起来不到 300 字，是权衡后的结果。

## 装多少：token 预算

```python
budget = context_window * (1 - output_reserve_ratio)   # 预留 25% 给输出
budget -= system_tokens + tool_schema_tokens
budget = max(budget, 2_000)                            # 安全下限
```

`output_reserve_ratio = 0.25` 的意思：不要把输入塞满。
输入占满窗口后，模型没有空间生成回答，会出现"回答被截断"或直接报错。

`max(budget, 2000)` 是安全下限：预算再紧也要留出 2000 token 给系统提示和最近一轮，
否则会把上下文裁到"模型连问题都看不见"。
**副作用**：把 `context_window` 配得特别小（比如 2000）并不会让裁剪更激进，
因为下限兜住了。这一点在文档里写清楚，免得排查时以为是 bug。

## 怎么省：两级裁剪

顺序是**先折叠、后丢弃**。

### 第一级：折叠（保留结构，丢掉细节）

把较早的工具输出压成一行：

```
[历史工具输出已折叠：grep_files(path=src) 返回 8421 字符，摘要：匹配 47 条（扫描 12 个文件）]
```

为什么先折叠？因为**丢消息会破坏 `tool_call` / `tool_result` 的配对**。
一旦配对破裂，多数模型服务返回 400，整个会话就废了。
折叠只改内容、不动消息结构，天然安全。

保护机制：`keep_recent_turns`（默认 6）轮以内的工具输出**不折叠**。
模型要靠最近的完整上下文接着干活，把最新的工具输出折叠掉等于蒙住它的眼睛。

### 第二级：丢弃（整轮丢）

折叠还不够时，从最早的轮次开始**整轮丢弃**：

```python
for start in starts[1:]:            # starts = 每轮 user 消息的下标
    if total_all - prefix[start] <= budget:
        return history[start:], ...  # 找到第一个装得下的切点
```

三个必需的性质：

1. **必须整轮丢**（user 开头到下一个 user 之前），理由同上——配对不能拆。
2. **必须持续丢直到装得下**，不能只丢一轮。这是本项目真实踩过的坑（见 `11-实现踩坑记录.md`）。
3. **至少保留最后一轮**，即使仍然超窗也要把当前问题发出去——
   超窗是服务端的事，让用户完全看不到回应更糟。

用前缀和数组把每次试算做成 O(1)，避免 O(n²) 重复求和。

## 工具输出入库前先截断

`add()` 里对 role=tool 的消息做一次截断：

```python
if len(content) > max_tool_output_chars:   # 默认 24000
    保留头尾，中间替换成 "... [省略 N 字符] ..."
```

为什么不直接存全量、等裁剪时再说？
因为一条 10 万字符的工具输出一旦进了历史，后面每一轮裁剪都要重新遍历它。
入库存一个上界，后面的开销是可控的。

头尾都保留是刻意的：报错堆栈在尾部，有用信息在头部，砍中间最划算。

## 可观测性

`ContextStats` 记录每次装配的量化指标：

```python
stats.system_tokens       # 系统提示占用
stats.history_tokens      # 历史占用
stats.tool_schema_tokens  # 工具 schema 占用
stats.folded_messages     # 这次折叠了几条
stats.dropped_messages    # 这次丢了几条
```

"模型怎么忘了刚才说的话" 这类问题，全靠这几个数字定位。

## 常见误区

| 误区 | 实际情况 |
|---|---|
| 历史越长越好 | 每轮都重发，成本线性增长，且会稀释注意力 |
| 用向量检索替代裁剪 | 检索解决"大"，不解决"准"。项目约定这类结构化文本全量注入更准 |
| 折叠工具输出会丢信息 | 丢掉的是细节，保留的是"做过什么、结果多大"。真要细节可以重新调用 |
| 系统提示写得越详细越好 | 它是每轮都发的常量，越长越贵，且挤占用户问题 |
| 裁剪只按条数就行 | 必须按 token 预算，因为工具输出和对话的长度差两个数量级 |
