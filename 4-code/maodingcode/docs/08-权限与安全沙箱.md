# 08 · 权限与安全沙箱

代码：`maodingcode/security/policy.py`

## 为什么权限不能交给模型

一个 coding agent 最危险的时刻，是它"很有把握地"执行了一条破坏性命令。

有人会想：让模型自己判断危不危险不就行了？不行。原因是**模型可以说服自己任何事**。
给它一个"请谨慎执行命令"的提示，它依然会在某些上下文下认为
`rm -rf ./build` 是合理的清理操作——而如果工作目录变量没展开对，就是灾难。

所以权限必须是**确定性的、可审计的、模型改不动的**。

## 三挡权限模式

| 模式 | 只读工具 | 写文件（工作区内） | 执行命令 | 不可逆操作 |
|---|---|---|---|---|
| `readonly` | 放行 | **拒绝** | **拒绝** | **拒绝** |
| `suggest`（默认） | 放行 | 放行 | 询问 | 询问 |
| `auto` | 放行 | 放行 | 放行* | 放行* |

\* 即使 `auto` 模式，命中危险命令黑名单的仍然**直接拒绝**。

`readonly` 模式的用途：让 Agent 先"看看"不改动任何东西。
`auto` 只应该在完全可信的目录里使用。

## 可逆性分级

权限决策的核心依据是**这个动作能不能撤销**：

```python
class Reversibility(str, Enum):
    READ_ONLY     = "read_only"      # 无副作用
    REVERSIBLE    = "reversible"     # 有副作用但可回滚
    IRREVERSIBLE  = "irreversible"   # 难以回滚
```

`run_shell` 一律标 `IRREVERSIBLE`，因为**你无法从命令字符串判断它会不会删东西**。
这是保守的正确做法。

可逆性在 `ToolRegistry.register()` 时自动回填给策略层：

```python
def register(self, tool: Tool) -> Tool:
    self._tools[tool.name] = tool
    if self.policy is not None:
        self.policy.register_reversibility(tool.name, reversibility_of(tool))
```

好处：工具的性质只在一处声明（工具定义里）。维护两份表迟早不一致。

**fail-closed 设计**：策略层查不到某个工具的可逆性时，按 `REVERSIBLE` 处理。
所以在 `readonly` 模式下，未注册的工具会被拒绝——宁可误拒，不可误放。

## 危险命令黑名单

```python
DEFAULT_DENY_PATTERNS = (
    (r"\brm\s+(-[a-zA-Z]*\s+)*-[a-zA-Z]*[rf]", "递归强制删除"),
    (r"\bmkfs(\.\w+)?\b",                      "格式化文件系统"),
    (r":\(\)\s*\{.*\}\s*;\s*:",                "fork 炸弹"),
    (r"\bgit\s+push\s+.*--force",              "强推覆盖远端历史"),
    (r"\bgit\s+reset\s+--hard\b",              "丢弃全部未提交改动"),
    (r"\bcurl\b[^|]*\|\s*(sudo\s+)?(ba|z|)sh\b", "管道执行远程脚本"),
    # ... 共 16 条
)
```

设计原则：**只列"几乎没有正当理由让 Agent 自动执行"的模式。**

这条线要划得准：

- 划太松 → 拦不住真危险的操作，等于没有；
- 划太严 → 用户正常的 `git clean -n`（只看不删）都被拦，会关掉权限功能。

所以黑名单里全是这类：删根目录、格式化磁盘、强推远端、清空历史、
管道执行远程脚本。这些操作**让 Agent 自动做**在任何场景下都说不过去。

黑名单的优先级高于一切——`auto` 模式也拦。

## 路径沙箱

```python
def is_inside_workspace(self, path: Path) -> bool:
    root = self.config.workspace_root.resolve()
    try:
        path.resolve().relative_to(root)   # 必须 resolve 后比较
        return True
    except ValueError:
        return False
```

**必须比较 `resolve()` 之后的路径**，否则 `../` 和符号链接都能绕过：

```
workspace=/home/me/proj
用户传  ../.ssh/id_rsa
  未 resolve: /home/me/proj/../.ssh/id_rsa  → 前缀匹配可能通过 ❌
  resolve 后: /home/me/.ssh/id_rsa          → relative_to 抛 ValueError ✅
```

规则：

| 动作 | 工作区内 | 工作区外 |
|---|---|---|
| 读文件 / 列目录 / 查找 | 放行 | 询问 |
| 写文件 / 改文件 | 按模式 | **询问**（即使 `auto`） |

另外还拒绝了含 NUL 字节的路径（`PermissionDenied`）。

## 确认弹窗的设计

`ui/render.py:confirm_prompt()` 遵循"1 秒内能判断"的原则：

```
┌──────────────────────────────────────────────────────────┐
│ 需要确认：run_shell                                       │
├──────────────────────────────────────────────────────────┤
│ 执行 shell 命令需要确认                                     │
│   command: python -m pytest tests/ -q                     │
└──────────────────────────────────────────────────────────┘
  执行？[y] 本次允许  [a] 全部允许  [n] 拒绝  →
```

三个要点：

1. **命令原文完整可见**，不能只显示前 30 个字符；
2. **必须写明为什么被拦下来**（"执行 shell 命令需要确认" / "命令命中危险模式"）；
3. **提供 `[a] 全部允许`**——一次会话里可能要跑十条测试命令，
   逐条确认会让人烦躁到直接切 `auto`，反而更不安全。

`auto-approve` 状态**每轮重置**（`_run_turn` 里 `self._auto_approve = False`），
不会跨轮泄漏。

## 已知局限

诚实地说，这套策略不是完整的沙箱：

- **黑名单是正则匹配，可以被绕过**。`r''m -rf`、变量拼接、编码混淆都能躲过。
  它的定位是"拦住手滑和模型的常见失误"，不是"对抗恶意攻击"。
- **没有系统级隔离**。真要跑不可信代码，应该上容器或 `seccomp`，
  而不是靠命令行黑名单。
- **`run_shell` 的权限粒度是整条命令**，无法表达"允许 pytest 但不允许 pytest 带某参数"。

生产环境应该：容器化执行 + 只读挂载 + 网络隔离 + 文件系统快照。
命令行黑名单只是最外面一层，别再往上加期待。
