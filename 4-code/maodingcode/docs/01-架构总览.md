## 分层

| 层 | 目录 | 职责 | 不应该知道的事 |
|---|---|---|---|
| 界面层 | `ui/` | 渲染事件、读用户输入、确认弹窗 | 不知道 Loop 内部状态机 |
| 装配层 | `cli.py` | 把组件按正确顺序拼起来 | 不实现业务逻辑 |
| 引擎层 | `core/` | Loop、上下文、记忆、埋点 | 不打印任何东西、不读 stdin |
| 能力层 | `tools/` `mcp/` `skills/` | 提供模型可调用的能力 | 不关心谁调用它 |
| 策略层 | `security/` | 确定性放行/拒绝判定 | 不知道具体工具怎么实现 |
| 接入层 | `provider/` | 一次模型调用的归一化 | 不知道 Agent 循环的存在 |

依赖方向严格单向：界面 → 引擎 → 能力 → 策略/接入。
没有反向依赖，所以每一层都能单独测。

## 三个关键抽象

### 1. Provider —— 把"模型"变成可替换件

```python
class Provider(ABC):
    def chat(messages, tools) -> ChatResponse: ...
    def count_tokens(text) -> int: ...
```

`AgentLoop` 只知道 `ChatResponse`（含 `content` 和 `tool_calls`），
完全不知道你用的是 DeepSeek 还是本地 Ollama。

**收益**：测试不用联网。换一个按剧本返回的 `ScriptedProvider`，
就能把收敛、工具执行、权限拦截全部覆盖——见 `tests/smoke_test.py`。

### 2. Tool —— 把"能力"变成统一描述

一个工具 = 名字 + 描述 + JSON Schema + 执行函数 + 可逆性标记。

描述决定模型**什么时候想起用它**，比参数说明重要得多。
所以本项目的工具描述都写成两段式：先一句"是什么"，再一句"什么时候用"。

### 3. Policy —— 把"能不能做"从模型手里拿走

```python
decision = policy.check(tool_name, args)   # -> ALLOW / ASK / DENY
```

模型只负责"想做什么"，"能不能做"由确定性的查表 + 正则决定。
这是整个安全模型的地基：**模型改不动它。**

## 一次完整请求的数据流

以"帮我给 utils.py 加个函数"为例：

```
1. cli.py               读入用户输入
2. AgentLoop.run()      context.add(Message.user(...))
3. ContextManager.build()
                        系统提示 + 历史 + 工具 schema → 预算内裁剪
4. Provider.chat()      发送请求
5. 模型返回 tool_calls: [read_file(utils.py)]
6. Policy.check()       只读 → ALLOW
7. ToolRegistry.dispatch() 执行 → 文件内容
8. Message.tool_result()  回灌进 context
9. Tracer.record_*()    记录步数 / token / 耗时
10. 回到 3，循环
11. 模型返回纯文本 → StopReason.COMPLETED
12. render.cost_report() 打印统计
```

## 配置装配顺序

`cli.py:Session.__init__` 的顺序是有讲究的，不能随便调换：

| 顺序 | 做什么 | 为什么在这个位置 |
|---|---|---|
| 1 | 建 `Policy` | 工具注册时会回调它回填可逆性，必须先在 |
| 2 | 注册内置工具 | 依赖 1 |
| 3 | 加载技能 | 只把索引写进系统提示，正文懒加载 |
| 4 | 连接 MCP | 单个 Server 失败要隔离，不能拖垮启动 |
| 5 | 建 `ContextManager` + 记忆 | 需要 3 的索引来装配系统提示 |
| 6 | 建 `Provider` + `AgentLoop` | 最后拼引擎，前面都是它的依赖 |

第 4 步的失败隔离值得单独说：一个 MCP Server 拉不起来（命令不存在、网络不通），
只记进 `MCPManager.errors`，`/mcp` 里能看到，但 Agent 照常启动。
如果在这里抛异常，用户会因为一个用不上的第三方 Server 而完全没法用工具。

## 为什么不引入框架

没有用 LangChain / LangGraph。理由是：

- 这个项目的目的是**把 Agent 运行时讲清楚**，框架会把关键细节藏起来；
- 核心链路不到 200 行，自己写的可调试性远好于学一套框架的抽象；
- 零第三方依赖让它在任何装了 Python 3.11 的机器上都能跑。

什么时候该上框架：需要复杂的状态机编排、需要 checkpoint 与回滚、
需要多人协作维护时——那是 `17-多Agent` / `18-LangGraph` 那两章的适用场景。
