# 代码审查

## 目标

找出**真实存在**的问题，而不是把代码重写一遍。审查报告的读者是想快速决定
"这个改动能不能合"的人，所以结论要摆在最前面。

## 步骤

1. **先看改动范围**
   用 `run_shell` 执行 `git diff --stat` 了解改了哪些文件；
   如果用户指定了具体文件，直接跳过这一步。

2. **读完整上下文，不要只看 diff**
   用 `read_file` 读出改动所在的整个函数/类。
   只看 diff 很容易把"上游已经保证了的前提"误判成 bug。

3. **按四个维度逐项检查**

   | 维度 | 具体找什么 |
   |---|---|
   | 正确性 | 边界条件、空值、并发、异常吞掉、资源未释放 |
   | 安全性 | 注入、越权、密钥硬编码、不可信输入直接拼命令或 SQL |
   | 可维护性 | 重复逻辑、过深嵌套、命名与行为不符、缺失的必要注释 |
   | 性能 | 循环里查数据库/发请求、无界缓存、N+1 查询 |

4. **给每个问题定级**
   - `BLOCKER`：会上线出事，必须改
   - `MAJOR`：应该改，会在特定条件下暴露
   - `MINOR`：建议改，不影响正确性
   - `NIT`：可改可不改，纯风格

5. **给出修改建议**
   只对 BLOCKER 和 MAJOR 给出具体改法（可以是代码片段）。
   MINOR 和 NIT 只描述问题，不要展开写代码——审查意见太长没人看。

## 输出格式

```
## 结论
<一句话：能不能合，主要卡在哪>

## 问题清单

### [BLOCKER] <问题标题>
位置：<文件>:<行号>
问题：<为什么是问题，会导致什么后果>
建议：<具体怎么改>

### [MAJOR] ...
```

## 注意

- **不要为了凑数而报问题。** 如果代码没问题，就说没问题。
- 不确定的地方标 `[需确认]`，并说明你为什么不确定，不要猜。
- 不要顺手改代码——先出报告，等用户确认后再改。
